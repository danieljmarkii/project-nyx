# Schema migrations: DEFINER triggers, relational guards, the pre-flight and how a migration is applied.

Loaded when a session reads a file under these paths. Each rule keeps its guard and its pointer into `docs/engineering-lessons.md`; a guarded rule fails CI wherever its text lives. Same standing as `CLAUDE.md` (Tier 1).

- **A DEFINER trigger's error message never carries a value read from another row (CUL-867):** a `BEFORE` trigger fires before RLS, and under `SECURITY DEFINER` — the B-520 posture every integrity trigger holds — its lookup sees every tenant's rows, so anything the function reads from the parent and formats into a `RAISE` is a cross-account field read for any JWT holding the ids: 064's first draft returned a victim event's date through the `local_day` bound's message, one request, no ownership. A guard `RAISE`s once, naming only `NEW.*` values, with one message for "no such parent" and "out of bound" alike; "two unguessable UUIDs" is not a mitigation, because attachment paths are `${petId}/${eventId}/…` and a pasted signed URL outlives its token. Proven by a probe that sends the victim pair with an absurd value from a zero-pet JWT and asserts the message is free of the parent's data (064's C22 / C23 shape), run against the file before and after the fix. _(full account: `docs/engineering-lessons.md` §C-31)_
- **A guard on the CHILD is not the invariant, and a floor derived from the thing it checks cannot catch that thing's removal (CUL-899):** 066 guarded every write carrying `vet_visit_id` and left `vet_visits.pet_id` mutable, so ONE RLS-legal `UPDATE vet_visits SET pet_id` falsified the invariant its own `COMMENT ON FUNCTION` asserted — 045's diagnosis on the half it did not import, *a comment writing a cheque the code does not cash*. Ask of any relational guard: **what else can move?** A guard that re-validates on EVERY write also BRICKS what it failed to protect — the rows became un-editable on a terminal `23514` (→ client quarantine), so the predicate is `IS DISTINCT FROM OLD` on **both** the reference and the row's own scope: writable-but-violating is repairable, bricked is not. The sibling lesson is about the guard's guard: a non-vacuity floor that iterates the scanned-directory list is green when a directory is REMOVED from it (measured — a planted violation in `components/` passed), so derive the expected set from the REPOSITORY, never from the constant under test. Two registries, three rejected entries, one session: `ALLOWED` is an exemption, so a detector's registry earns each entry or pre-authorises a hole (C-32). A shape-based detector beats a bare-string one where a flag key and a table share a name (C-36, inverted), and its exclusions are stated as TESTS — `Array.from` was caught by the file's own proofs. State a guard's blind spots in the file; undocumented ones read as coverage. _(full account: `docs/engineering-lessons.md` §C-38)_

**Migration Safety Pre-flight.** Any PR containing a schema migration must include, in the PR description:
- **Rollback plan** — exact reversal steps (e.g. `DROP COLUMN X`, `DROP TABLE Y`) or `Irreversible — back up first` if not.
- **Destructive y/n** — `y` if the migration drops, renames, or alters a column with existing data; `n` if it's purely additive.
- **Backfill** — if existing rows need values, the SQL or script that produces them; `N/A` if not.

If destructive=`y`, the PR description also names the table(s) affected and the row-count check the PM should run before applying. Migrations are the highest-blast-radius action in this repo; this pre-flight is non-optional.

**Migrations apply from a cloud session via the Supabase MCP, on the PM's typed number (CUL-1614, D3).** `apply_migration` is a **live write**: run it only after the PM types `apply <NNN>` in the session that applies it (never a relayed message, never a prompt), and approve its dialog only on `MATCH`; then `get_advisors` (security + performance); `project_id` `aigchluqluzuhtbfllgh`, `name` snake_case. Own PR, Migration Safety Pre-flight; apply an additive one with its schema PR, one code needs before that code merges; the PR merges once applied and checked; a dispatched child never applies or merges one (steward §7). SQL Editor only if the MCP is down.
