A health record that never says whose it is

Open a logged vomit and the bar reads “Vomit”. The body reads “VOMIT” again, then the date. In a two-cat household nothing on the screen answers the first question a vet asks — which cat? — on the one surface an owner actually turns around and hands over, because it is where the photo and the AI read live.

CUL-574 fixed the version of this that named the wrong pet. This is the version that names none. B-550 hit the same thing one surface over on vet-document/[id] and put the name in the header, on the reasoning that the bar sits outside the ScrollView — so it is still on screen when the phone is turned around over a scrolled record.

R1 — Deciding: the form the pet’s name takes in the /event/[id] header bar. Everything else about this change is settled.
  • A · “Mochi’s vomit” — warmest, and literally the shipped B-550 shape one surface over. Costs a hand-maintained possessive noun per event leaf, on a label list another track is actively growing.
  • B · “Mochi · Vomit” — recommended. Label-agnostic, no shared-component change, and pet-first puts the ellipsis on the half the body restates. One helper in lib/logCopy.ts that medication/[id] and the other anonymous record screens can adopt unchanged.
  • C · two-line — the most legible at accessibility text and the only one where neither half can eat the other; buys that with a shared Header prop and ~10pt of bar. Worth it if you want this to become the app-wide record-screen header rather than a fix to one screen.
Consequence: B or A is an S-sized single-file change plus a copy unit test, shippable this session. C is the same change plus a shared-component PR and a pass over the other Header call sites — a bigger, more valuable, second-session shape. The fallback rule (miss → bare event label) and the single-pet rule (name renders unconditionally) are recorded above and are not part of R1.
