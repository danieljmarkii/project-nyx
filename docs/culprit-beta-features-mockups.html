Beta features program · Round 1

A place to try features before they’re finished

Beta features is a short list of things we’re still building — switched off for everyone by default, and visible only to accounts we’ve let in. It lets the Home screen widget live inside the shipping app — on for your account, invisible to everyone else — so its slow, secondary progress never holds up the App Store submission. Access is managed in the database for now; tying eligibility to Premium later is a deliberate one-line change, which is exactly why the two gates are kept separate.

First beta: Home screen widget Access: allowlist (DB-managed) Default: off for all Premium: deferred — swap-in later Reuses: the Ask flag primitive

Where it lives — and who sees it

Beta features sits in Settings → Preferences, next to Notifications. But the row only exists for accounts on the allowlist. Everyone else’s Settings looks exactly as it does today — no row, no hint that a beta program exists.

Invisible unless we’ve let you in

The eligibility gate is the same allowlist primitive the Ask feature already uses — a list of account IDs kept in app_config. If your ID isn’t on it, the Beta features row simply isn’t rendered. That’s the scope cut: no Premium check, no paywall, just a hand-picked cohort we manage in the database.

allowlist · app_config on for your account invisible to others reuses Ask primitive

The “1 on” hint on your row is optional polish — a quiet count of active betas, mirroring how the row reads its own state. Sam’s account (right) is off the list, so the whole program is absent for them.

A caveat, corrected. Flagging dark hides the in-app Beta features row from the review account — but it does not hide the widget itself. iOS shows every app’s widgets in the gallery to anyone who has the app; the flag only controls whether we publish data. So a reviewer (or any curious user) can still add the widget and see its ungated state — which is exactly why that empty state must look deliberate, not broken (see “The beta page”). Net: this reduces review exposure, it doesn’t eliminate it.

The opt-in layer — your choice, per feature

This is the second gate. Eligibility got you the shelf; nothing on it is live until you flip it. Each beta is off by default, and the intro line says so plainly.

defaults off reversible one card per beta records untouched

The Beta pill and the intro set expectations without over-promising: these features aren’t finished, and they might change. Warm and honest — no exclamation, no “new!” confetti (nyx-voice).

Naming — resolved (PR 4). “Beta features” it is: the plainest, most honest label, and every owner reads “beta” as unfinished, may change. “Labs” is dev jargon; “Early access” pre-optimises for a Premium future that’s deferred. If Premium reframes it later, renaming is a one-string change.

On is what actually starts it

Turning the widget on is what begins publishing its data to the home screen; turning it off stops that cleanly. The switch is the plain truth of the preference — no separate “apply”, no lie.

The teal hint appears only in the on state, because that’s the one moment the instruction is useful — iOS makes you add the widget from the home screen; the app can’t place it for you.

One genuinely new build piece. If you turn the widget off after adding it to your home screen, it needs an honest “switched off” state — otherwise it falls back to the generic “Sign in to start logging” placeholder, which would be a lie for a signed-in owner. That’s the only new widget UI this needs, and it’s only reachable once an owner can flip it off themselves.

How access works — two gates, never conflated

Eligibility decides whether you see the shelf. Opt-in decides what’s on. Keeping them separate is the whole trick: it’s what makes the eventual Premium swap a one-line change rather than a redesign.

Gate 1 · eligibility

On the allowlist?

No →Beta features doesn’t appear in Settings at all.
Yes →You see the Beta features shelf.
Owned by us. A list of account IDs in the database.

Gate 2 · opt-in

Toggled on?

No →Feature stays off (the default).
Yes →Feature is live for your account.
Owned by you. A switch on the beta page.

Today, and the one-line future

  • Gate 1 today = the allowlist. We add an account ID in the database; that account sees the shelf. Yours is the first.
  • Gate 1 later = Premium member — or “Premium or on the allowlist”, so we keep internal testers. This is the only line that changes.
  • Gate 2 = the toggles. This never changes.
The swap costs nothing on this page. When Premium ships (RevenueCat + entitlements), Gate 1’s check moves from “is your ID on the list” to “are you Premium”. The beta page, the toggles, and the widget don’t change at all — which is why we’re not building any of the Premium machinery now.

One honest limit worth stating: the allowlist resolves on the client, so it’s a cohort gate, not a hard paywall. Perfect for a beta (worst case, someone sees a widget early). When money is involved, the real enforcement is the server-side entitlement check — that’s Gate 1’s future job, not the allowlist’s.

New betas cost one card each

Ask already lives behind the same per-account flag, so it’s the natural next candidate to surface here as a self-serve beta — shown as an example, not committed scope. Nothing else on the page moves when a beta is added or graduates out.

When a beta “graduates”, its card leaves the shelf and it becomes an ordinary feature — free or Premium is decided by that feature’s nature at that time, separately from beta access. Early access is a convenience; it never means a care feature gets paywalled (Pets > $).

Feedback is the point of a beta. The “Share feedback” row already in Settings → Support is the low-lift channel for round 1; a beta-specific prompt is a later nicety, not a blocker.
