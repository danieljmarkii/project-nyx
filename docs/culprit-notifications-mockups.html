B-661 · Notification Foundation · PRs 3–4 · Rounds 1–2

Turning notifications on, honestly — and what they open

Part 1 ships one notification — a 9pm daily summary, off by default, one per account across every pet. Round 2 (new, below) locks the two PR 4 surfaces: the lock-screen notification itself and the Day Summary screen it opens, in four states — ordinary, incident, zero-log, and multi-pet. Round 1 (further down, unchanged) is the consent model that turns it on: the primer sheet and the settings screen's three honest permission states. The through-line across both is the same — the notification never says what it cannot know, and the screen it opens describes and doors, it never concludes.

Round 2 · The notification, on the lock screen

This is the whole of what fires at 9pm. iOS runs no JavaScript at local-notification fire time, so the body is static — decided once, when the schedule is set, not when it fires. A body that named the day's contents ("no incidents today") could therefore be computed against a stale record and land as reassurance from a record that has since changed — which clinical-guardrails forbids. So the body speaks to the ritual, never the record, and is never wrong. The truth lives one tap away, on the Day Summary screen (below), which reads live.

What the body may and may not say

The lock-screen body is the one string in Part 1 that is computed early and can’t be corrected at fire time, so it carries the hardest safety rule:

  • G1 — asserts no record contents. No counts, no “no incidents”, no med names. It says the day is ready to read, which is true on every day.
  • D3 — one per account. Three pets never means three pings; the neutral body is also the multi-pet-safe shape.
  • Fires whether or not anything was logged. A ritual that skips days teaches the owner the channel is unreliable; the zero-log day is handled by the screen, not by silence.
static body (G1) neutral (D3) tap → Day Summary
Ruling this round (§10.3 — Designer + T&S): the body stays neutral even for a single pet. A pet name on a lock screen is an involuntarily-public exposure we can’t scope to the owner’s iOS preview setting, and the body already asserts nothing (G1) — so naming buys only warmth, bought with the owner’s exposure. The warmth lives where the surface is private (the in-app primer names the pet); the named body is recoverable later as an explicit opt-in (backlog). Designer dissent recorded, not erased.

Round 2 · The Day Summary screen — four states

The surface the notification opens. It answers exactly one question — what happened in {pet}’s record today — and every row is a doorway into the event it names. It is not a rival Home: no AI, no verdict, no score, no logging FAB. Meals carry their intake, doses their adherence, symptoms surface plainly — and the screen describes and doors, it never concludes (G3).

Doorway rows, earliest-first

The day reads top-to-bottom, the same order and the same labels as the calendar drill-in (one mapper, describeDayEvent, so a food/dose reads identically everywhere). Each row is a tap into its own event detail.

  • Meals carry intake (“most eaten”), doses carry adherence (“given”) — a null rating shows no qualifier, never an assumed “given”.
  • Glyph tint = category — meal teal, medication slate, symptom rose (next frame), everything else neutral.
  • A treat is a meal-typed row named for its food (“Dental chew”), teal like its sibling.

The concern surfaces — the screen still doesn’t conclude

A vomit sits in the day in its own rose, exactly where it happened, next to the refused breakfast. What the screen doesn’t do is judge it: no “concerning”, no severity, no all-clear over the good rows around it.

  • G3 — describes and doors. The row is a tap into the event detail, where the single-incident AI read (with its own escalate-never-reassure rules) lives. The summary never re-renders that verdict in miniature.
  • A refusal reads “refused” — plainly, never softened to “picky”. Intake is not preference.
  • Nothing here reassures on the good rows: a calm-looking day is a record statement, not a wellness one.
symptom surfaces plainly no verdict (G3)

A designed state, not a blank — and not an all-clear

The zero-log day is the clinically sensitive one, and its copy is bound by G2: absence is a record fact, never a wellness verdict. No “all quiet”, no “all clear”, no “nothing wrong” — a silent record is not a well pet, and this screen never implies it is (asserted by a test over the copy).

  • It names the pet on a single-pet account (“Biscuit’s record”) — the wedge owner’s commonest empty state, and the pet’s name is what makes it land (nyx-voice Pattern 1). A no-pet / multi-pet-all-empty screen falls back to “Nothing in the record today”.
  • The CTA is new this round. This screen has no FAB, so the body’s “ten seconds to add” invitation would otherwise dead-end. A low-emphasis link (accent text, never a filled button — it invites, it doesn’t demand) opens the quick-log.
names the pet record fact (G2) CTA → quick-log

One screen, sectioned per pet — active first

Because there is one notification per account (D3), the screen it opens carries every pet, sectioned, with the active pet first. The pet heading appears only when there’s more than one pet to disambiguate.

  • A pet with nothing logged gets the same G2 line, scoped to that pet — “Nothing in Mochi’s record today.” A record fact about Mochi’s day, never an all-clear over Mochi.
  • No per-pet CTA — the whole-screen zero-log carries the log door, but a per-pet line can’t pre-select the empty pet, so it stays a plain fact rather than a mis-targeted button.
active pet first per-pet zero-log (G2)

Round 1 · The consent model that turns it on — unchanged

Everything below shipped in PR 3 and is reproduced here so this one link carries the whole feature. Two gates, never conflated: the OS permission (one system prompt per install) and the product opt-in (a per-category toggle, defaulted off).

The primer — before the one system prompt

We get exactly one system permission prompt per install, so it is never fired at launch, at onboarding, or unprompted. It fires only from an explicit toggle-on, and only after this sheet. Reaching the sheet costs nothing; the OS prompt is spent only if the owner taps Turn on.

What the sheet has to earn

By the time the owner reaches iOS's Allow / Don't Allow, they should already know what "Allow" means. So the primer says all three things §2 asks for:

  • What it sends — a look back at the day's record.
  • How often — just one a night.
  • That it's reversible — "turn it off whenever you like."
retrospective copy names the pet no exclamation

G4 (the D7 lineage): the copy is a look back at "the meals, symptoms, and doses you logged" — past tense, owner-authored. Nothing here reads like a medication reminder, because Part 1 ships none.

Declining spends nothing. "Not now" and the scrim only dismiss — the code never reaches the request, so the one prompt is preserved for a later, more considered yes.

One notification per account (D3)

Three pets must never mean three 9pm pings. On a multi-pet account the copy drops the pet name and says "for all your pets" — which is also the lock-screen-privacy-friendly shape.

This is the only copy difference between the two frames; everything else — the icon, the permission note, the buttons — is identical.

Open item for this round: is naming the single pet ("Biscuit's day") worth the small lock-screen exposure, or do we standardize on the neutral body everywhere? Designer + T&S call (§10.3).

The settings screen — three honest states

A toggle that is on while the OS has denied permission is a lie with a safety cost. So the screen renders exactly what is true right now — never a switch that can't do what it claims.

State (a) · never asked

‹
Notifications
You choose what Culprit lets you know about — and you can change your mind any time.
Daily summary
A calm look back at the day’s record, around 9:00 each night

Interactive; the primer guards the first enable

Permission has never been asked, so the switch is live. Flipping Daily summary on opens the primer → the one system prompt. The switch shows on optimistically while the sheet is up, and snaps back if the owner declines.

The framing line carries G6: everything defaults off, and it says so.

Daily summary — live everything else — off (G6)

The screen shows only what's real — one live category. Future ones (B-288's check-in nudge, B-227's health insights) add their own live rows when they ship, rather than sitting here as dead "Coming soon" toggles now. None of them is a medication reminder — G4 holds.

State (b) · granted

‹
Notifications
You choose what Culprit lets you know about — and you can change your mind any time.
Daily summary
A calm look back at the day’s record, around 9:00 each night

Live — the toggle does what it says

Permission is granted, so the switch is the plain truth of the preference. Turning it on schedules the 9pm notification; turning it off cancels it. No primer here — there is no prompt left to spend, so a granted toggle-on writes straight through.

Reconcile is the integrity mechanism. Every time this screen surfaces, the live OS schedule is diffed against the stored preference + permission, and drift is repaired in the safe direction. No schedule is ever trusted to still exist.

State (c) · denied in iOS Settings

‹
Notifications
Notifications are off for Culprit
Turn them back on in iOS Settings and this switch comes back to life.
Open Settings
Daily summary
A calm look back at the day’s record, around 9:00 each night

Visibly inert — with the door back

The OS has denied notifications, so the switch cannot honor an "on". Rather than lie, the screen states it plainly and hands over a deep link straight to Culprit's iOS Settings page.

The banner uses a danger treatment — a red-tinted fill, a hairline, and a warning glyph (PM call, 2026-08-02: the earlier quiet-grey note was too easy to miss). This is a functional system state, not a health flag, so nyx-voice's "no alarm" rule — which governs the pet's health — doesn't apply here; surfacing it loudly is honest states (Principle 5) done right. The red action carries the fix — Open Settings.

Even the pref underneath stays honest. If the owner had turned Daily summary on and later revoked at the OS level, the switch still reads off here, and reconcile has already cancelled the orphaned 9pm schedule — so nothing fires that the owner can no longer see the source of. Re-grant in Settings and the switch comes back to life.

The one system prompt, in context

The primer's Turn on is the only thing that ever reaches this dialog. A granted result schedules and persists; a denied result never writes a toggle-on the OS won't honor — the screen simply drops to state (c).

System prompt · fired from the primer only

‹
Notifications
Daily summary
A calm look back at the day’s record, around 9:00 each night
“Culprit” Would Like to Send You Notifications
Notifications may include alerts, sounds, and icon badges. These can be configured in Settings.
Don’t Allow
Allow

Full authorization, asked once, properly

We deliberately don't use provisional (quiet) authorization: it would land the 9pm summary silently in Notification Center — a thing the owner opted into that looks like it doesn't work. Full alert authorization, asked once at the moment of intent, is the honest shape.

  • Allow → schedule the 9pm notification + persist the opt-in.
  • Don't Allow → write nothing; the screen becomes state (c).

Because iOS only shows this once, everything upstream — never at launch, never at onboarding, primer-gated — exists to make sure the one ask is a good one.
