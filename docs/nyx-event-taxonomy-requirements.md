## §3 The spine: families as presentation, leaves as data (D2)

- **Leaf = one `event_type` enum value.** The single analysis key everywhere (engine, report, History, sync) stays leaf-grain. - **Family = a constants-layer grouping**: picker group, category tint, ordering. ## §4 The selection framework (D1's quantitative half)

Five value axes, 0–3 each, every score citing the evidence pack; one cost axis. The sum ranks; the PM triages the ranking into waves. The framework **informs** — it does not decide (D1's cough/sneeze ruling predates it, and sneeze ships on family coherence despite a mid-table score; the framework's job is to make that kind of call visible, not to forbid it).

- **A · Own-record demand** — what the owner already logs in `other` notes (the F3 method). 3 = double-digit note count · 2 = several · 1 = adjacent evidence · 0 = none. *Honest limit: n=1 today (G6 generalized — never calibrate to one cat); becomes a real demand instrument when a cohort exists (§16 Q5).*
- **B · Population weight** — sweep A §A4 (claims rankings + VetCompass prevalence + presenting-sign studies), species-split. 3 = top-5 sign family both species or #1-class one species · 2 = top-10 presence · 1 = present in lists · 0 = negligible.
- **C · Instrument coverage** — sweep C §A: validated-instrument items the leaf derives (derive-don't-ask). 3 = derives items across multiple instruments or completes an index · 2 = one instrument item or a consensus sign-list item · 1 = proxy only · 0 = none.
- **D · Detection leverage** — lanes the leaf feeds at plausible logging density, or a deterministic safety rule it enables. 3 = immediate lane fit or safety rule · 2 = lane fit with new per-type config · 1 = data-only for now · 0 = no lane plausible.
- **E · Whitespace / strategic** — sweep B §B (nobody structures it) + the Zoetis derm/resp trip-wire. 3 = unstructured everywhere AND strategic pressure · 2 = unstructured everywhere · 1 = some competitors have it unstructured · 0 = commodity.
- **Cost** — S = tile + existing confirm · M = tile + attributes or photo-first fit · L = new primitive (measurement flow, escalation register, child table).

## §8 Read-surface degradation audit (binds every wave)

A new leaf value can reach **old app versions** (a flag-off or un-updated device on the same account — the household/multi-device LWW reality) and **deployed functions** pinned to older type sets. Rule: **every read surface renders an unknown `event_type` sanely, and every wave's PR verifies it.** The surface list: History rows + filters · Today/TodayZone · day summary · recap lane · the widget snapshot builder · `generate-report` (fetches all types, renders only `REPORT_SYMPTOM_TYPES` — unknown = silently ignored, verified 2026-08-23) · `generate-signal` (fetches only its type lists — unknown = invisible) · `ask` (G5 Timeline-parity — must at minimum name unknown-typed rows as events) · notifications day-summary counts. **Known state, corrected 2026-08-26 (HR-9 — v1.2 over-stated the label problem and missed the real one).** The label sinks are **already safe**, everywhere: `EventIcon` falls back to `CircleHelp`, and every label call site audited degrades gracefully to the raw key or a generic noun. Nothing crashes. So the app-wide "label audit" is a *verification* item, not a repair item, and a wave that budgets for a sweep here is budgeting for the wrong thing. The two real targets:

**(a) Silent de-symptomization — the one that softens the record.** Wherever categorization runs through `SYMPTOM_TYPES` (`lib/dayEvents.ts` → the recap lane and the day spine; `EventRow.tsx`; `TodayZone.tsx`), an unknown *symptom* type is not merely unlabeled — it renders **neutral rather than rose**, and it drops out of the symptom lane. A flag-off or un-updated device therefore shows the household's cough rows as ordinary neutral events on the day it matters. This is a silent softening of a health record, not a cosmetic fallback, and it is the class the §8 audit exists for.

**(b) The `undefined` hole on the safety rail.** The client re-derives Signal copy from a closed symptom union; a symptom the build doesn't know reaches the cross-pet safety banner as literal `undefined` ("recurring undefined since July"). This is not reachable by the existing unknown-*type* pin — the type is known; the *symptom* is new — and it is why W1-PR-3 splits client-first (§13a). Every wave re-runs both checks; neither is satisfied by "the label didn't crash." 

## §9 Engine handshake (membership, not floors)

Expansion never auto-updates the algorithm: each leaf makes an explicit per-lane membership decision; floors live in B-755's contract and are **owned product calibrations** where no guideline number exists (the cough finding — §4 of the deep-dive, verification pass).

**The mechanism this table assumes does not exist yet — building it is W1-PR-3b's first job (hard review HR-1, the pass's highest-consequence structural finding).** Today `CORRELATION_SYMPTOM_TYPES` is **one list** that scopes the DB fetch *and* is iterated by **all five per-type lanes** (① food-correlation · ③/④ · ⑦ chronicity · ⑤ · ⑥). There is no per-lane membership anywhere. So "add cough to ⑦" is not a list edit: adding `cough` to that list auto-enrols it in **①**, which can then emit a card naming a protein as associated with coughing — **the exact claim the cough row below forbids by name** — and in **⑤**, whose shipped template would offer to time a respiratory sign against a recent feeding (the regurgitation-vs-cough confusion the never-hairball rule exists to prevent). The ① window fallback also silently hands an unlisted type a 12h attribution window. Chronicity config is global too — one `minEpisodes` for every type — so an *owned cough floor* has nowhere to land.

**Therefore, binding on every wave: the fetch set is the UNION; membership is per lane; and a leaf's row below must decide EVERY lane, including — especially — the ones that must not fire.** A blank cell is not a default, it is an unfinished decision. The per-lane map and per-type floor config land **behaviour-neutral for the existing five types first**, with a negative fixture per lane that must *not* fire for the new leaf, and only then does the leaf join the lane it was scoped for.

**0. No evidence-quality guard may gate the EXISTENCE of a response — and for a presence-class finding it may not cap the TIER either (D16, ruled 2026-08-30; TIGHTENED per F1/F3 as D20, ruled 2026-08-30).** This is rule 4 generalised twice, and it is the organising rule of the whole contract: apply it first, and to every rule below.

Three of v1.3's closures each built an **evidence-quality escape hatch** — a marked "yes", a confirmable sleeping count, an answered chip — and then let that hatch decide whether the app spoke at all. In every case the animal that cannot pass through the hatch is the sick one: the partially-obstructed cat passing drops, the CHF dog who pants at rest, the covered-box household. One defect in three costumes, and a fourth (the RRR count-duration minimum) was found wearing the same one.

**The test, applied to every guard in this contract and to every guard a future wave adds:** *is there a patient for whom this guard can never be satisfied **because of** the illness the rule exists to catch?* If yes, the guard may set the **wording**. Whether it may also set the **tier** depends on the finding's class:

- **Presence-class finding** — one whose clinical weight comes from the *presence* of an observation rather than from a rate, a trend or a measurement. Here a guard may set the **wording only**. It may not lower the tier and it may not gate existence. Unresolved evidence reaches the same tier with **conditional wording** — *"if nothing is coming out, this is an emergency"* — which is a sentence that is true under both branches and therefore costs nothing to say.
- **Every other class** — a guard may still set the tier, as v1.4 permitted.

**Why the tightening (F3, F1).** v1.4 let a guard set "the wording **and** the tier", and two of the six silence defects used exactly that permission: they did not silence the patient, they *capped* it one tier below the emergency. Fourteen unresolved straining trips in five hours topped out at prompt-24–48h for a condition fatal in 24–48h, while the identical cat in an uncovered litter box banded — **the lid on the box deciding between a red alert and a shrug.** A tier cap on a presence-class red flag is a silence defect wearing a register.

**All three leaves W2 ships are presence-class**, so inside this contract the permission is wording-only, everywhere. The distinction is written as a class rather than as a list because a later wave will add leaves that are not (a measurement, a rate), and it should inherit the right half of the rule without re-litigating it.

**What silence is still permitted to mean.** Silence is permitted only where the record holds **nothing of the escalating class** — not where it holds something the app could not evaluate. "Couldn't tell" is not "no". "Couldn't measure" is not "no finding". "Not sure which cat" is not "no cat". Below-floor *observed-normal* is silence and carries no claim (the lane is escalate-only); below-floor *unevaluable* is never silence.

1. **The band's host never self-closes under it — and none of the host's silent exits reaches it (CE-21; extended per HR-14).** When a safety band renders in the B-745 sheet, the completion beat's dwell timer does not run and the sheet does not auto-dismiss — it stays until explicitly dismissed, and the dismissal is a visible control. Pinned with a test (the B-156 G1 rule: a safety prompt survives the time it takes to act). **The dwell timer was not the only way out.** The host already gives every non-confirm stage two dismissals that fall straight through to close: a **scrim tap** and the **Android back button**. So on the band stage the **scrim is inert and the back handler is a no-op**: the band takes the confirm stage's guarded treatment, not the done stage's pass-through, and the only exit is the labelled control. **All three exits are fixture-covered, not just the timer (F31).**

   **This applies to every band, including the pooled household band (rule 14).** A band is defined by its register, not by whether it names one animal.

   **The fourth exit — backgrounding mid-band — is survivable only because a durable card exists to come back to, and v1.5 routed it to a card that did not exist offline (F-C). 2. **The strain lane counts TRIPS — one predicate, no time-keyed collapse anywhere in it (CE-1, CE-7; REWRITTEN per HR-11; RE-RULED per D17).** The unit is a *trip*. The 3h episode collapse would silence the cluster rule permanently, and two surfaces printing two different strain numbers is the B-067 class — so the count is defined once, here, and every surface reads it.

   **A QUALIFYING ROW, defined once because it is load-bearing in three rules and two fixtures and was undefined in v1.4 (F30):** a `urine_strain` row for the subject (the pet — or, under rule 14, any pet in the household) that is **not soft-deleted** and whose `occurred_at` falls inside the window. Nothing else qualifies it: not its chip answer, not its `logged_via`, not whether it has hydrated a child row.

   **What v1.2 got wrong, and what v1.3's fix still got wrong.** v1.2 re-parameterised the generic episode module, which **chains** by design: an obstructed cat straining every ~8 minutes for two hours collapses to **one trip** at any gap ≥ 8 minutes, while a *less* sick cat straining every 25 minutes counts 5 and fires. The predicate was anti-correlated with severity. v1.3 split de-dup from counting — correctly — but then handed the de-dup job to a **fixed time window**, which is the same defect attenuated: the shipped window anchors to the cluster's **first** member (`report.ts:200`, `:959`), so the count saturates at `span / W` and under-counts across the whole obstructed band. And a time window cannot do the job it was given, because **the thing it is trying to separate is not separated by time**: a double-tap and a caregiver's second phone are minutes apart in both directions.

   **The rule: duplicate prevention belongs to the capture surface; the trip predicate does not collapse rows at all.**
   - **Trip count = the number of qualifying rows in the window.** No chaining, no de-dup window, no episode collapse. A row is a trip.
   - **A double-submit of one capture flow is prevented at the source, not repaired afterwards.** The app already has a **shared primitive** for this: `useSubmitGuard` (B-336), a latch whose contract is written at its call site — *true keeps the guard latched (the sheet is transitioning to the beat, so no later tap may write again); false releases it (the write failed, the owner is still on the confirm, so the pill must work again)*. The latch itself is a **ref**, not React state — `inFlight.current` in `hooks/useSubmitGuard.ts:30–42` — which matters, because two taps in one tick both pass a `disabled={submitting}` prop that is waiting on a state flush. The shipped confirm routes its save through the hook (`components/log/SimpleEventConfirm.tsx:105`, `:641`, handler at `:332`), and `app/log.tsx` uses the same one. **W2a's strain capture reuses the hook — it does not re-implement the guard**, and it does not settle for the `disabled` prop, which is the visual half of a latch and not the latch. A fixture pins it. *This is why the window was deletable: it was guarding something the capture surface already prevents, while demonstrably costing the batch-recall case below.*
   - **Accepted cost, stated rather than discovered (D17).** Two phones logging the same trip over-count by one, and one prolonged trip logged twice over-counts by one. **On this lane over-count is the safe error** and under-count is the failure HR-11 was filed for. `logged_by` would not fix it even if it existed: the household shares one credential (the B-054/B-086 evidence), so both phones are the same auth user, and `038_logged_via.sql` records a capture *surface*, not a person or a device.
   - **The cost is not symmetric across surfaces, and the report is where it is not (F24).** In the band, over-count is the safe error because the band's error budget is one-sided. In the **vet report** it is not: a count read as a physiological rate can mislead a clinician in either direction, and the stated cost is *per trip*, so two logging caregivers run a systematic ~2× inflation rather than a one-off +1. The resolution is the one this project already uses for exactly this class (the diet-trial C5 logging-density ruling): **disclose beside the number, never absorb it into the number.** Every count sentence keeps its **"you've marked"** attribution (rule 12) — the count is of *marks*, not of observed physiological events — and §10 carries the multi-caregiver limitation in the report's own words. Nothing about the predicate changes; what changes is that no surface presents it as a measurement.
   - **The case the deleted window was costing (Dr. Chen, verified).** The owner who comes home, realises the cat has been in and out of the box all evening, and logs three trips in three quick confirm passes writes three rows at `occurred_at ≈ now` — D10 makes strain witnessed-by-construction and the CUL-576 clock seed makes "now" the default, so this is the *modal* retrospective log, not an edge case. Under any time-keyed de-dup those three collapse to one and the canonical patient degrades to the n=1 line. Under this rule they are three trips.
   - **The report reads the same predicate, and does not collapse for display either (§10.3a; REWRITTEN per F11).** v1.4 permitted a display collapse with an escalate-on-presence merge, which put **two numbers** inside the report — a trip count of three beside one displayed entry carrying `dupCount: 3`, on D17's own rescued patient. The collapse is **deleted**: strain rows are never collapsed in the report, so the row count and the trip count are the same number by construction and the merge rule has nothing to govern. Accepted cost, stated: a 15-trip obstructed cat prints 15 rows. On a safety leaf the rows *are* the evidence, and a vet reading a suspected obstruction wants the timestamps.

   State in the code, at the predicate, *why* the generic episode module is not the mechanism here — the chaining property is the reason, and it is not obvious from the module's name. Every surface that speaks a strain count states its unit; §9's table records why strain is the one symptom whose safety count is not the episode count.

3. **Fire once per cluster — identity by MEMBER-SET INTERSECTION, the marker carries the tier it fired at, and it is written on DELIVERY (CE-8; restated per HR-15; REWRITTEN per v1.3 findings 6, 9, 10, 14; REWRITTEN AGAIN per F2, F7, F12, F21, F22, F27).**

   **What this rule governs, stated first because over-reach was three of the fourth pass's findings.** The marker governs **the arrival of a band** and **the arrival of a durable Signal card**. It governs nothing else. It does **not** gate the in-sheet capture-time lines at the lower tiers, it does **not** gate the ask, it does **not** gate a finding's membership in a band that is rendering anyway, and it does **not** gate the Signal card's continued presence once it has arrived. Scarcity is a property of *interruption*; a line inside a sheet the owner just opened interrupts nothing.

   - **A marker records the cluster's member ids and the tier it fired at:** `{ memberEventIds, tierShown }`.
   - **A cluster matches a marker iff their member id sets intersect.** Intersection is stable under adding a row, deleting a row, editing an `occurred_at`, and hydrating half the rows — which is every churn trigger, closed by one property rather than four guards. Member ids are **raw row ids**, so two devices that would pick different survivors still intersect.
   - **The band fires iff no matching marker exists, or the cluster's tier is HIGHER than every matching marker's `tierShown`** (the ladder is defined in 5a).
   - **The marker is written when the response is DELIVERED, never when it is computed (F22).** v1.4 specified the marker's read side and left its write side to the reader, and the attractive reading — whichever channel computes it, writes it — burns the marker on a background evaluation while the owner is on another tab, so *neither* channel delivers. So: the band's marker is written when the band **renders in a sheet the owner has open**; the card's marker is written when the card is **presented in a visible Signal zone**. An evaluation that resolves to no delivered surface writes nothing, and the next entry point (rule 6) speaks. This is "fails toward firing" applied to delivery rather than to identity, and it is the same direction rule 3 already takes for an unidentifiable cluster.
   - **Markers age out** once the cluster can no longer be live: `now − the CLUSTER's last member's occurred_at > X + quietPeriod`, and **quietPeriod ≥ X**, so a cluster can never outlive its own window. **The marker never ages out while a cluster it matches is still live (F27)** — v1.4 aged it against the *marker's* recorded members, so a continuously-live cluster that kept accruing rows re-banded every `X + quietPeriod` on an animal nobody had done anything about.
   - **The marker is persisted per pet, per device by design** — one household member seeing the band does not silence it for the other. Stated so it is not "fixed" later. **The claim that every device computes the same identity is deleted: it was false under ordinary incremental sync, and it was never needed** — each device firing at most once per cluster is the whole requirement.
   - Because it is persisted account-adjacent state, **the marker joins `wipeLocalSession`** (the CLAUDE.md local-wipe rule; T&S).
   - **"Fails toward firing" survives only for a cluster that cannot be identified at all** — never for a restart, and never for a cluster whose marker is simply present.

   **ACKNOWLEDGEMENT is the episode boundary, and it is the one primitive v1.5 adds (F7, F12).** v1.4 had no way for an episode to end. Deleting the productive-trip reset was right — it was the F1 inversion — but it left the contract with **no boundary and no acknowledgement path**, so a cat unblocked at the ER and re-blocking twelve hours later could never band again (the old episode's rows are still inside the window, so the cluster still intersects the old marker at an unchanged ceiling tier), and a resolved episode kept colouring the next one. The app has exactly one signal that the owner has seen and acted on a safety statement: **rule 1's labelled dismissal.**

   **The obvious form of this is wrong, and it is worth saying why, because it is the form a later session will reach for.** *"Acknowledging retires the marker"* re-fires immediately: the old rows are still in the window, so the very next evaluation finds a qualifying cluster with no marker and bands again — CE-8's wallpaper, arriving through the closure. So:
   - **Acknowledging does not retire the marker; it starts a new evidence baseline.** The marker records `acknowledgedAt` alongside `memberEventIds` and `tierShown`.
   - **After an acknowledgement, a band may fire again for that cluster only on counts computed over the rows logged AFTER `acknowledgedAt`**, against the same floors. One more trip therefore does not re-band; a genuine re-blocking — **N_U** fresh unproductive trips, or **N_R** fresh unresolved ones — does. **This adds no constant**: the floors are the ones 5a already defines, applied to a later slice of the same rows.
   - **A tier rise still fires regardless**, acknowledged or not (an animal that escalates from `presence` to `band` is not waiting on a baseline).
   - **Nothing else closes an episode.** Not the calendar, not a productive trip, not a soft delete. In particular there is deliberately **no quiet-gap parameter**: a gap long enough to separate two episodes inside the window is unreachable given `quietPeriod ≥ X`, so a fourth constant would have to be invented to make that boundary expressible, and the acknowledgement baseline answers the same clinical question — *has the owner acted, and is it happening again?* — with the floors already ruled.

   **The durable safety card — under D25 the client-injected 6a overlay, which is what makes every sentence in this paragraph evaluable offline: its REGISTER stands down on ACKNOWLEDGEMENT, never on the clock (F7).** v1.4 decayed the card's register once the cluster was no longer live (within X) — so an owner who backgrounds the app mid-band and returns eight hours later finds the emergency already stood down, **on an animal that has been blocked the whole time.** Rule 11 adopted the opposite principle in as many words (*the calendar alone may not de-escalate*), and rule 1's fourth exit depends on this card being the backstop for exactly that owner. So the card stands down from the **emergency** register to the **ongoing-pattern** register only when **both**: the owner has acknowledged it, **and** the cluster is no longer live. It never stands down to *nothing* — the record still holds the evidence, and a zone that advertised itself may not go silent (§10.3, B-494). An unacknowledged emergency card is not alarm wallpaper; it is an undelivered message, and CE-8's wallpaper was the band *re-firing*, which the marker still prevents.

   **The card is the current state; the band is the arrival (F12).** The band fires on a tier rise; the card's body is **recomputed on every evaluation** and always carries the current trip count and the current span. Under v1.5 that sentence was unsatisfiable in exactly the condition this contract cites — a server-cached card cannot recompute offline (F-C); under D25 the card is the 6a overlay, derived client-side from local rows at each of rule 6's entry points, so recompute-on-every-evaluation is implementable as written. So bad→much-worse does not need a second re-fire rule to be visible — three unproductive trips becoming fifteen changes the card the owner is looking at, without minting a second interruption at the same tier. *This is the deletion that closes F12's second half: no "material rise" threshold is introduced, because the surface that should carry the rise was never a snapshot.*

   **A matching marker's `tierShown` is a FLOOR on the durable register, not only a gate on re-firing (the F1/F6 seam, closed here).** 5a is recomputed from live counts, and a chip answer moves a trip from unresolved to productive — which lowers `R` and could drop a band-tier cluster to a lower tier. Left alone, that is the F1 inversion arriving one layer out: the owner answers honestly and the emergency disappears. So once a cluster has been shown at a tier, no durable surface for that cluster renders below it. What recomputes is the **wording** — 5a's "the verdict is recomputed; the evidence never is" — not the register.

   **A suppressed band never removes a finding from a band that is rendering (F21).** Markers are per cluster and each leaf keeps its own, so a strain finding already marked would have dropped out of a composed band and left the decompensating cat with a band naming only its breathing. **If any current finding is firing a band, every current finding composes into it** (rule 15). The marker suppresses an *arrival*, never a *member*.

4. **The floor governs the TIER, never the EXISTENCE, of the response (CE-4).** A single marked-unproductive strain in a male cat is a presence-class red flag: n=1 gets a lower-register capture-time line; ≥ **N_U** gets the emergency band. N_U is build-gate calibration; the no-silence-at-n=1 rule is not. **Rule 0 now generalises this twice over — from floors to guards, and from existence to tier for presence-class findings. Read them together; where they overlap, rule 0 is the stronger statement.**

5. **The unanswered chip gets an ASK — and the ask is a RIDER, not a scarce event (CE-2, CE-3; REWRITTEN per F2).** With the chip unresolved, the response asks the question ("Did any pee come out?") with the conditional body — capturing the datum at the moment it matters without weakening the absence-of-log guard (unanswered still never counts as "No"; "Couldn't tell" is still treated as unresolved, never as an answer).

   **v1.4 bound the ask to the band's once-per-cluster marker, which is where F2 came from:** the covered-box cat's six trips produced one low-register question at trip one and **nothing for the next five hours**, because trips 2…N−1 were suppressed at equal tier. A count-carrying ask is the whole value of the T axis and could never render. **So the ask is not governed by rule 3 at all.** It is folded into the body of whatever renders, on every qualifying evaluation, for as long as `R ≥ 1`. It has no tier of its own and it never renders alone — `R ≥ 1` implies `T ≥ 1`, which always renders at least the observation line (5a).

   **5a. THREE AXES, COMPOSED — the ordered table is deleted (HR-12; REWRITTEN per v1.3 findings; REWRITTEN AGAIN per F1, F3, F6, F25).**

   **What v1.3 got wrong.** The window was **anchored at the most recent marked-productive trip** — a "yes" *reset* it — on the reasoning that a "yes" is real evidence the cat is passing urine. That reasoning is a clinical error and a rule-0 violation in one: a "yes" means *I saw some pee*, and **a few drops is the presentation of a partial obstruction, not the exclusion of one.** The partially-obstructed cat could therefore never accumulate to the band floor, the band was structurally unreachable, and the rule **inverted on owner attentiveness**. **The reset is deleted.** The window is a plain lookback, `[now − X, now]`. *(This closure held under the fourth pass — U genuinely accumulates now.)*

   **What v1.4 then got wrong: the shape of the table itself.** v1.4 replaced the reset with six rows evaluated in order, first match wins. Three findings attacked that structure and they are one defect: **a selection table cannot express a patient with findings on more than one axis.** A cat at `U=0, T=8` sat on the frequency row naming its count; the owner then witnessed one unproductive trip and it moved to the presence row — a **different register that drops the 8-trip fact** — so new evidence read as a downgrade (F6). The table also had no floor on unresolved trips, so the covered-box household capped one tier below the band (F3), and it rendered **nothing at all** for a male cat with four trips honestly marked "a little came out", calling that observed-normal four lines under its own sentence saying it is not (F1). And the tier order the whole thing depended on was never written down anywhere, while rule 3's `tierShown` quantified over it.

   **The closure deletes the table.** There is no ordering, no first match, and no arbitration. There are **three axes**; each contributes at most one finding — the strongest that qualifies on that axis — and the findings **compose by rule 15**, which is the composition rule this contract already had.

   **One evaluation, over one window `[now − X, now]`, reading four counts:** **U** = trips marked unproductive · **P** = trips marked productive · **R** = trips unresolved (unanswered *or* "couldn't tell") · **T** = U + P + R, the total trip count. Three floors, all build-gate calibration, none of which gates existence: **N_U** (unproductive → band) · **N_R** (unresolved → band, per D20) · **N_T** (total trips → frequency finding).

   | Axis | Finding (the strongest that qualifies) | Tier |
   |---|---|---|
   | **U** — productivity-negative | `U ≥ N_U` → **band**, emergency wording | `band` |
   | | `1 ≤ U < N_U` → **presence line**: this cat has strained without producing urine | `presence` |
   | **R** — unresolved | `R ≥ N_R` → **band**, *conditional* wording ("if nothing is coming out, this is an emergency") | `band` |
   | | `1 ≤ R < N_R` → the **ask** (rule 5), folded into whatever renders | — (rider, no tier) |
   | **T** — how much straining there is | `T ≥ N_T` → **frequency finding**, names the trip count | `frequency` |
   | | `1 ≤ T < N_T` → **observation line**, names the trip count, lowest register | `observation` |

   **`T = 0` is the only silence.** It entails `U = R = P = 0`: nothing was observed to escalate on. The only silence cell that can hold a sick animal is the one where the owner logged nothing, which no rule can reach.

   **The tier ladder, written down because rule 3 quantifies over it and v1.4 never stated it (F6):**

   > `band` **>** `presence` **>** `frequency` **>** `observation`

   The one non-obvious rung is `presence > frequency`, and it is clinical: **one witnessed unproductive strain in a male cat outranks twelve productive ones.** The first is the presentation of an obstruction; the second is the presentation of cystitis, which is a vet visit and not an emergency. *The ordering is a register ranking, not a floor — it is a Dr. Chen build-gate confirmation item, and nothing else in this contract depends on it being calibrated, only on it being total.*

   **The response's tier is the maximum over its composed findings.** Rule 3 compares *that* against `tierShown`.

   **Two things this structure gets for free, which the ordered table had to assert:**
   - **Monotonicity is structural.** Adding a qualifying row increments exactly one of U/P/R and always increments T, so U, R and T are non-decreasing under row addition, and each axis's finding is a monotone step function of its count. **The composed tier is therefore non-decreasing in each of U, R and T** — no convention, no arbitration, and no way for new evidence to read as a downgrade. Property-tested.
   - **No fact is dropped.** F6's cat renders the presence line *and* the frequency finding, at the presence tier, in one composed body: *"You've marked one trip where nothing came out, out of 8 trips tonight."*

   **Four properties the build binds to, each testable:**
   - **The verdict is recomputed; the evidence never is.** A late "yes" may soften what the durable flag *claims* — "an unproductive straining cluster" becomes "N straining trips, one later marked as passing urine" — but it may **never delete the episode**, and it may never lower the register below the cluster's `tierShown` (rule 3). v1.3 let one late "yes" clear the vet-facing flag outright, which inverted §10.3's own B-494 binding.
   - **The capture-time band is never un-said.** It was true when it rendered, and retracting a safety statement an owner may already have acted on is worse than leaving it.
   - **A marked "yes" never reassures.** It renders no sentence of its own; the absence of a band is not a statement that the cat is fine (`clinical-guardrails`: no path to a reassuring verdict by construction).
   - **P never subtracts.** A productive trip is counted; it raises the tier through T and can never lower one. Under D21 it also carries its own observation line, so the attentive owner's honest "a little came out" is the one answer that used to buy silence and now buys a sentence.

## §10 Vet report handshake

Verified 2026-08-23: `generate-report` fetches **all** event types and renders only `REPORT_SYMPTOM_TYPES` (the correlation set + lethargy); `other` rows are already invisible in the deployed v13 and on `main`. Consequences:

1. **Capture ships without report work** — a new leaf is fetched-and-ignored, no crash, no wrong data, and no regression vs. `other` today.
2. **The real report work per wave:** add shipped symptom leaves to `REPORT_SYMPTOM_TYPES`; render each family's section — Dr. Chen's ask is a **dated problem line** beside the GI workup, which needs a Tier-2 edit to `nyx-vet-report-requirements.md` (flagged, not written); RRR renders as a measured series beside weight when it exists.

   **2a. The unit rule — "episodes" already means three different numbers, and the problem line would have printed the mismatch (HR-7).** Three shipped surfaces count three different things and all of them say *episodes*: the Day Summary counts **raw rows**; the report's §3.5 frequency table counts **minute-deduped incidents**; ⑦ and Trend count **3h-chained episodes**. v1.2's own proposed line — "Coughing — 14 **episodes** over 6 weeks" — would have carried an *incident* count while the same morning's Signal card said "14 **episodes** across 5 of the last 8 weeks" after the chain. Cough maximises the divergence, because a coughing fit is logged repeatedly and the chain collapses exactly that.

   **Ruled (convened 2026-08-26): precise units, not one reconciled number.** The report's §3.5 table keeps its existing count and **labels it "entries"**; the §10.2 problem line prints the **episode** count and labels it **"episodes"**; **the two never share a bare word.** So the line reads *"Coughing — 38 entries · 14 episodes over 6 weeks, ongoing."* Dr. Chen's basis: that is **more** informative to a vet, not less — the ratio of entries to episodes is itself clinical signal about how the sign presents. The rejected alternative was renumbering §3.5 to the episode collapse, which would have silently changed the shipped counts for **every existing type** to fix a wording problem on a new one. Corollary for the checklist: `SYMPTOM_NOUN` is a membership list too, and the Day Summary's lead sentence has nowhere to state a unit at all — so it states a count of *logs*, never of episodes.
3. **Safety leaves bind to the B-494 rule:** a report that advertises its safety-flag zone may not stay silent on a straining cluster or a sustained >30/min RRR series — those leaves ship with their report flags **or the report does not learn the leaf yet**; an empty band that could have spoken is a negative claim.

   **3a. The strain trip count is ONE predicate, and the report neither de-dups nor collapses it (§9a rule 2, D17; REWRITTEN per F11).** `generate-report` collapses near-simultaneous observation rows within `DEDUP_WINDOW_MS` (`report.ts:200`) — apply that to strain and the report prints a different trip number than the band the owner already saw, which is the B-067 two-numbers class on a safety count. The report reads the same predicate: **a qualifying row is a trip** (§9a rule 2 defines *qualifying*).

   **v1.4 permitted a display collapse with an escalate-on-presence merge, and that put TWO numbers inside the report (F11)** — three confirm passes inside 60s surviving as one displayed entry carrying `dupCount: 3`, printed beside a trip count of three, on D17's own rescued patient. §10.2a already had to separate "entries" from "episodes"; strain would have added a third unit with no rule saying which one prints. **So the collapse is deleted rather than governed: strain rows are never collapsed in the report.** Row count and trip count are then the same number by construction, and the merge rule has nothing left to govern. Accepted cost, stated: a 15-trip obstructed cat prints 15 rows. On a safety leaf the rows *are* the evidence, and a clinician working up a suspected obstruction wants the timestamps, not a tidier table.

   **3b. The count is of MARKS, and the report says so (§9a rule 2, F24).** D17 accepts that two phones over-count by one, on the argument that over-count is the safe error — which is true of the band and **not** of the report, where a count read as a physiological rate misleads in either direction, and where the per-trip cost compounds into a systematic ~2× inflation for two logging caregivers rather than a one-off +1. The resolution is the one this project already uses for exactly this class (the diet-trial C5 logging-density ruling): **disclose beside the number, never absorb it into the number.** Every strain count in the report keeps its **"you've marked"** attribution, and the section states the multi-caregiver limitation in its own words. The predicate does not change; what changes is that no surface presents a mark count as a measurement.

   **3c. An unattributed trip stays unattributed all the way into the report (§9a rule 14, D23, F20).** A row whose owner recorded that they **could not identify the animal** carries a `pet_id` that is a *placement, not a claim*. D18 constrained the ask and the band and left this datum at capture, so the report would have printed a confident six-trip claim about whichever cat was tapped first — the CUL-574 wrong-pet class surviving into the one surface a clinician acts on. So the D14 column travels with the row, and the report renders those trips as **household-attributed** ("one of two cats"), never as a per-pet count. Where a report is scoped to one pet, an unattributed trip is disclosed rather than silently included or silently dropped.
4. All report-side work rides the held `generate-report` redeploy chain (CUL-19) — sequenced behind B-494, never its own deploy.
5. **A LANE-MEMBERSHIP CHANGE IS REPORT WORK (HR-3) — the rule this section most needs, and the one §9 alone would let a build session miss.** `generate-report` **imports the detection module** and filters its own detection input on the *same* `CORRELATION_SYMPTOM_TYPES` list, runs `detectSignals`, and renders the chronicity result as a safety flag plus a headline pointer. `REPORT_SYMPTOM_TYPES` is a **separate** list. So a wave that adds a leaf to a lane and nothing else produces this: whenever the held redeploy (CUL-19) clears, **the report prints an ongoing-pattern safety flag about a sign its own §3.5 frequency table never counts.** That defeats §10.1's "no wrong data" and it is squarely the B-494 class — a zone that advertises itself and then goes incoherent. Every wave therefore decides, in the same PR as the lane change: **add the leaf to `REPORT_SYMPTOM_TYPES`** (the report already fetches all types) **or exclude it from the report's `detectSignals` input.** Never neither. And mechanically sooner than the deploy: the deploy manifest fingerprints `generate-report`'s whole import closure **including the detection module**, so the wave's engine PR must **re-acknowledge a held function's fingerprint** — budget for it, it is not a surprise.

## §11 The `other`-row swap script (D3)

One-time, dogfood-era mechanism; the T&S basis is that the script's reviewer **is** the rows' owner. Shape:

0. **Step 0 — the device build floor (HR-5a).** A server-side `UPDATE` reaches **every** device on the account at its next hydration, but the §8-audit build that renders the new type sanely reaches devices at **release cadence**. Run the swap and an un-updated device on the same account silently de-symptomizes the re-keyed rows (§8a). So: **every device on the account carries the audited build (W1-PR-2) — verified, not assumed** — before the script runs. Same class as the client-first gate on W1-PR-3.
1. A read query lists candidate rows (id, occurred_at, note text) for one target leaf; the **PM reviews the id list** — per-row explicit, never pattern-match auto-applied.
2. The update is `UPDATE events SET event_type = '<leaf>' WHERE id IN (<reviewed ids>)` — **notes and `occurred_at` untouched** (the note text is the provenance that justified the swap); soft-delete state untouched. **The `updated_at` trigger bump is REQUIRED and is the propagation mechanism — do not suppress it (HR-5b, a correction: v1.2's "no `updated_at` semantics beyond the write itself" read as licence to do exactly that).** Hydration pulls are **watermark-incremental on `updated_at`**, and the `events` update trigger bumps it on every UPDATE. That bump *is* how the re-key reaches the account's other devices. Suppress it and every device except the one that ran the script holds `other` rows **forever**, with no error anywhere. Sync quiescence (step 3) remains the push-side guard; it is a different concern from the pull-side watermark.
3. **Sync quiescence first:** run only when the owner's devices have empty sync queues — a server-side edit to a row with a pending device write loses to last-write-wins. Verify, run, then re-hydrate the app.
4. Post-swap verification: per-type counts before/after (the swap moves rows between types; total count unchanged), and the expected engine effect stated in advance. **But the predicted ⑦ firing is a CLOCK, not a fact (HR-5c).** ⑦'s window start, its 14-day recency floor and its 42-day firm boundary are all evaluated **at run time** — so if W1 lands months from now and the cat has recovered, verification "fails" on a *recovering* cat, and a build session debugs a working engine. (Nor is the note count the episode count: 14 notes ≠ 14 episodes after the collapse — §10.2a.) **The rule: compute all four floors on swap day, against the rows as they then are, and record the outcome in advance — including "does not fire, for recency," which is an acceptable and predicted result, not a defect.**
5. The script + its reviewed id list are committed with the wave PR (the affected-row-count discipline from the B-414 Class-A rule, applied to a Class-B act that consent cleared).
