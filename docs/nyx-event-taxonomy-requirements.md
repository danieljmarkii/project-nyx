## §3 The spine: families as presentation, leaves as data (D2)

- **Leaf = one `event_type` enum value.** The single analysis key everywhere (engine, report, History, sync) stays leaf-grain. New leaves are **additive `ALTER TYPE event_type ADD VALUE`** migrations (own PR; effectively irreversible in Postgres — add per shipping wave, never pre-seed unshipped leaves). Local SQLite `event_type` is TEXT — no local migration.
- **Family = a constants-layer grouping**: picker group, category tint, ordering. The B-745 grouped grid already renders exactly this (Symptoms / Food & care / Body & more); new families are new groups, not a redesign. **Where it lives today vs. where this spec assumes it lives (hard review HR-4):** the family groups are currently declared **in the picker component, not in `constants/eventTypes.ts`**, and the per-type tint is a separate map in that same component. So a wave that adds a family is editing the component, and the first wave that adds leaf metadata (`hasPhoto`, `species`, family group, `confidenceModel` — **none of which exist on the entry record today**) is the one that moves the grouping into constants. That move is a real PR item in W1-PR-2, not a given; do not write a checklist step that assumes the fields are already there.
- **Attributes = per-leaf structured fields**, always optional, never a decision at moment of event (Principle 1). Stored per-leaf where a child table or column already fits the pattern (weight → `weight_checks` precedent); specified per leaf in §5, built only with the leaf's wave.
- **Species conditionality** reads `pets.species`: a leaf declares `species: 'cat' | 'dog' | 'all'`; the picker renders only matching leaves for the active pet. A species value outside dog/cat renders the `all` set. Labels may also vary by species (litter-box wording vs. house-accident wording) — copy-level, not key-level.
- **Naming:** keys follow the existing plain-word convention (`cough`, not `tussis`); proposed keys in §5 lock at each wave's PR. Labels are owner language (nyx-voice; never jargon — "Straining in the litter box," not "stranguria").

## §4 The selection framework (D1's quantitative half)

Five value axes, 0–3 each, every score citing the evidence pack; one cost axis. The sum ranks; the PM triages the ranking into waves. The framework **informs** — it does not decide (D1's cough/sneeze ruling predates it, and sneeze ships on family coherence despite a mid-table score; the framework's job is to make that kind of call visible, not to forbid it).

- **A · Own-record demand** — what the owner already logs in `other` notes (the F3 method). 3 = double-digit note count · 2 = several · 1 = adjacent evidence · 0 = none. *Honest limit: n=1 today (G6 generalized — never calibrate to one cat); becomes a real demand instrument when a cohort exists (§16 Q5).*
- **B · Population weight** — sweep A §A4 (claims rankings + VetCompass prevalence + presenting-sign studies), species-split. 3 = top-5 sign family both species or #1-class one species · 2 = top-10 presence · 1 = present in lists · 0 = negligible.
- **C · Instrument coverage** — sweep C §A: validated-instrument items the leaf derives (derive-don't-ask). 3 = derives items across multiple instruments or completes an index · 2 = one instrument item or a consensus sign-list item · 1 = proxy only · 0 = none.
- **D · Detection leverage** — lanes the leaf feeds at plausible logging density, or a deterministic safety rule it enables. 3 = immediate lane fit or safety rule · 2 = lane fit with new per-type config · 1 = data-only for now · 0 = no lane plausible.
- **E · Whitespace / strategic** — sweep B §B (nobody structures it) + the Zoetis derm/resp trip-wire. 3 = unstructured everywhere AND strategic pressure · 2 = unstructured everywhere · 1 = some competitors have it unstructured · 0 = commodity.
- **Cost** — S = tile + existing confirm · M = tile + attributes or photo-first fit · L = new primitive (measurement flow, escalation register, child table).

## §9 Engine handshake (membership, not floors)

Expansion never auto-updates the algorithm: each leaf makes an explicit per-lane membership decision; floors live in B-755's contract and are **owned product calibrations** where no guideline number exists (the cough finding — §4 of the deep-dive, verification pass).

**The mechanism this table assumes does not exist yet — building it is W1-PR-3b's first job (hard review HR-1, the pass's highest-consequence structural finding).** Today `CORRELATION_SYMPTOM_TYPES` is **one list** that scopes the DB fetch *and* is iterated by **all five per-type lanes** (① food-correlation · ③/④ · ⑦ chronicity · ⑤ · ⑥). There is no per-lane membership anywhere. So "add cough to ⑦" is not a list edit: adding `cough` to that list auto-enrols it in **①**, which can then emit a card naming a protein as associated with coughing — **the exact claim the cough row below forbids by name** — and in **⑤**, whose shipped template would offer to time a respiratory sign against a recent feeding (the regurgitation-vs-cough confusion the never-hairball rule exists to prevent). ## §9a The W2 escalation contract (v1.4 — BINDING on the W2 build)

This contract has now survived three adversarial passes and been rewritten twice. The design review (`docs/event-taxonomy-design-review-2026-08.md`, report 2 — CE numbers) found 13 rule-level holes; the hard review (`docs/event-taxonomy-hard-review-2026-08.md` — HR numbers) broke two of the closures and moved two more on fact-check evidence; a third pass on *those* rewrites returned FAIL with 15 defects, six of the silence-on-the-sick class, and the 2026-08-27 product-team review verified 11 more. **v1.4 rules and rewrites against all of them (D16–D19), and a fourth pass on THAT result returned FAIL — 22 findings, recorded below as §9b.** The v1.3-era warning block is gone: each v1.4 closure names the finding it answers in place, so a build session meets the rule and its reason rather than a stale warning, and the review documents are the archive. §9b now carries the *new* open findings, and **W2 is not buildable until they are ruled.** Read it before building any rule below.

**The maintenance rule this section keeps re-learning, stated once so v1.5 does not re-learn it a fourth time: a closure written to satisfy a finding acquires load-bearing mechanism that nobody then attacks.** That is how rules 2 and 13 failed the first time, and how HR-11/12/15/19's closures failed the second. So v1.4 prefers **deleting mechanism to adding it**: three of the six silence defects close by *removing* the thing that caused them — the window reset, the time-keyed de-dup, and the sleep gate on existence — and the two rules that are genuinely new (14, 15) cover scope this contract never had, rather than repairing scope it did.

**Reconciliation with the "engines are server-side" hard constraint (HR-27) — state it once so nobody has to re-derive it.** D4 puts a deterministic cluster rule on the client, over local rows. CLAUDE.md's hard constraint says the correlation engine and PDF generation are server-side, never on-device. These do not conflict, and the boundary is not "detection": it is **statistical inference vs. deterministic rules over the pet's own rows.** The *statistical* engine — correlation, floors, multi-sample inference, anything that could be wrong in a way an owner cannot check — stays server-side, unchanged. A **deterministic, threshold-free, escalate-only rule evaluated over local rows** is a distinct and already-sanctioned class: `lib/dietTrial` is the shipped precedent, and it is on-device for the same reason this is — the answer must exist at the moment of capture, offline, before any function could be called. A future constraints-enforcing session should read D4 as inside the rule, not as an exception to it.

---

**0. No evidence-quality guard may gate the EXISTENCE of a response — only its wording and its tier (D16, ruled 2026-08-30).** This is rule 4 extended from floors to guards, and it is the organising rule of the whole contract: apply it first, and to every rule below.

Three of v1.3's closures each built an **evidence-quality escape hatch** — a marked "yes", a confirmable sleeping count, an answered chip — and then let that hatch decide whether the app spoke at all. In every case the animal that cannot pass through the hatch is the sick one: the partially-obstructed cat passing drops, the CHF dog who pants at rest, the covered-box household. One defect in three costumes, and a fourth (the RRR count-duration minimum) was found wearing the same one.

**The test, applied to every guard in this contract and to every guard a future wave adds:** *is there a patient for whom this guard can never be satisfied **because of** the illness the rule exists to catch?* If yes, the guard may set the **wording** and the **tier**. It may not decide whether anything renders.

**What silence is still permitted to mean.** Silence is permitted only where the record holds **nothing of the escalating class** — not where it holds something the app could not evaluate. "Couldn't tell" is not "no". "Couldn't measure" is not "no finding". "Not sure which cat" is not "no cat". Below-floor *observed-normal* is silence and carries no claim (the lane is escalate-only); below-floor *unevaluable* is never silence.

1. **The band's host never self-closes under it — and none of the host's silent exits reaches it (CE-21; extended per HR-14).** When a safety band renders in the B-745 sheet, the completion beat's dwell timer does not run and the sheet does not auto-dismiss — it stays until explicitly dismissed, and the dismissal is a visible control. Pinned with a test (the B-156 G1 rule: a safety prompt survives the time it takes to act). **The dwell timer was not the only way out.** The host already gives every non-confirm stage two dismissals that fall straight through to close: a **scrim tap** and the **Android back button**. Either one silently dismisses an emergency band with a touch above the sheet — and because rule 3 suppresses per cluster, *it never comes back*. So on the band stage the **scrim is inert and the back handler is a no-op**: the band takes the confirm stage's guarded treatment, not the done stage's pass-through, and the only exit is the labelled control. Test all three exits, not just the timer.

   **The fourth exit — backgrounding mid-band — is survivable only because the Signal safety card is not marker-gated, and that dependency is now binding rather than incidental.** The band's per-cluster marker (rule 3) governs **the band**; it never gates the Signal card. A later "consistency" fix that made the card respect the band's marker would silently close this exit and delete the backstop for every owner who backgrounds the app while reading. Pin it with a test: *a cluster whose band marker is set still renders the Signal safety card.*

2. **The strain lane counts TRIPS — one predicate, no time-keyed collapse anywhere in it (CE-1, CE-7; REWRITTEN per HR-11; RE-RULED per D17).** The unit is a *trip*. The 3h episode collapse would silence the cluster rule permanently, and two surfaces printing two different strain numbers is the B-067 class — so the count is defined once, here, and every surface reads it.

   **What v1.2 got wrong, and what v1.3's fix still got wrong.** v1.2 re-parameterised the generic episode module, which **chains** by design: an obstructed cat straining every ~8 minutes for two hours collapses to **one trip** at any gap ≥ 8 minutes, while a *less* sick cat straining every 25 minutes counts 5 and fires. The predicate was anti-correlated with severity. v1.3 split de-dup from counting — correctly — but then handed the de-dup job to a **fixed time window**, which is the same defect attenuated: the shipped window anchors to the cluster's **first** member (`report.ts:200`, `:959`), so the count saturates at `span / W` and under-counts across the whole obstructed band. And a time window cannot do the job it was given, because **the thing it is trying to separate is not separated by time**: a double-tap and a caregiver's second phone are minutes apart in both directions.

   **The rule: duplicate prevention belongs to the capture surface; the trip predicate does not collapse rows at all.**
   - **Trip count = the number of qualifying `urine_strain` rows in the window.** No chaining, no de-dup window, no episode collapse. A row is a trip.
   - **A double-submit of one capture flow is prevented at the source, not repaired afterwards.** The app already has a **shared primitive** for this: `useSubmitGuard` (B-336), a latch whose contract is written at its call site — *true keeps the guard latched (the sheet is transitioning to the beat, so no later tap may write again); false releases it (the write failed, the owner is still on the confirm, so the pill must work again)*. The latch itself is a **ref**, not React state — `inFlight.current` in `hooks/useSubmitGuard.ts:30–42` — which matters, because two taps in one tick both pass a `disabled={submitting}` prop that is waiting on a state flush. The shipped confirm routes its save through the hook (`components/log/SimpleEventConfirm.tsx:105`, `:641`, handler at `:332`), and `app/log.tsx` uses the same one. **W2's strain capture reuses the hook — it does not re-implement the guard**, and it does not settle for the `disabled` prop, which is the visual half of a latch and not the latch. A fixture pins it. *This is why the window was deletable: it was guarding something the capture surface already prevents, while demonstrably costing the batch-recall case below.*
   - **Accepted cost, stated rather than discovered (D17).** Two phones logging the same trip over-count by one, and one prolonged trip logged twice over-counts by one. **On this lane over-count is the safe error** and under-count is the failure HR-11 was filed for. `logged_by` would not fix it even if it existed: the household shares one credential (the B-054/B-086 evidence), so both phones are the same auth user, and `038_logged_via.sql` records a capture *surface*, not a person or a device.
   - **The case the deleted window was costing (Dr. Chen, verified).** The owner who comes home, realises the cat has been in and out of the box all evening, and logs three trips in three quick confirm passes writes three rows at `occurred_at ≈ now` — D10 makes strain witnessed-by-construction and the CUL-576 clock seed makes "now" the default, so this is the *modal* retrospective log, not an edge case. Under any time-keyed de-dup those three collapse to one and the canonical patient degrades to the n=1 line. Under this rule they are three trips.
   - **The report reads the same predicate (§10).** `generate-report`'s generic observation de-dup does **not** apply to the strain trip count, or the two surfaces print two numbers. Where the report collapses strain rows for *display*, the collapse is **escalate-on-presence** — the shape the report already uses for severity and the blood/foreign phenotype (`report.ts:935–943`): **any member marked unproductive ⇒ the surviving row is unproductive**, never the reverse.

   State in the code, at the predicate, *why* the generic episode module is not the mechanism here — the chaining property is the reason, and it is not obvious from the module's name. Every surface that speaks a strain count states its unit; §9's table records why strain is the one symptom whose safety count is not the episode count.

3. **Fire once per cluster — identity by MEMBER-SET INTERSECTION, and the marker carries the tier it fired at (CE-8; restated per HR-15; REWRITTEN per findings 6, 9, 10, 14).** The emergency band fires once per satisfied cluster, never per qualifying log; a re-fire happens on a defined quiet period or a genuine re-escalation, and then as a different — never softer — sentence. This is what keeps the register scarce (S1) and removes the incentive CE-19 found (hiding the tile as the only off-switch).

   **v1.2's "suppression fails toward firing across restarts" re-created the very problem CE-8 closed** — composed with rule 6's foreground re-evaluation, the chronic-FIC cat re-fired the band on every app launch. **v1.3's replacement — identity = the first qualifying row's id — then failed in both directions at once:** it *cannot express re-escalation* (escalating does not change which row came first, so a second, larger cluster inside the same window is permanently suppressed), and it *churns* on soft-delete, an `occurred_at` edit, and partial hydration — each of which mints a new id and re-fires.

   - **A marker records the cluster's member ids and the tier it fired at:** `{ memberEventIds, tierShown }`.
   - **A cluster matches a marker iff their member id sets intersect.** Intersection is stable under adding a row, deleting a row, editing an `occurred_at`, and hydrating half the rows — which is every churn trigger, closed by one property rather than four guards. Member ids are **raw row ids**, so two devices that would pick different survivors still intersect (this also answers what "the first qualifying event" meant: nothing now depends on it).
   - **The band fires iff no matching marker exists, or the cluster's tier is HIGHER than every matching marker's `tierShown`.** A tier rise *is* the genuine re-escalation rule 3 always promised — so the promise and the mechanism now describe the same rule — and it makes 5a's monotonicity structural rather than asserted.
   - **The marker is persisted per pet, per device by design** — one household member seeing the band does not silence it for the other. Stated so it is not "fixed" later. **The claim that every device computes the same identity is deleted: it was false under ordinary incremental sync, and it was never needed** — each device firing at most once per cluster is the whole requirement.
   - **Markers age out** once the cluster can no longer be live: `now − last member's occurred_at > X + quietPeriod`. And **quietPeriod ≥ X**, so a cluster can never outlive its own window.
   - Because it is persisted account-adjacent state, **the marker joins `wipeLocalSession`** (the CLAUDE.md local-wipe rule; T&S).
   - **"Fails toward firing" survives only for a cluster that cannot be identified at all** — never for a restart, and never for a cluster whose marker is simply present.
   - **The durable Signal card's REGISTER decays; its presence does not (finding 14).** The cooldown governs the band, and v1.3 left the card ungoverned — so the chronic-FIC cat pinned a permanent emergency card to Home, which is CE-8's alarm wallpaper arriving on the other surface. The card renders in the **emergency** register while the cluster is live (within X) and stands down to the **ongoing-pattern** register afterwards. It never stands down to *nothing*: the record still holds the evidence, and a zone that advertised itself may not go silent (§10.3, B-494).

4. **The floor governs the TIER, never the EXISTENCE, of the response (CE-4).** A single marked-unproductive strain in a male cat is a presence-class red flag: n=1 gets a lower-register capture-time line; ≥ **N_U** gets the emergency band. N_U is build-gate calibration; the no-silence-at-n=1 rule is not. **Rule 0 generalises this from floors to guards — read them together.**

5. **The unanswered chip gets an ASK, not silence and not an assertion (CE-2, CE-3).** With the chip unresolved, the band asks the question ("Did any pee come out?") with the conditional body — capturing the datum at the moment it matters without weakening the absence-of-log guard (unanswered still never counts as "No"; "Couldn't tell" is still treated as unresolved, never as an answer). Once per cluster, per rule 3.

   ---

   **5a. Rules 3/4/5 are ONE predicate with four tiers over ONE window (HR-12; REWRITTEN per findings 1, 4, 5, 7, 9, 13 and the missing productive tier).** As written in v1.2 they never composed at all; v1.3's arbitration composed them but introduced the pass's single highest-severity defect.

   **What v1.3 got wrong.** The window was **anchored at the most recent marked-productive trip** — a "yes" *reset* it — on the reasoning that a "yes" is real evidence the cat is passing urine. That reasoning is a clinical error and a rule-0 violation in one: a "yes" means *I saw some pee*, and **a few drops is the presentation of a partial obstruction, not the exclusion of one.** The partially-obstructed cat could therefore never accumulate to the band floor, the band was structurally unreachable, and the rule **inverted on owner attentiveness** — the owner who reliably notices the drops is the one it goes quiet on. The reset also minted a new cluster id, which defeated the monotonicity property in the same breath. **The reset is deleted.** The window is a plain lookback, `[now − X, now]` — which also dissolves the question of what it should have anchored to when no productive trip had ever been marked, rather than answering it.

   **The other two gaps in the same table.** There was **no floor on unresolved trips**, so ten unanswered straining trips in six hours got the same low-register ask as one — and the modal feline setup (covered box, clumping litter) makes U *structurally* unreachable, because the owner can never honestly answer. And the table rendered **Silence** for the pure-pollakiuria cat (U=0, R=0, P=12 — the modal FIC presentation), while rule 9 asserts a prompt-24–48h tier for productive straining exists. Both close with one axis: **T**.

   **The arbitration.** One evaluation, over one window `[now − X, now]`, reading four counts: **U** = trips marked unproductive · **P** = trips marked productive · **R** = trips unresolved (unanswered *or* "couldn't tell") · **T** = U + P + R, the total trip count. Two floors: **N_U** (unproductive → emergency) and **N_T** (total trips → frequency finding). Both are build-gate calibration; neither gates existence.

   **The rows are evaluated in order and the first match wins** — they are deliberately not written as mutually exclusive predicates, because the ordering *is* the severity ranking, and a table whose cells must each restate every prior exclusion is one a build session gets wrong.

   | State (within the window) | Response |
   |---|---|
   | T = 0 | **Silence.** Nothing was observed to escalate on. The only silence cell that can hold a sick animal is the one where the owner logged nothing — which no rule can reach. |
   | U ≥ N_U | **Band** (emergency). The ask is folded into the band's body when R ≥ 1, never rendered separately. |
   | 1 ≤ U < N_U | **Presence line** (lower register, rule 4) — plus the ask when R ≥ 1. Rule 4's "n=1" line generalised: *any* count of marked-unproductive trips below the band floor speaks, and it is one row rather than two because a floor may only move the tier. |
   | U = 0, T ≥ N_T | **Frequency finding** (prompt-24–48h, rule 9's promised tier). Names the trip count and never asserts unproductive — this is the pure-pollakiuria cat, and it is also where the covered-box household lands on trip count alone. Carries the ask when R ≥ 1. |
   | U = 0, T < N_T, R ≥ 1 | **Ask.** Unresolved is not "no", and it is not silence either. |
   | U = 0, T < N_T, R = 0 | **Nothing rendered** — the record holds only marked-productive trips below the frequency floor. Silence here is observed-normal, not unevaluable, and carries no claim (rule 0). |

   Note what the table no longer does: it never asks "Did any pee come out?" over two explicit Nos (finding 13 — the ask is conditioned on `R ≥ 1` in every row that carries it), and **P never subtracts from U**. A productive trip is counted, and it can raise the tier through T; it can never lower one.

   Four properties the build binds to, each testable:
   - **Monotone within a cluster.** The register never moves down a tier for the same cluster. Enforced by rule 3's `tierShown`, not by convention — and no longer defeasible, because nothing mints a new cluster id mid-window.
   - **The verdict is recomputed; the evidence never is (findings 5, 7).** A late "yes" may soften what the durable flag *claims* — "an unproductive straining cluster" becomes "N straining trips, one later marked as passing urine" — but it may **never delete the episode**. v1.3 let one late "yes" clear the vet-facing flag outright, which inverted §10.3's own B-494 binding and produced the sequence where the band says "call now", the owner acts, and the report is then silent about the visit's cause. **The recompute may retract a verdict; it may not retract a record.**
   - **The capture-time band is never un-said.** It was true when it rendered, and retracting a safety statement an owner may already have acted on is worse than leaving it.
   - **A marked "yes" never reassures.** It renders no sentence of its own; the absence of a band is not a statement that the cat is fine (`clinical-guardrails`: no path to a reassuring verdict by construction).

9. **The dog branch FIRES — the "explicitly decline for dogs" arm is deleted (CE-14; REWRITTEN per HR-18, fact-check-mandated).** `urine_strain` is species `all`. v1.2 offered W2 two arms: fire with dog copy, or decline for dogs and record the consequence. **The second arm is clinically unsupported and is removed.** Unproductive urinary straining in a dog is the *same* emergency pattern as in a cat — obstructive urolithiasis, male-skewed, fatal within roughly 48–72 hours via hyperkalemia (ACVS; practice guidance) — not the UTI-grade complaint the decline arm implicitly assumed. 11. **The RRR ask terminates — SLEEP-ANCHORED, DERIVED, and it speaks below the threshold (CE-6, CE-15…CE-18; REWRITTEN per HR-17/19/20 and per findings 2, 3).** The over-reference state is state-dependent: the first high count asks for one recount; the second states the sustained finding and routes to the vet without asking again. Every state carries the presence-side pointer ("if breathing looks hard or open-mouthed, call regardless of the number"); 30 is framed as the general reference, never an action threshold — **"if your vet has given you a number for {pet}, use theirs" is kept verbatim**; every rendered state is pinned by a Pattern-8 reassurance scan.

    **(a) Sleep-anchoring governs the SERIES, and a count that cannot be sleep-confirmed still gets a response (HR-17; REWRITTEN per finding 2).** All four primary studies support <30/min **while asleep**, in both species, and **6–14% of verified non-decompensating animals cross 30 while awake at rest** (Ohad 12/190; Porciello 7/51 dogs and 1/22 cats, with ranges reaching 44–45). So a >30 count the owner could not confirm as sleep **may never enter the sustained-finding state**, and the stored series stays sleeping-counts-only. That much v1.3 had right.

    **What it got wrong is what happens to the animal instead.** It routed the count to "count again while she's asleep" and stopped — which scores *"I could not get a sleeping count"* as *"no finding"*, when **the inability to obtain one is itself the clinical finding**: the tachypneic cat who cannot settle and the CHF dog panting at rest are precisely the animals that can never yield a sleeping count, and they are the target population. Rule 0, exactly.

    **The closure — a separate presence-class finding, never a widening of the series (Dr. Chen's binding execution constraint).** An over-reference count that cannot be sleep-confirmed, or an owner-marked "she won't settle", renders its **own** presence-class line in its own wording — *"she won't settle and her breathing is fast — that's worth a call"* — routed like any presence finding, with the recount still offered. It **never enters the stored series** and never contributes to "sustained". Widening the sustained state to admit awake counts would corrupt exactly the dataset §15 Q4 asks the vet to trust; two registers, one of which the vet reads, is the fix.

    **The count-duration minimum gates the NUMBER, never the RESPONSE (finding 2's sibling, found 2026-08-27 — the fourth hatch).** The row stores its actual count duration, and below a minimum the count does not become a stored rate. But v1.3 then *discarded* it with an offer to restart — so **20 breaths in 8 seconds (≈150/min, abandoned mid-count)** produced nothing at all, on an animal breathing hard enough that the owner could not finish counting. An abandoned count at an extreme implied rate renders the presence-class line above and offers the restart; the minimum decides only whether a number joins the series.

    **(b) The state machine is DERIVED on every evaluation, never stored — and it is MONOTONE (HR-20; extended per the 2026-08-27 review).** A stored "already asked" boolean lets two high counts **170 days apart, with 40 normal nights between them**, state a sustained finding — and renders differently after a reinstall or on the second caregiver's phone. Instead: **sustained = |{over-reference counts within `maxAge`, each separated by at least `minSeparation`}| ≥ 2; ask at exactly 1.** Restart, reinstall, and device 2 then agree by construction.

    Two things v1.3 left the derivation open to:
    - **It could downgrade with the calendar.** Two qualifying counts aging out of `maxAge` un-say a said finding — the app tells an owner their dog has a sustained finding and, days later with no new evidence, quietly stops. A finding that was true when stated is not retracted by the passage of time: rule 11 takes **5a's monotone property** — once the sustained state has been stated for a series, a later evaluation does not return it to the ask state. New evidence may escalate; the calendar alone may not de-escalate.
    - **`minSeparation` set-selection is a packing problem and needs a named algorithm**, or two devices with the same rows disagree on how many counts qualify. Use the **greedy earliest-first** shape already shipped for phase-stable distribution counting (`countDistributionWeeks`, B-188): walk the qualifying counts in ascending time, take one, skip everything within `minSeparation`, repeat. Deterministic, phase-stable, and already precedented.

    **(b-i) Night semantics, stated because nothing in v1.3 stated them (found 2026-08-27).** "Night", `minSeparation`, and the series' per-night aggregation were all undefined — and whether (c)'s rising run even *exists* depends on the aggregation rule. So: a count belongs to the **local calendar date** of its `occurred_at` (B-421's local-midnight boundary; never UTC). `minSeparation` is counted in **nights, not fixed hours**, so a DST transition cannot add or remove a qualifying count. Where a night holds several sleeping counts, the night's series value is the **maximum** — the safe direction on an escalate-only lane, and stated as a bias rather than left implicit (it is a Dr. Chen build-gate calibration item alongside the floors). Fixtures for this lane are timezone-honest per B-514 — local components or an explicit `timeZone`, never a UTC literal — and the set includes a DST-transition night.

    **(c) A rising series under 30 gets a rule, or the series surface does not ship (HR-19; REWRITTEN per finding 3).** **18 → 22 → 26 → 28 over four nights** is the case: both of rule 11's states key on an over-reference count, so nothing fires, and a chart with no words reads as *"nothing to say"* — **reassurance by layout**, on a record trending toward the threshold. §9 promises "trend beats single readings" and §14's frame 10 exists for exactly this series.

    **v1.3 modelled the rule on the shipped gap-shortening lane and borrowed its shape wholesale, which is where it broke.** `detectGapShortening` fires on a **strictly** monotone run of 4 (`detection.ts:5502`), and its own documentation says why that number: it holds the *by-chance* false-positive rate at 1/4! ≈ 4.2% on i.i.d. continuous gaps. Two things do not carry across. First, **an RRR count is quantized** — a tap count over a partial minute lands on ±2/min steps — so ties are ordinary and a genuinely rising 9-night decompensation series routinely contains no strictly-rising run of 4. Second, and load-bearing: **L4 is an `insight`-class lane, the engine's lowest-ranked quiet row, where a false negative costs nothing. This is a safety lane, where a false negative is the entire failure mode.** A false-negative rate may not be inherited from a lane whose false negatives are free.

    **The closure — adopt the precedent's structure, re-derive its parameters.** The precedent is three gates, not one, and the review's correction is right that v1.3 mis-described it: it carries a **magnitude test** (`latestGap ≤ ratio × median`, `detection.ts:5081`) and a **staleness/reversal guard** beside the run. Adopted faithfully:
    - **Run:** **non-decreasing** across the run, not strictly increasing — quantization makes a flat step ordinary, and a flat step is not a reversal.
    - **Magnitude:** a required **total rise** across the run (`last − first ≥ M` breaths/min). This is what carries the false-positive rate here — the inverse of L4's allocation, where the run length carries it and the ratio is kept loose. Said plainly so nobody "restores" strictness later: on quantized data the run length cannot hold the FPR, so the magnitude test must.
    - **Recency / reversal:** adopted as-is in spirit — a run that has stopped rising, or whose most recent nights have fallen back, is not live and does not fire.
    - **`runLength` and `M` are re-derived for this lane against ±2/min quantization, and the derivation is a build-gate calibration with a measured false-negative arm** — the fixture set carries a real 9-night decompensation series with realistic quantization and asserts it **fires**, beside the noise gate that asserts the normal-band series does not. The B-182 lesson, applied before the floor locks rather than after.

    Escalate-only and silent otherwise: silence carries no claim, because the rule can only ever escalate. **Binding: the RRR series surface never ships without this rule attached.** (Convened 2026-08-26: adopt the rule and **keep frame 10** — the alternative on the table was cutting the trend claim and the frame, and it was rejected because the shipped gap-shortening lane is the precedent that this is buildable, and a cut loses real clinical value.)

13. **The haptic claim is earned by the STAGE MACHINE, not by a suppression flag — and the awaited read has a stated timeout, fail direction, and cancel path (CE-22; REWRITTEN per HR-13; completed per finding 15 and the 2026-08-27 review).** "Silence on safety" still holds — a band path plays no haptic. v1.2's mechanism could not deliver it, in two independent ways:

    - **The guard is structurally blind to this.** The haptic at band time is the *completion beat's* `commitSymptom()` — a non-safety sibling component that the marker-scan guard never reads. Adding the band's own marker to the scan set asserts that *the band* doesn't import haptics, which it never would. The guard would go green over an unfixed defect (the CUL-613 lesson: run a new guard against the tree it was written for).
    - **The suppression predicate has no evaluation point.** The beat mounts **synchronously** inside the save handler, while the band decision is an **async post-save SQLite read**. At the moment the haptic fires, "will a band render?" is simply not answerable yet.

    **The rule: make the band decision an input to the stage transition.** The save handler **awaits detection and selects a `band` stage**, so on a band path the beat — and therefore its haptic — **is never mounted at all**. Silence becomes structural rather than suppressed, which is also what makes it testable.

    **What v1.3 left unspecified, and both branches of it fail toward the thing rule 13 exists to prevent:**
    - **Timeout.** The wait is bounded by a named constant (build-gate calibration; sized so the sheet never appears hung). **On timeout or error the fail direction is: no haptic, and the completion surface still renders its sentence.** The beat is suppressed *as a haptic*, not as a confirmation — CUL-614 requires a completion surface to name the record, and an unresolved detection is not a reason to leave a write unconfirmed. The safety decision then routes to the Signal card when it resolves.
    - **The silent cancel in front of it.** `handleLogged` early-returns on `!visibleRef.current` (`components/log/EventTypeSheet.tsx:231`) — written for a good reason (a resolved write must not flash a stale beat onto a reopened sheet), but it means **a scrim tap during the awaited detection read cancels the band with no fallback at all.** The write has landed and the animal may be obstructed. **The detection decision resolves into state that survives the dismiss**, and where the sheet is gone it routes to the Signal card — rule 6's post-save entry point degrading to rule 6's no-sheet presentation, not to nothing. Pinned with a test: *dismissing the sheet during the awaited read still produces the safety card.*

    **Pin the haptic rule with a component test on the sheet ("a band-qualifying save plays no haptic"), not with the import guard.** Keep the band component's marker addition, but say what it actually guards: it stops a *future* edit from adding a haptic call inside the band component — a different and smaller hole than the one the rule is about.

    "What to tell the vet" (CE-23) uses the band's own trip predicate and attribution phrasing — one count, everywhere.

14. **Multi-cat attribution: the ask tier may pool the household; the band never does (D18, ruled 2026-08-30 — NEW).** Sam's household is the target user for this leaf and the contract had no rule for it.     - **The band never pools.** An emergency band names one animal and tells the owner to act on it; pooled evidence cannot name one, and a band that names the wrong cat is worse than the ask. ## §10 Vet report handshake

Verified 2026-08-23: `generate-report` fetches **all** event types and renders only `REPORT_SYMPTOM_TYPES` (the correlation set + lethargy); `other` rows are already invisible in the deployed v13 and on `main`. Consequences:

1. **Capture ships without report work** — a new leaf is fetched-and-ignored, no crash, no wrong data, and no regression vs. `other` today.
2. **The real report work per wave:** add shipped symptom leaves to `REPORT_SYMPTOM_TYPES`; render each family's section — Dr. Chen's ask is a **dated problem line** beside the GI workup, which needs a Tier-2 edit to `nyx-vet-report-requirements.md` (flagged, not written); RRR renders as a measured series beside weight when it exists.

   **2a. The unit rule — "episodes" already means three different numbers, and the problem line would have printed the mismatch (HR-7).** Three shipped surfaces count three different things and all of them say *episodes*: the Day Summary counts **raw rows**; the report's §3.5 frequency table counts **minute-deduped incidents**; ⑦ and Trend count **3h-chained episodes**. v1.2's own proposed line — "Coughing — 14 **episodes** over 6 weeks" — would have carried an *incident* count while the same morning's Signal card said "14 **episodes** across 5 of the last 8 weeks" after the chain. Cough maximises the divergence, because a coughing fit is logged repeatedly and the chain collapses exactly that.

   **Ruled (convened 2026-08-26): precise units, not one reconciled number.** The report's §3.5 table keeps its existing count and **labels it "entries"**; the §10.2 problem line prints the **episode** count and labels it **"episodes"**; **the two never share a bare word.** So the line reads *"Coughing — 38 entries · 14 episodes over 6 weeks, ongoing."* Dr. Chen's basis: that is **more** informative to a vet, not less — the ratio of entries to episodes is itself clinical signal about how the sign presents. The rejected alternative was renumbering §3.5 to the episode collapse, which would have silently changed the shipped counts for **every existing type** to fix a wording problem on a new one. Corollary for the checklist: `SYMPTOM_NOUN` is a membership list too, and the Day Summary's lead sentence has nowhere to state a unit at all — so it states a count of *logs*, never of episodes.
3. **Safety leaves bind to the B-494 rule:** a report that advertises its safety-flag zone may not stay silent on a straining cluster or a sustained >30/min RRR series — those leaves ship with their report flags **or the report does not learn the leaf yet**; an empty band that could have spoken is a negative claim.

   **3a. The strain trip count is ONE predicate, and the report's generic de-dup does not apply to it (§9a rule 2, D17).** `generate-report` collapses near-simultaneous observation rows within `DEDUP_WINDOW_MS` (`report.ts:200`) — apply that to strain and the report prints a different trip number than the band the owner already saw, which is the B-067 two-numbers class on a safety count. The report reads the same predicate: **a qualifying row is a trip.** Where it collapses strain rows for *display*, the collapse is **escalate-on-presence** — the shape the report already uses for severity and the blood/foreign phenotype (`report.ts:935–943`): any member marked unproductive ⇒ the surviving row is unproductive, never the reverse. Without that rule a "yes" survives over a marked "no" inside a collapsed cluster, which is the same inversion §9a rule 0 forbids, arriving through the report.
4. All report-side work rides the held `generate-report` redeploy chain (CUL-19) — sequenced behind B-494, never its own deploy.
5. **A LANE-MEMBERSHIP CHANGE IS REPORT WORK (HR-3) — the rule this section most needs, and the one §9 alone would let a build session miss.** `generate-report` **imports the detection module** and filters its own detection input on the *same* `CORRELATION_SYMPTOM_TYPES` list, runs `detectSignals`, and renders the chronicity result as a safety flag plus a headline pointer. `REPORT_SYMPTOM_TYPES` is a **separate** list. So a wave that adds a leaf to a lane and nothing else produces this: whenever the held redeploy (CUL-19) clears, **the report prints an ongoing-pattern safety flag about a sign its own §3.5 frequency table never counts.** That defeats §10.1's "no wrong data" and it is squarely the B-494 class — a zone that advertises itself and then goes incoherent. Every wave therefore decides, in the same PR as the lane change: **add the leaf to `REPORT_SYMPTOM_TYPES`** (the report already fetches all types) **or exclude it from the report's `detectSignals` input.** Never neither. And mechanically sooner than the deploy: the deploy manifest fingerprints `generate-report`'s whole import closure **including the detection module**, so the wave's engine PR must **re-acknowledge a held function's fingerprint** — budget for it, it is not a surprise.

## §11 The `other`-row swap script (D3)

One-time, dogfood-era mechanism; the T&S basis is that the script's reviewer **is** the rows' owner. Shape:

0. **Step 0 — the device build floor (HR-5a).** A server-side `UPDATE` reaches **every** device on the account at its next hydration, but the §8-audit build that renders the new type sanely reaches devices at **release cadence**. Run the swap and an un-updated device on the same account silently de-symptomizes the re-keyed rows (§8a). So: **every device on the account carries the audited build (W1-PR-2) — verified, not assumed** — before the script runs. Same class as the client-first gate on W1-PR-3.
1. A read query lists candidate rows (id, occurred_at, note text) for one target leaf; the **PM reviews the id list** — per-row explicit, never pattern-match auto-applied.
2. The update is `UPDATE events SET event_type = '<leaf>' WHERE id IN (<reviewed ids>)` — **notes and `occurred_at` untouched** (the note text is the provenance that justified the swap); soft-delete state untouched. **The `updated_at` trigger bump is REQUIRED and is the propagation mechanism — do not suppress it (HR-5b, a correction: v1.2's "no `updated_at` semantics beyond the write itself" read as licence to do exactly that).** Hydration pulls are **watermark-incremental on `updated_at`**, and the `events` update trigger bumps it on every UPDATE. That bump *is* how the re-key reaches the account's other devices. Suppress it and every device except the one that ran the script holds `other` rows **forever**, with no error anywhere. Sync quiescence (step 3) remains the push-side guard; it is a different concern from the pull-side watermark.
3. **Sync quiescence first:** run only when the owner's devices have empty sync queues — a server-side edit to a row with a pending device write loses to last-write-wins. Verify, run, then re-hydrate the app.
4. Post-swap verification: per-type counts before/after (the swap moves rows between types; total count unchanged), and the expected engine effect stated in advance. **But the predicted ⑦ firing is a CLOCK, not a fact (HR-5c).** ⑦'s window start, its 14-day recency floor and its 42-day firm boundary are all evaluated **at run time** — so if W1 lands months from now and the cat has recovered, verification "fails" on a *recovering* cat, and a build session debugs a working engine. (Nor is the note count the episode count: 14 notes ≠ 14 episodes after the collapse — §10.2a.) **The rule: compute all four floors on swap day, against the rows as they then are, and record the outcome in advance — including "does not fire, for recency," which is an acceptable and predicted result, not a defect.**
5. The script + its reviewed id list are committed with the wave PR (the affected-row-count discipline from the B-414 Class-A rule, applied to a Class-B act that consent cleared).

## §12 The flag — `event_types_v2` (B-712 two-gate shape)

Gate 1: `app_config.event_types_v2` allowlist, seeded dark (migration, own PR). Gate 2: `BETA_REGISTRY` shelf card, local opt-in, default off, sign-out wipe. `serverCost: false` — capture has no server component (engine/report membership ships separately and is account-agnostic). One deliberate interaction: writes are flag-gated but **reads are not** — a household's flag-off device renders a beta device's cough rows via §8's degradation contract, by design.

**FL-1, re-scoped: byte-identical for the CAPTURE SURFACES, and `EVENT_TYPES` is NEVER flag-gated (HR-4 — v1.2's blanket wording was not merely imprecise, it pointed the implementer straight at the bug this section forbids).** "Flag-off byte-identical" full stop is unachievable here, and both ways of trying to achieve it are wrong:

- The flag-off flat grid derives its tiles **from `EVENT_TYPES` itself** (and a test pins it at exactly eight tiles). Add `cough` unconditionally and the **flag-off grid grows** — the feature leaks past its own flag and the pin fails.
- So gate the `EVENT_TYPES` *entry* instead — and now a swapped row on the owner's **flag-off iPad renders "Event" over 14 cough rows** while her beta phone says "Cough." That is precisely the outcome the reads-are-not-gated paragraph above forbids.

The rule, stated so neither branch is available:
- **`EVENT_TYPES` is never flag-gated.** It is the shared record vocabulary — labels, glyphs, tint — and it must be complete on every device that can *read* a row, flag or no flag.
- **FL-1 binds the capture surfaces only:** with the flag off, the **grid's tile set** and the **confirm** are byte-identical to today. Read surfaces are deliberately **not** byte-identical, and §8's degradation audit is the reason that is safe rather than sloppy.
- **The flag gates the grid's tile list**, not the vocabulary — a `v2Only` field on the entry, or a separately-derived gated grid list. **This is a real design item in W1-PR-2, not a one-line conditional**, and the snapshot pin moves with it: it pins the **picker surface**, not the constant.

**PR 0 also carries the B-747 fix — which is a LIVE bug today, not one this track creates (HR-10).** The beta-shelf row is gated on `widget_enabled` alone while the registry **already** holds `log_picker_v2`, so an account allowlisted for the picker beta but not the widget **cannot reach the shelf right now**. The OR-fix must also cover the active-beta count, not just the row's visibility, and `event_types_v2` would be the **third** live shelf row rather than the fourth.
