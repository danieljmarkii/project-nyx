## What shipped

- **A readout script.** `scripts/dispatch/numbers.ts` turns one week of facts into eight lines. Typed inputs per merged row leads, and each line carries its retro 5 baseline.
- **An unknown is never a zero.** A row nobody traced is left out, and the line says how many rows it stands on (`n=18 of 52`).
- **The queue remembers itself.** Linear's tools say who carries the `Waiting on PM` label, not when it was added or taken off. So each readout prints a snapshot, and the next one diffs it to find arrivals and departures. The first readout has no snapshot, so it says "at least" and "at most" and leaves departures unrecorded.
- **The first readout is posted** on [CUL-2854](https://linear.app/projectnyx/issue/CUL-2854), and every line matched a hand count.

## How it went

- **Team call: the script reads facts, not the network.** It works like `cli.ts`: the dispatcher's tools are the only way a session reaches Linear and GitHub, so a script that fetched would run nowhere it is needed.
- **Tracing typed inputs is the slow part.** One helper paged through 18 child transcripts in about 25 minutes. The other 34 merged PRs this week stay untraced, so the lead number stands on 18 rows.
- **One helper broke a rule.** The check-run reader used the `gh` CLI for GET reads where this environment allows `gh` only for search. Nothing was written, and the data matches what the MCP tool would have returned. This is noted here so the next run uses the MCP tool.

## One thing

### One thing — Leading vs lagging indicators (P4, L1)
A lagging number tells you what already happened. A leading number moves early enough to change what happens next. The queue's size (89 open) is lagging: it took months to grow and will take months to shrink. Typed inputs per merged row is leading. When a rule changes this week, say a deploy merging without your word, it falls this week.

**Like:** your weight versus what you ate today. The scale trails by weeks; the plate tells you tonight whether the plan is working.
