# Sync hygiene — one bound `markSynced` helper (B-125) + an atomic `insertMeal` (B-126)

**Date:** 2026-07-26

Two small, long-deferred `Later` rows from 2026-06-19, shipped together because they are the same kind of work on the same write path: make the local-first sync layer correct by construction rather than correct by coincidence.

## B-125 — the post-push `synced = 1` sweep

Every sync writer ended its flush by building the queue-drain UPDATE with a string-interpolated id list:

```ts
const ids = unsyncedMeals.map((m) => `'${m.id}'`).join(',');
await db.execAsync(`UPDATE meals SET synced = 1 WHERE id IN (${ids})`);
```

There was never a live injection surface here — the ids are device-minted UUIDs and cannot carry a quote. But that is a property of today's id generator, not of the query. The same shape copied onto a writer keyed by anything else would be a real hole, and the shape *was* being copied: the row was written against **six** writers and there were **seven** by the time it came up, because `weight_checks` (B-186) landed in the interim and inherited the interpolated form from its sibling. That drift is the row's own argument.

`markSynced(db, table, ids)` now lives in `lib/sync.ts` and all seven writers call it — `meals`, `weight_checks`, `events`, `vet_visits`, `feeding_arrangements`, `medications`, `medication_administrations`. It binds every id as a `?` param and chunks at 400, comfortably under the 999-variable ceiling an older SQLite build compiles with. Today every writer caps its queue read at 100 so the loop runs exactly once; the chunking is there so a future writer that raises its `LIMIT` cannot quietly hit the ceiling.

Two deliberate calls worth recording:

- **`table` is a `SyncedTable` union, not a `string`.** A table name is an SQL identifier and cannot be bound to a placeholder, so it stays interpolated. Typing it as a closed union is what keeps that one interpolation provably a compile-time literal rather than something a caller could ever route data into.
- **`diet_trials` / `diet_trial_foods` are excluded.** `pushDietTrialRows` already binds its ids, and its UPDATE also clears `sync_error`; folding it in would mean widening the helper to serve one caller's extra SET clause.

The writers moved from `db.execAsync` to `db.runAsync` as a consequence — `execAsync` takes no params, which is why the interpolation existed in the first place.

## B-126 — `insertMeal` atomicity

`insertMedicationDose` and `insertWeightCheck` both wrap their event + child INSERTs in `withTransactionAsync`, each with a comment noting that the meals path has the same latent gap. `insertMeal` now closes it.

A half-write — event row lands, meal INSERT throws — would sync an orphaned `event_type='meal'` row to Supabase with no food, no quantity and no intake rating: a meal the record asserts happened but can say nothing about. For a diet trial that is worse than no row at all, since it inflates the feeding count while contributing nothing to coverage.

The `food_items_cache.last_used_at` touch stays **outside** the transaction on purpose. It is a local-only recency stamp for the picker's ordering, with no server column and no bearing on the health record; rolling back a correctly-written meal because a cosmetic touch failed would trade a real loss for a cosmetic one, and a missed stamp self-heals the next time that food is logged.

Code review caught that this reasoning stopped one line short, and it was right. Excluding the touch from the transaction protects the *rows*, but everything below that line is the meal's follow-through — the sync push and the Signal regen. Left unguarded, a failed stamp would throw past both for a meal that IS durably committed, and surface to the caller's `catch` as a failed log the owner would reasonably re-enter. The touch is now wrapped in a log-and-continue `try/catch`, so the cosmetic failure costs exactly the cosmetic thing.

## Tests

- `lib/sync.test.ts` — `markSynced` binds rather than interpolates (asserted with a quote-carrying id that *would* break the old form), chunks 950 ids into 400/400/150 with every id covered exactly once, no-ops on an empty list rather than emitting `WHERE id IN ()`, and — run against a real `node:sqlite` using the SQL + params captured from the production call — flips only the named rows.
- `lib/meals.test.ts` — which statements sit inside the transaction (both INSERTs in, the cache touch out); that a failed child INSERT propagates to the caller without firing the sync push or the Signal regen for a meal that no longer exists; and the mirror case, that a failed recency touch still lets the committed meal push and regen.
