# B-417 PR 1 — migration 040, the diet-trial schema gate

**Date:** 2026-07-25

Shipped via **#450**. Schema only, no UI — the house isolation rule.

## What shipped

Migration `040_diet_trial_lifecycle.sql`, applied live to production (`20260725180333_diet_trial_lifecycle`). Three sections, exactly as spec'd in `docs/nyx-diet-trial-requirements.md` §3.1/§3.2/§3.3:

- **§3.1** — eight additive columns on `diet_trials` (`food_label`, `indication`, `phase`, `outcome`, `outcome_notes`, `stopped_reason`, `ended_at`, `transition_started_at`) plus three ENUMs.
- **§3.2** — the new `diet_trial_foods` table: the allowed set. `pet_id` as a direct column (house hard constraint, not a join through the parent), dated membership via `allowed_from`/`allowed_until`, `updated_at` + trigger and `deleted_at` so the PR 2 mirror is possible at all, `food_label NOT NULL`, both indexes, and the RLS policy whose `WITH CHECK` names the food-ownership predicate.
- **§3.3** — dropped the non-UNIQUE `idx_diet_trials_active` and replaced it with `CREATE UNIQUE INDEX ... ON diet_trials(pet_id) WHERE status = 'active'`.

This was the gate the whole B-417 track queued behind. `diet_trials` shipped in migration 001, **seven** surfaces read it, and production held **zero rows** — so the vet report's own first clinical question ("is this diet trial working?") had never rendered with real data. Every schema choice here was free today at zero rows and a migration forever after, which is why the spec called it the last cheap moment.

## Three deliberate omissions, documented in-file

Recorded in the migration header specifically so a future session doesn't "helpfully" add them back: **no `diet_class`** (C4 landed §7 two-element), **no `paused` on the trial-status enum** (P-2 — a vet-directed hold records as stopped-early plus a new trial), **no severity columns** (C5 — severity comes from logged events, and §7 discloses logging density instead).

## Verification

**Rollback** verified by running the documented rollback and then re-applying the entire migration on top of it inside a discarded transaction. The re-apply succeeding *is* the proof the four ENUM drops are complete — a surviving type throws `42710`. Intermediate state checked directly: 0 leftover ENUMs, table gone, `diet_trials` back to 11 columns.

**`get_advisors` differential — clean.** Performance **47 → 47**, security **7 → 7**, zero new rows, nothing naming either new table. Two things that confirmed rather than assumed: the `(select auth.uid())` wrapping kept the new policy off the `auth_rls_initplan` list, and there is **no `unindexed_foreign_keys` row for `diet_trial_foods`** — so the UNIQUE constraint's own btree index really does cover the `diet_trial_id` FK, and two indexes are genuinely enough for three FKs. An earlier worry that brand-new never-scanned indexes would trip `unused_index` was unfounded; they aren't flagged.

**Sixteen behavioural assertions**, run as real `authenticated` roles with JWT claims, all inside rolled-back transactions: the named cross-account insert blocked `42501` with the same-account control still accepted; cross-pet insert blocked; account B sees nothing and its blind `UPDATE`/`DELETE` affect 0 rows; B deleting its whole account leaves A's allowed set unchanged; a second active trial rejected `23505` while completed/abandoned trials still stack; dated membership accepts a later `allowed_from` and rejects a same-day duplicate; parent delete cascades with no orphans.

The **counterfactual** is the one worth keeping: performing the same insert *as service role* (RLS bypassed) succeeds, and deleting that account then **does** silently shrink A's allowed set. So the hazard is real rather than theoretical, and the `WITH CHECK` predicate is the only thing standing between an account deletion and a silent mutation of a different owner's record.

## Two things that went wrong, and what they cost

**A green test that wasn't testing anything.** Assertion 13 (`set_updated_at` stamps `updated_at`) returned `0 stamped` where 1 was expected, and the verdict expression scored it `ok` anyway — the `CASE` matched only failure *strings* (`BREACHED`/`BLOCKED`/`dupe`) and never a count mismatch. I reported 16/16 passing before catching it. The trigger was never at fault: `set_updated_at()` is `NEW.updated_at = NOW()`, and `NOW()` is `transaction_timestamp()`, so the oracle `updated_at > created_at` is false by construction inside a single transaction. Re-run with a real oracle (force the value stale with the trigger disabled, re-enable, UPDATE) it passes in five parts — and surfaced a bonus fact for PR 2: **a client-supplied stale `updated_at` is discarded by the trigger**, so a device cannot pin a stale LWW watermark.

The lesson is the generalisable one: *a pass/fail expression that enumerates failure strings will score every unanticipated failure as a pass.* The verdict should have compared against the expectation, not scanned for known-bad substrings.

**File ↔ production drift in the persisted comments.** The `COMMENT ON` bodies are the only part of a migration that survives into the database, and they had drifted between the file and what was applied. Read back out of `pg_description` and reconciled — 9 in the file, 9 live, 0 mismatches. Then, rather than trusting the edit, fingerprinted both sides: Supabase records the exact SQL it executed in `supabase_migrations.schema_migrations`, and the committed file now normalises to **the identical md5** (`bc20a1eed6e8cbf57e282d17db23f077`, 4762 chars, modulo line comments and whitespace). A rebuild from the file reproduces production exactly.

## The `rls-privacy-reviewer` gate FAILED, and was right to

The named attack held — the `WITH CHECK` genuinely closes cross-account `food_item_id`, on INSERT and on UPDATE, and the reviewer sharpened *why* my test proved it: the `42501`-rather-than-`23503` is the signature that the **policy** rejected the write, not the FK failing incidentally. Had it returned `23503` the test would have proven nothing.

But it found the door next to the one I'd guarded. **`diet_trial_id` was in neither `USING` nor `WITH CHECK`** — a bare, RLS-bypassing existence check. My 16-assertion matrix had a categorical hole: not one assertion touched `diet_trial_id`, none tested owner-initiated DELETE, and none tested the cross-pet intra-account case. I verified all of it against production before acting:

1. **Cross-pet within one account — confirmed accepted.** A row whose `pet_id` is one pet and whose `diet_trial_id` is *another of the same owner's* pets' trials passes both predicates and the FK, because nothing compared the trial's `pet_id` to the row's. §5.3 makes the allowed set the only permit path, so the effect is a permit for the wrong pet: a real off-diet exposure scores `permitted`, and PR 7 renders that to a clinician. It fails in the **reassuring** direction. This is `personas.md`'s multi-pet-bleed anti-pattern landing in the artifact it warns about.
2. **Cross-account trial reference — confirmed accepted, with confirmed harm.** I measured the consequence rather than reasoning about it: with A holding a row pointing at B's trial, **B deleting that trial — or deleting their whole account — silently removed the row from A's allowed set.** That is the *same* silent shrink the `food_item_id` predicate exists to prevent, arriving through the FK that predicate doesn't cover. The boundary was closed on one door and left open on its twin.
3. **UPDATE was unguarded too** — the path PR 2's last-write-wins mirror will use. My first attempt at this test appeared to pass with `23505`; that was a **test artifact** (a UNIQUE collision I'd created myself), not a defense. Isolated with a distinct food, the laundering UPDATE succeeded.

**Fix: migration 041**, importing the mechanism 040 cited but didn't use. `023_dose_paired_event.sql` solved this exact shape with a `BEFORE INSERT OR UPDATE` trigger, explicitly *because* a trigger "runs server-side on every write regardless of client." A third `WITH CHECK` predicate would have been the tempting one-liner and would have been wrong: a policy binds `authenticated` only, and `generate-report` / `ask` / `generate-signal` all hold the service role key. Checking the **pet** closes both findings at once — `pets.user_id` makes a pet unique to one owner and `NEW.pet_id` is already RLS-verified, so same-pet ⟹ same-owner.

Post-fix verification, all six green: cross-pet blocked `23514`, cross-account blocked, UPDATE laundering blocked, both controls (legitimate insert, benign UPDATE) still pass so it isn't over-blocking — and **the service-role write is blocked too**, which is the whole reason it's a trigger. Security advisors still 7 → 7; the new function doesn't appear, so the pinned `search_path` held.

**Two findings deliberately NOT fixed here**, because they're design calls rather than boundary bugs, and both are recorded in 041's header:
- `food_label NOT NULL` + `ON DELETE CASCADE` are in tension. 040 claims the label serves "snapshot readers that outlive the row" while conceding the row dies with the food — so a hard food delete loses the whole *entry*. Low reachability today (`lib/foodArchive.ts` made the owner path a reversible archive that never touches trials), but `food_items_delete` still grants a hard DELETE. Making the snapshot real means `RESTRICT`, or `SET NULL` + nullable `food_item_id` — **a PM call**.
- `FOR ALL` grants the owner a hard DELETE over rows 040 says must only ever be soft-removed. Confirmed: an owner DELETE succeeds. Splitting the policy would default-deny it but constrains PR 2's sync shape — **PR 2's call**, with its write paths in view.

The reviewer also verified something I hadn't: all three service-role Edge Functions build their data client from the **anon key plus the caller's JWT**, so RLS applies to every read and a body-supplied `petId` is authorised rather than trusted. `generate-report`'s admin client issues no data query — only storage downloads on already-RLS-enumerated paths. And it caught a standing constraint worth carrying: `indication` is a diagnosis-grade field on a table that flows to the widget; it is *not* in `fetchActiveTrials`' projection today, but `trialCache` is module-scope and never cleared on sign-out, so adding it later would put a diagnosis into a cross-account-reachable cache.

## Carried forward

- **PR 5 must re-base `lib/trialContaminant.ts`** (B-351 slice 4, #447) off the single `diet_trials.food_item_id` and onto `diet_trial_foods`. §4.1 rules that column display-only legacy. **PR 3's multi-select must not reach users before that lands**, or a legitimately-allowed second trial food gets flagged as a contaminant. Tracked as B-438.
- **PR 2 needs a terminal-error branch.** §3.3's UNIQUE index makes a `23505` permanent rather than retryable, and the existing `syncPending*` shape has no such branch — it would retry a doomed insert forever.
- **PR 3's complete-then-start must be ordered**, now that one-active-trial is a hard server constraint rather than a convention.
- **A same-day re-add after a soft delete hits the UNIQUE constraint.** That is the intended reading of dated membership (removal is an UPDATE, re-add is a new row with a later `allowed_from`), and it is documented in the migration, but PR 2/PR 3 should handle it deliberately rather than rediscover it as a bug.
