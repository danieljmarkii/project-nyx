# CUL-599 — the tab bar: glyphs + the pet as the Pet tab

**Date:** 2026-08-23

Shipped via #702. One PR, no schema, no deploy, no flag.

Lane B (chrome) of the **Aug. 2026 Design Polish** track. Spec:
`docs/nyx-app-polish-requirements.md` §1 (DP-1) + §8. Design authority: mock round 1 §01
(the glyph paths and option C) as converged in round 2 §01 (the ladder). Both decisions —
D1 (glyphs + labels; the Pet tab is the pet) and D2 (the fallback ladder) — were PM-ruled
on 2026-08-22, so this session was execution, not deliberation. No PM gate was hit.

## What was there before

Four grey words. The bar was hand-rolled rather than configured, and its own comment says
why: *"the default Expo Tabs icon container clips text when using text-as-icon, so we own
the bar entirely."* Text-as-icon was a workaround, the workaround forced ownership of the
bar, and ownership plus a colour swap was where it stopped. The most-seen chrome in the
app was the least-designed.

Worth being precise about what this PR does and does not overturn: owning the bar is
**inherited, not new**. The clipping constraint still holds; what changed is that the bar
is now a component with tests instead of eighty lines inside a router.

## The Pet tab

D1's second half is the interesting one. The fourth tab renders the *active pet* — their
photo (or the tinted initial chip) and their **name** as the label. The mock's argument
for it is the multi-pet one: Sam's standing question is "whose data am I looking at", and
a bar that always names the active pet answers it for free, in chrome, on every screen,
without a banner or a scope chip.

That makes the tab bar the second surface (with the Home header, CUL-600) that is bound
to `activePet` rather than to a route. Both re-render off the store; there is no shared
file between them, which is why the two issues are parallel-safe.

## The ladder, and the one call inside it

D2 closes the risk that D1 creates: a pet named *Schrodingers Cat* on a 320pt phone.
The ruling is a ladder, not a truncation —

    full name @11pt  →  full name @10pt  →  the literal word "Pet"

— because a chopped name reads worse than no name, and the avatar carries the identity in
every rung anyway. The full name always rides the accessibility label, so **VoiceOver
never says "Pet" when the pet is Schrodingers Cat**. That is the half that makes the
fallback acceptable: the name is never lost, only unrendered.

### Why it measures instead of asking the platform

The spec deliberately left the mechanism open: *"onTextLayout or a char-width budget —
implementation's choice, deterministic either way."* This took the budget, and the reason
is not that measuring is hard.

`onTextLayout` measures truthfully, but only **after a first paint**. So the tab would
render at 11pt and then visibly reflow — to 10pt, or to "Pet" — on every cold start and
every pet switch, to decide something that is *fixed* for a given (name, width) pair.
A flicker in the most-seen chrome in the app, to compute a constant. A synchronous
estimate has no first frame to get wrong, and being a pure function, the ruled behaviour
is pinned by tests rather than by a device someone happens to be holding.

The cost is honest: an estimate can be wrong. What matters is that its two error
directions are **not symmetric**.

- Over-estimate → a name drops a rung early. Mildly unfortunate. Still a whole word.
- Under-estimate → a name renders wider than its tab. That is *precisely the clipping the
  ladder exists to prevent* — the ladder would have caused the failure it was built to
  stop.

So the fit test demands 4% headroom, spending the residual error entirely on the harmless
side. The constant is calibrated against the mock's own stated figure — *"at the narrowest
supported width a tab fits ~12 characters"* — and that sentence is itself a test, so a
future retune of the character table has to survive the claim it was tuned against rather
than silently drifting away from it.

Character advances are a small class table (narrow / semi-narrow / default / upper /
wide), not one average, because an average makes `Willow` and `Lili` the same width and
those differ by more than a whole rung.

### It is width-aware, not a per-name verdict

Worth writing down because it is easy to read the AC as "Schrodingers Cat gets 'Pet'".
It does not — it gets "Pet" *on a 320pt phone*. On a 393pt one the same name renders whole
at the 10pt rung. The ladder is a function of the tab's width, resolved from
`useWindowDimensions`, so it also re-resolves on rotation and on a foldable.

## Two things this PR touched that the issue did not name

**`GlyphSvg` moved to `components/glyphs/`.** The spec asks for the three new glyphs "on
the shared `GlyphSvg` wrapper" — but it was not shared; it was private to
`components/event/eventGlyphs.tsx`. The wrapper is the single point of control for the
house line (24×24, no fill, 1.75 stroke, round caps and joins), and a second copy of it is
how two glyph families quietly stop matching six months later. The event family is
otherwise untouched: `EventGlyph`/`EventGlyphProps` are still exported from where they
were, now as aliases, so `EVENT_TYPES` and `EventIcon` never learn the wrapper moved.

**The bar grew.** 80 → 81pt (iOS), 60 → 65pt (Android). It holds a glyph and a tick now,
not just a word. The height is *derived from its parts in code* rather than stated as a
literal, because a stated total is a number that goes stale the first time a part moves.
The bottom padding is untouched — it is the home-indicator allowance, not content.

Left alone deliberately: `components/log/FAB.tsx` positions itself at a hardcoded
`bottom: 72`, which is a tab-bar-height assumption living outside the tab bar. It still
clears, so this PR did not widen into a second file to fix a latent coupling it did not
create. Flagged on the QA script (the Android pass is where it would show).

## The spec line that was nearly missed

Spec §1 says tab labels "stay fixed-size under Dynamic Type (platform tab-bar
convention)". Read as a nicety, that is a one-line style preference. It is not: the ladder
fits a name to a tab **at a known font size**, so a system-scaled label would overflow the
tab the ladder had just fitted it to — the ladder's guarantee is void without
`allowFontScaling={false}`. Caught on a self-review pass after the first green test run,
not by the tests, because nothing in the suite could have failed on its absence. It has
its own assertion now, on every label rather than one.

## Tests

53 new. The three AC names on their ruled rungs at 320pt, and — more usefully — the
invariants over 13 names × 9 widths: the label is always either the whole trimmed name or
the word "Pet" (never a truncation, by definition), it never exceeds its budget, it only
renders at a declared rung, and it is monotonic in width (a wider phone never renders a
worse rung, so the bar cannot change its mind on rotation).

The rendered-bar suite pins what the tests could not otherwise see: that the focus states
draw **without moving anything** (the avatar's ring is a transparent border when
unfocused, the tick is always laid out), that every rung shares one line height so a size
change cannot walk the tick up and down, and that a store-level pet switch re-titles the
tab.

One test-harness note worth carrying forward: **jest-expo's default window is 750pt
wide**, which is no supported phone and a frame on which the ladder never engages at all.
Six assertions passed vacuously before that was caught. The suite now mocks
`useWindowDimensions` and states its width per test, so a reader can see which frame each
ruling is about.

## What the reviews found

Both mandated reviews ran (`code-reviewer`, `pm-feature-review`). `adversarial-reviewer` and
`rls-privacy-reviewer` are N/A **with reason**, not by silence: no clinical or statistical
logic, no data boundary, no schema, no service-role path.

They converged on one defect from opposite directions, and it was real: **the ladder
under-charged everything that isn't ASCII Latin.** Full-width scripts were billed the Latin
lowercase default — roughly half their true advance — so a six-character Japanese name
passed the fit test at 11pt and was then tail-ellipsised by `numberOfLines={1}`. That is a
mid-word cut. The module built to prevent one was the thing causing it, for exactly the
names it had never modelled. Two siblings in the same class: an emoji measured as two
half-width surrogate halves, and accented capitals falling through an ASCII-only `A`–`Z`
range to the lowercase bucket.

The lesson is narrower than "handle Unicode". It is that **a table of assumptions needs to
say where it stops**. The docstring claimed a guarantee ("never a cut") that the code could
only deliver for the scripts it had classes for, and nothing in 25 tests could notice,
because every invariant checked the estimate against *itself* — `estimateLabelWidth(text)
<= budget` is true by construction whatever the table says. The fix added classes; the
better fix was adding the paragraph that states what the guarantee does not cover, so the
next person reads a boundary instead of inferring a promise.

Two more from the same pass, both mine:

- **Letter spacing was unmodelled.** The label renders at `trackingWide`, so 0.4pt × 12
  characters is 4.8pt — larger than the 4% headroom meant to absorb the *entire* estimate's
  error, in the one direction this module may not err.
- **The 6pt side padding the budget subtracts was never rendered.** `styles.tab` had no
  `paddingHorizontal`. So the arithmetic was being protected by a padding that did not
  exist — two errors pointing opposite ways. That is not a working system; it is one that
  has not failed yet, and it would have failed the day someone added the padding the spec
  describes.

Modelling tracking honestly cost a claim: the narrowest-width capacity moves from the
mock's eyeballed "~12 characters" to a measured ~10, and "Schrodingers Cat"'s rescue moves
from a 393pt phone to a 430pt one. **Both tests were rewritten to the measured truth rather
than the constants retuned to preserve them** — the drift is in the safe direction, and the
three AC names still land on their ruled rungs.

### The finding I caused in three files I never opened

`MealCompletionCard`, `MedicationCompletionCard` and `Snackbar` each carried
`const TAB_BAR_HEIGHT = Platform.OS === 'ios' ? 80 : 60`, commented *"Tab bar height from
`app/(tabs)/_layout.tsx`"*. This PR moved that computation out of `_layout.tsx` and changed
the number, so all three comments became false and all three constants stale in one commit.

The sting is that this session's own commit message had already articulated the principle —
*"a stated total is a number that goes stale the first time a part moves"* — and used it to
justify deriving `TAB_CONTENT_HEIGHT` from its parts. The same reasoning, one file further
out, was sitting unapplied. `TAB_HEIGHT` is now exported and imported by all four consumers.
Worth carrying forward as a habit: after changing a constant, grep for its *value*, not just
its name.

### Checked and not actioned

Two claims did not survive verification, which is why they were checked rather than obeyed:

- *"The active pet tab shows a ring AND a tick; §1 specifies ring + ink label."* The mock is
  the design authority and it renders both — `.t.on .dot{background:#00C2A8}` alongside
  `.t.on .avatarchip{box-shadow:0 0 0 2px #00C2A8}`, in every round-2 frame. The spec prose
  abbreviates. Whether both cues are *wanted* is a legitimate design question for the device
  pass; it is not a build defect.
- *"The FAB overlap grew 3pt."* The old bar was 80pt, not 78 — the overlap went 8 → 9. The
  FAB's column sitting over the Pet tab at 320pt is pre-existing geometry; that tab was
  always rightmost. What is new is that it now carries a face, which is a screenshot
  question rather than a regression.

### Filed, not folded

CUL-617 (PetAvatar has no loading/failed-photo state — pre-existing, made load-bearing here),
CUL-618 (no pet switcher reachable from the Pet tab — a PM call, since the destination is
unchanged and only the affordance's *appearance* moved), CUL-619 (Foods-tab scope honesty),

The one judgement call on that boundary: `PetAvatar`'s `charAt(0)` surrogate-pair split was
**fixed here** rather than filed, because it is one line, cannot regress a Latin name, and
is the same defect class as the ladder's astral gap — the tab rendering a replacement glyph
where the pet's identity belongs.

## The duplicate

A parallel session built CUL-599 at the same time: **#701** (branch `…-grfqhz`, created 00:10:16Z)
against this session's **#702** (`…-wiw7wk`, seconds later). Neither could see the other. Both
are drafts, both CI-green, both meet the AC. Nothing was merged or closed — which one ships is
recorded on the issue as a PM decision with a factual comparison.

Two things are worth keeping from it beyond the immediate call.

**Each PR caught something the other missed, and neither miss was random.** #701 noticed that
the bowl glyph's base line, drawn verbatim from the mock at y=20 against a bowl reaching y=21,
crosses the bowl's interior at 22pt and reads as a fill line rather than a base — a *drawing*
error invisible to anyone treating the mock's path as authoritative, which this session
explicitly did ("do not redraw them here — a change to the drawing is a mock round, not an
edit"). That rule is right for intent and wrong for a path that does not survive its render
size. #702 fixed three files holding a stale copy of the bar height, which #701 leaves 2pt
wrong — the failure mode of changing a constant without grepping for its *value*.

So the two misses are mirror images: one session trusted the artifact too literally, the other
trusted its own blast radius too narrowly.

**The near-identical solutions diverged on one real fork.** Both landed on a character-advance
budget over `onTextLayout`, both on wide-script classes, both on `allowFontScaling={false}` —
independently. Where they split is letter spacing: #702 *models* the label's `trackingWide` in
the estimate; #701 *removes* tracking from the pet label so there is nothing to model. Both are
sound, and #701's is arguably the better instinct — deleting the term beats measuring it. Worth
remembering the next time an estimate acquires a correction factor: check whether the thing
being corrected for needs to exist.

**Ported before merge:** #701's bowl correction, after verifying the geometry rather than
taking it on trust — the rim spans 16pt, so `a8 8` is a semicircle and the body descends a
full 8pt from y=13 to y=21, putting the mock's y=20 base line inside the bowl. The claim
holds, and the corrected paths ship here verbatim with attribution. The rule in
`navGlyphs.tsx` ("do not redraw — a change to the drawing is a mock round") now carries the
exception that earned it: the rule governs a glyph's *intent*, not a path that does not
survive its render size.

Process note: this is the collision the parallel-lane plan (spec §9) did not price. Lanes B and
C were declared parallel-safe on *file* disjointness, which held — the collision was two
sessions on the same issue, and the only cheap guard against it is claiming the issue in Linear
(`In Progress`) before the first line of code, not at wrap.
