# Engines v3 PR-12: History v2's read copy gains the three read stamps

**Date:** 2026-09-28

Shipped via #969 (CUL-1267, EN-F's phone half; advances CUL-1201 part 1). Client only: no server, migration or deploy change. With PR-11b (#971) already merged, this was CUL-1267's last PR.

## What shipped

- **The phone's copy of the per-incident read** (`event_ai_verdicts`, History v2 §5.3) mirrors migration 075's three **read** stamps: `photo_set_key`, `rule_version`, `engine_flags`. Never `model_id` / `prompt_hash` (PM D-1): they describe the model's raw output, which the phone never holds. `engine_flags` is stored as a JSON array, so NULL (pre-stamp) and `'[]'` (every key off) stay apart. DDL in `BASE_SCHEMA_SQL` and `COLUMN_UPGRADES`.
- **"Photo not read" when the photo on screen was never read** (075 §2b's assignment). `readCopies` hands each copy `photoSetStale`: the row is stamped and the photo the event shows (`EVENT_ATTACHMENT_ORDER`) is not in its `photo_set_key`. `readStateOf` demotes a calm read to `unread` and drops the verdict word. It never touches `worth_a_call` or `pending` (CUL-1201 part 2). Unflagged (PM D-2); reads written before 075 are not compared (PM D-3).
- **One re-pull per phone.** The watermark key is now `event_ai_verdicts:v2`. The upsert fills stamps into a pre-stamp row at the same instant, once.
- **The millisecond tie** (CUL-1201, 9/25 comment). On an equal `julianday` the upsert compares the seconds field as a number (`CAST(substr(…, 18) AS REAL)`). A text compare would have broken C-40: `…00.000Z` sorts after `…00+00:00`, and the existing suite pins that they are one instant.
- **Spec:** `docs/nyx-history-v2-requirements.md` v1.9 (§5.3, §5.4, §6), PM-approved.

## What broke and how it was fixed

The approved plan defined "stale" as the phone's attachment set differing from the stamped set. The `adversarial-reviewer` showed the two sets need not converge:
- an offline replace leaves the old row on the server, because `detachEventAttachment`'s remote delete is best-effort and never retried;
- a replace made on another phone leaves the old row on this one, because the attachment pull is insert-only.

Either way the set compare showed *Photo not read* permanently over a photo that was read. On two phones the mark moved back and forth each time one re-pushed its rows. The owner's question is only whether the photo in front of them was read, and the app shows one photo per event. So "stale" became membership of the shown photo in the stamped set (commit 2). §5.4's sentence was changed to match; that sentence is newer than the PM's approval, which was flagged to the PM before merge.

## Falsification attempts

- **Adversarial:** tried a stale copy holding `worth_a_call` and one holding an unknown verdict: the rose stands. Tried a replaced photo whose re-read failed: calm drops to grey. Tried `.000Z` vs `+00:00`: no-op. Tried a microsecond-newer version inside one millisecond: it replaces, and an older one is refused. Tried the stamp fill against a microsecond-older row: refused. The one break found was the non-converging sets above, now fixed.
- **Privacy (`rls-privacy-reviewer`): PASS.**
  - The sign-out wipe takes `sync_watermarks` whole, so both the old and the new watermark keys go.
  - The full re-pull stays scoped by 013's pet-ownership RLS.
  - Every page and every row write is behind `stale()`.
  - `engine_flags` shows only the owner's own flag state.
  - A client PATCH of a stamp gets 42501 from 075 §2b.
- **Mutation:** each of these turned tests red when applied:
  - deleting the demotion;
  - letting stale silence the rose;
  - deleting the stamp fill;
  - reverting the tie-break;
  - a text tie-break;
  - the old watermark key;
  - a reversed attachment order;
  - a set compare.

## Residuals (stated in code)

- A pre-075 calm read over a replaced photo stays calm (D-3).
- A build downgrade can leave older stamps beside a newer verdict. It errs toward grey only.
- A minute boundary inside one millisecond keeps the pre-PR-12 tie behaviour.
- **CUL-1393:** the incident record screen does not apply the stale check yet. It can still show the old calm words under a new photo while Home says *Photo not read*.
