# DR-3 (CUL-26) — The offer: in-context + value moments

**Date:** 2026-08-15

Built the Daily Recap's **in-context offer** (B-762 / spec §4, R-6). On an **in-app** arrival at `/day-summary` (never a notification-tap arrival) while `daily_summary` is off and OS permission isn't denied, a night-ground banner asks whether Culprit may send the 9pm recap. `Turn on` → **the primer** (the OS prompt is unreachable from the banner directly); `Not now` → a 30-day local quiet marker. Starting a **diet trial** or a **med course** each re-surfaces the offer once, ever (own markers). OS-denied accounts never see it. Shipped via **#660** (draft), on branch `claude/cul-26-offer-moments-eu8f7i` (cut from `main` after DR-0…DR-6 landed). Design lock: `docs/culprit-daily-recap-mockups.html` §3, second frame.

## The design spine

- **The consent-path invariant — banner → primer → prompt, never banner → prompt.** The banner's `Turn on` (`onTurnOn`) ONLY opens the primer; `ensurePermission(true)` is reached EXCLUSIVELY from the primer's own confirm (`onPrimerConfirm`). This is the named gate, pinned by `app/day-summary.offer.test.tsx` (tap the banner's Turn on → the primer's c2 headline appears AND `ensurePermission` was called only with `false`; only the primer's Turn on reaches `true`). The enable flow is copied from the settings screen so the two surfaces that open the shared primer behave identically (granted → persist; denied → never a toggle-on the OS won't honor).
- **One decision, one set of markers.** `shouldOfferDailyRecap` is pure: in-app + off + not-denied + not-quieted. The markers are a single AsyncStorage blob (`quietUntilMs`, `trialMomentUsed`, `medMomentUsed`). A value moment DELETES `quietUntilMs` (lifts the quiet) and sets its once-ever flag; the decision reads the marker as-is, so "re-surface" is expressed as the absence of a live quiet. `coerceOfferState` fails toward the empty default (never a stuck quiet).
- **The value moment lifts, it doesn't force.** Trial-start / med-course-start lift the quiet, but the off/not-denied gates still decide whether the banner shows — a lifted quiet over an already-on or OS-denied account offers nothing. Once ever per kind: a second trial never re-nags (a no-op if the flag is set). Fired in the WRITE PATH, not at the call site.
- **Arrival is classified two ways, `source` primary.** `source: 'notification'` marks every tap; `firedAt` (B-672's fire instant) is a belt-and-braces fallback. Either → notification arrival → no offer. Anything else → in-app. The classifier is strict (a real, positive `firedAt`) so a stray empty param never mis-silences the offer on an in-app visit.
- **Fail-closed, and no flash.** `eligible` starts false (banner hidden), flips true only after the async read confirms eligibility; an uncertain read stays false. A notification arrival skips the reads entirely.
- **In the ready state only.** The banner renders at the foot of the ready-with-content ScrollView — never over the centered zero-log/error designed states (the mock's "the ask happens where the value is visible"). A value moment on a zero-log day simply shows on the next content day; the lifted quiet isn't lost.

## Review fold (code-reviewer CLEANUP items, applied)

- **Eligibility now reads ON FOCUS, not just mount** (`useDailyRecapOffer` → `useFocusEffect`). A recap strip's push to the Pet tab leaves `/day-summary` mounted underneath, so a `daily_summary` toggled in Settings — or a value moment lifting the quiet — while away must re-read on return. This is the settings screen's own on-focus reconcile pattern. In folding it I made **eligibility the sole authority for `show`** (dropped the separate `dismissed` flag): a "Not now" / a grant sets `eligible=false` directly, so a re-focus can correctly re-surface a genuinely-eligible offer (a value moment fired mid-session) instead of a sticky dismiss suppressing it forever.
- **The `source:'notification'` tap param — the named gate — is now built in the PURE, tested layer** (`notificationRouteParams` in `lib/notificationRouting.ts`, used by `useNotificationScheduling`), with a unit test pinning that `source:'notification'` rides EVERY tap including the `firedAt`-absent branch. Previously the invariant lived inline in the untested hook; a future edit could have silently reopened "offer shows on a tap arrival" with nothing failing.
- **NIT left by design:** the two AsyncStorage marker writes are unlocked read-modify-write (a theoretical clobber if two fired in the same instant). Left as-is — it matches the established fire-and-forget bookkeeping pattern (`clearTrialHeadsUpLedger`, `notificationInteractions`) and the two call sites cannot realistically fire simultaneously.
