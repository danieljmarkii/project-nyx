## B-171 — the drug is named the way the owner names it

**PM ruling: option (b)** — brand when present, generic fallback. (The PM offered (c) `Zyrtec (cetirizine)` as a swap-in; see the cross-surface note below for where (c)'s content ended up surviving anyway.)

The card read *"Logged together · cetirizine · with Delectable"* for the tile Sam had picked as **Zyrtec**. A confirmation card's whole job is reassurance-by-recognition, so confirming her action in a word she doesn't use spends the card's one moment on the morning it matters least.

The rule now lives in exactly one function — `drugDisplayName()` in `lib/medications.ts` — and is resolved at the call site in `app/log.tsx`, so `MedicationPayload.drugName` stays a display-ready string exactly like its neighbour `pairedFoodName`. The card renders; it never re-derives a name.

### The cross-surface reorder — built, reviewed, and reverted

This is the part most worth recording, because it is a judgment call I made *on top of* the ruling, shipped in my own PR body as an invariant, and then had falsified.

`formatDrugLabel()` (B-161) already fed three read surfaces — History (`EventRow`), the Home Today strip (`TodayZone`), and the day sheet (`lib/dayEvents.ts`) — leading with the **generic**: `cetirizine · Zyrtec`. Applying (b) to the card alone leaves card and row disagreeing on the first word, which looked like exactly the drift B-171 complains about, relocated one surface over. B-171's row left it open ("**maybe** the History row") and the kickoff asked for the consistency check, so I reordered it brand-first and claimed in the PR that the leading token was now "un-driftable by construction", pinned by a property test.

**The `adversarial-reviewer` broke that claim, and it was right.** Three costs the copy framing never priced:

1. **It drifts at two call sites the rule doesn't reach.** `app/(tabs)/profile.tsx:526` is a *second* `showMedicationMoment` caller I never found — the B-154 regimen "log a dose" path, whose own comment calls it *"the wedge's most-wanted path"*. It passes `reg.drug_name`, prefilled from `medication_items.generic_name` (`AddMedicationModal.tsx:183`), so its card would read **"cetirizine"** while the row underneath read **"Zyrtec · cetirizine"**. Likewise the combo cross-link's `paired_dose_drug_name`, aliased from `pdmi.generic_name` (`lib/db.ts:559, 595`) — *"Given with a cetirizine dose"* beside a *"Zyrtec · cetirizine"* row.
2. **The real cost is a med-safety cue.** `getDoubleDoseFlag` keys strictly on `medication_item_id` (`lib/db.ts:1118`), so two library items carrying the **same active ingredient** — one captured brand-forward, one entered generic — are *undetectable* as a double dose. The shared **leading** generic was the only thing putting those two rows next to each other in a History scan, and every consumer truncates at `numberOfLines={1}`, so brand-first is precisely what drops the generic. The PM ruled (b) on *recognition* grounds; this cost was not on the table.
3. The extractor is explicitly instructed to copy a brand into `generic_name` when no generic is visible, so brand==generic collisions are common by design.

**Resolution: the reorder is reverted and filed as `B-522`**, where it belongs — needing Dr. Chen + `clinical-guardrails` sign-off on (2) and both call sites fixed in the same PR. This PR ships exactly what the PM ruled: `drugDisplayName` on the completion card. A test now asserts `formatDrugLabel` still leads with the generic, so the flip fails loudly rather than drifting back in.

So card and row still differ on the leading word (`Zyrtec` vs `cetirizine · Zyrtec`). That is a **superset relationship, not a contradiction** — both names are on the row — and B-522 owns closing it properly.

**The lesson worth carrying:** the property test I wrote certified the *function pair* (`formatDrugLabel` starts with `drugDisplayName`) while a shipped *call site* violated the very property it named. A test over pure helpers cannot certify an invariant about call sites, and writing one that reads like it does is worse than not having it.

**Not affected either way:** the vet report. `generate-report` builds drug names server-side (`report.ts:3312`) and is not on this path — the generic remains the clinical primary there.

**Incidental fix kept:** a reachable `Zyrtec · Zyrtec` when brand and generic are the same string is now collapsed to one name.

## B-172 — the card asked a question it had already answered

The combo card asserted at the top ("Logged together", vehicle chip pre-lit) and then asked at the bottom (*"Did Pixel take it?"* with **Given** pre-selected). The owner taps nothing, and **the downgrade affordance — the entire safety point of that row — is easy to miss.**

`comboAdherencePrompt` → `doseAdherencePrompt`, now adherence-driven.

**The rule: assert only what the owner asserted; ask whenever the record is genuinely open.**

| State | Line |
|---|---|
| `given` | `Pixel took it — tap to change.` |
| `partial` | `Pixel took part of it — tap to change.` |
| `missed` | `This dose was missed — tap to change.` |
| `refused` | `Pixel refused it — tap to change.` |
| in doubt | `Did Pixel still get it?` *(unchanged)* |
| unset, no evidence | `Did Pixel take it?` *(unchanged)* |
| combo, vehicle not yet rated | `Did Pixel take it?` — see below |

### Why restating is not reassurance — and the branch where that argument failed

The line is an **echo of the owner's own affirmative tap**, never an app-generated wellness claim. It asserts nothing the lit chip beneath it does not already assert, and it changes **no default** — `initialComboDoseAdherence` and `isComboDoseInDoubt` are untouched, so there is still no path to a reassuring "given" by construction (`clinical-guardrails` Pattern 2).

**That argument has one hole, and adversarial review found it.** It only holds where the `given` *is* an owner tap. In a combo whose vehicle has no `intake_rating` yet, `initialComboDoseAdherence(null)` returns `'given'` — correctly, since there's no evidence the vehicle *failed* and it must not fabricate an in-doubt state either. But "the app had nothing to go on" is not "the owner said so."

And this is the **canonical flow, not an edge case**: the intake chips and "+ Add a med given with this" live on the same meal card (`MealCompletionCard.tsx:263-310`, both gated on `showIntake`), and `handleAddMed` calls `hide()`. So an owner who crushed the pill into the food taps combo at *serving* time — before the bowl has been touched and before intake can honestly be rated. Restating that as *"Pixel took it"* asserts **consumption** derived from an **administration**, and that asymmetry is the entire premise of PR B3. It is also a stronger claim than the card's own title rule, which `MedicationCompletionCard.tsx:185` states as *'Neutral "Logged" (never "Gave")'*.

Fix: `isGivenAssumed({isCombo, vehicleIntake, adherence})` — true only for a combo with `vehicleIntake == null` and `adherence === 'given'` — and that branch keeps the question. Deliberately **not** triggered by a refused/picked vehicle: a dose reaches `'given'` there only by the owner explicitly answering the sharpened in-doubt prompt, the strongest assertion on this surface, and re-asking would resurrect the very defect B-172 exists to fix.

I had actually noticed this configuration while designing the copy and talked myself out of it — "the line doesn't add a claim the chip doesn't already make." That reasoning was wrong: the chip says **Given** (administration); the prose said **took it** (consumption). The isolated reviewer, not anchored by the build conversation, is what caught it.

### The latent contradiction it also fixed

Found while wiring it, not anticipated: the card holds open 1500 ms after a chip tap (`CHIP_CONFIRM_HOLD_MS`) so the change is *visibly confirmed*. A label pinned to `given` would have sat over a freshly-lit **Missed** chip for that entire beat — the card contradicting itself during the exact window that exists to reassure the owner their correction landed. Driving the line off live `payload.adherence` means the prose follows the chips, and turns the hold into the confirmation it was designed to be. Pinned by a test.

`missed` is the one state that deliberately does **not** name the pet: `AdherenceChipRow`'s own header comment splits the pet-driven states (`refused`, `partial`) from the owner-driven `missed`, so blaming a cat for a dose the household forgot would be both factually wrong and unkind. The copy now honours a split the component had only documented.

`ComboDoseConfirmSheet` (B-325) keeps the in-doubt ask — it only ever opens on a not-finished vehicle with unselected chips, so there is no owner assertion to restate.

## Observations deliberately left alone

- **`MedicationPicker`'s tile** leads with the generic, with the brand in the uppercase eyebrow (`ZYRTEC · 5 MG · TABLET`). The brand *is* present, and a picker is a **scanning** surface rather than a **recognition** one, so the mismatch doesn't bite the way the card's did. Making the tile lead with the brand is a visual-hierarchy change, not a copy change, and deserves its own row if the PM wants it.
- **`AdherenceChipRow`'s default `label='Did they take it?'`** is **unreachable** — all four call sites pass `label={null}`. It would violate `nyx-voice` Pattern 1 ("they", not the pet's name) if it were ever used. Left alone rather than fixed speculatively; noted here so the next session that reaches for that default knows.
