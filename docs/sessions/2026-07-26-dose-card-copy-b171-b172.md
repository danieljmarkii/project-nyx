# Dose completion cards — name the drug the owner's way, and confirm-to-correct (B-171, B-172)

**Date:** 2026-07-26

Shipped via **#485**. Two `pm-feature-review` catches from B-156 PR B2b, closed together because they land on the same two lines of the same card. Copy-only: no schema, no migration, no Edge Function, no new secret, no threshold or default changed.

---

## B-171 — the drug is named the way the owner names it

**PM ruling: option (b)** — brand when present, generic fallback. (The PM offered (c) `Zyrtec (cetirizine)` as a swap-in; see the cross-surface note below for where (c)'s content ended up surviving anyway.)

The card read *"Logged together · cetirizine · with Delectable"* for the tile Sam had picked as **Zyrtec**. A confirmation card's whole job is reassurance-by-recognition, so confirming her action in a word she doesn't use spends the card's one moment on the morning it matters least.

The rule now lives in exactly one function — `drugDisplayName()` in `lib/medications.ts` — and is resolved at the call site in `app/log.tsx`, so `MedicationPayload.drugName` stays a display-ready string exactly like its neighbour `pairedFoodName`. The card renders; it never re-derives a name.

### The cross-surface consequence, taken deliberately

This is the part worth recording, because it was a judgment call on top of the ruling rather than a mechanical application of it.

`formatDrugLabel()` (B-161) already existed and already fed three read surfaces — History (`EventRow`), the Home Today strip (`TodayZone`), and the day sheet (`lib/dayEvents.ts`) — and it led with the **generic**: `cetirizine · Zyrtec`. Shipping (b) on the card alone would have produced the exact drift B-171 complains about, just relocated one surface over: card says Zyrtec, the History row directly underneath says cetirizine.

B-171's own row anticipated this ("spans the whole med surface — standalone + combo cards, **maybe** the History row"), and the kickoff asked for the consistency check, so the "maybe" was the call to make. Resolution: `formatDrugLabel` is **rebuilt on top of `drugDisplayName` and reordered brand-first**.

| Surface | Before | After |
|---|---|---|
| Completion card | `cetirizine` | `Zyrtec` |
| History / Today / day sheet | `cetirizine · Zyrtec` | `Zyrtec · cetirizine` |

One rule — *the owner's word leads* — and the generic is kept on the row surfaces, which is where an owner actually looks to answer a vet's *"what's she on?"*. That is also where option (c)'s content survives, in the denser middot form, without spending width on the one-glance card (the combo subline is already `{drug} · with {food}` on a `numberOfLines={1}` label, so `Zyrtec (cetirizine) · with Delectable` would have truncated).

Building the row label *on top of* the card's helper is what makes the leading token un-driftable by construction rather than by review, and a property test pins it: the row label must always `startsWith` the card's name, across the whole cross-product of name cases. Because it is one function, the reorder is trivially reversible if the PM would rather History kept generic-first.

**Not affected:** the vet report. `generate-report` builds drug names server-side and is deliberately not on this path — the generic remains the clinical primary there.

**Incidental fix:** a reachable `Zyrtec · Zyrtec` when brand and generic are the same string is now collapsed to one name.

## B-172 — the card asked a question it had already answered

The combo card asserted at the top ("Logged together", vehicle chip pre-lit) and then asked at the bottom (*"Did Pixel take it?"* with **Given** pre-selected). The owner taps nothing, and **the downgrade affordance — the entire safety point of that row — is easy to miss.**

`comboAdherencePrompt` → `doseAdherencePrompt`, now adherence-driven.

**The rule: assert only what the owner asserted; ask whenever the record is genuinely open.**

| State | Line |
|---|---|
| `given` | `Pixel took it — tap to change.` |
| `partial` | `Pixel took part of it — tap to change.` |
| `missed` | `This dose was missed — tap to change.` |
| `refused` | `Pixel refused it — tap to change.` |
| in doubt | `Did Pixel still get it?` *(unchanged)* |
| unset, no evidence | `Did Pixel take it?` *(unchanged)* |

### Why restating is not reassurance

The line is an **echo of the owner's own affirmative tap**, never an app-generated wellness claim. It asserts nothing the lit chip directly beneath it does not already assert, and it changes **no default** — `initialComboDoseAdherence` and `isComboDoseInDoubt` are untouched, so there is still no path to a reassuring "given" by construction (`clinical-guardrails` Pattern 2). B-156 G1 already ratified the standalone one-tap `given` as the owner's own tap; this only makes the correction path readable. The two branches that still **ask** are precisely the two where nothing has been asserted.

### The latent contradiction it also fixed

Found while wiring it, not anticipated: the card holds open 1500 ms after a chip tap (`CHIP_CONFIRM_HOLD_MS`) so the change is *visibly confirmed*. A label pinned to `given` would have sat over a freshly-lit **Missed** chip for that entire beat — the card contradicting itself during the exact window that exists to reassure the owner their correction landed. Driving the line off live `payload.adherence` means the prose follows the chips, and turns the hold into the confirmation it was designed to be. Pinned by a test.

`missed` is the one state that deliberately does **not** name the pet: `AdherenceChipRow`'s own header comment splits the pet-driven states (`refused`, `partial`) from the owner-driven `missed`, so blaming a cat for a dose the household forgot would be both factually wrong and unkind. The copy now honours a split the component had only documented.

`ComboDoseConfirmSheet` (B-325) keeps the in-doubt ask — it only ever opens on a not-finished vehicle with unselected chips, so there is no owner assertion to restate.

## Observations deliberately left alone

- **`MedicationPicker`'s tile** leads with the generic, with the brand in the uppercase eyebrow (`ZYRTEC · 5 MG · TABLET`). The brand *is* present, and a picker is a **scanning** surface rather than a **recognition** one, so the mismatch doesn't bite the way the card's did. Making the tile lead with the brand is a visual-hierarchy change, not a copy change, and deserves its own row if the PM wants it.
- **`AdherenceChipRow`'s default `label='Did they take it?'`** is **unreachable** — all four call sites pass `label={null}`. It would violate `nyx-voice` Pattern 1 ("they", not the pet's name) if it were ever used. Left alone rather than fixed speculatively; noted here so the next session that reaches for that default knows.
