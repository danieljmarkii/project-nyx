# Vet Files — detail-screen ⋯ actions + honest Files-row state (B-547, B-548, B-549)

**Date:** 2026-08-02

Three `pm-feature-review` (VF-6) follow-ups on the Vet Files track
(`docs/nyx-vet-files-requirements.md`). All detail-screen / add-sheet plumbing — the
append and copy machinery already existed; what was missing were the affordances that
reach it, and one capability state that told the truth too late. No schema, no Edge
Function, no clinical logic.

**shipped via #556.**

## What shipped

### B-548 — honest capability state on the Files/PDF row
The Files row rendered fully live with the confident subtitle "PDFs from email or a
clinic portal", and only *after* the tap did the owner learn the binary lacks
`expo-document-picker` ("PDFs need an app update") — which on TestFlight they cannot
act on. New probe `isDocumentPickerAvailable` (`lib/vetDocumentCapture.ts`) runs once
at mount (a `useState` lazy initializer); the AddDocumentSheet Files row now renders
**disabled with an honest, forward-looking subtitle** — "Available after the next app
update — photos and the camera work now". Empty-states-are-features applied to a
capability state. Camera and Photos never touch that module, so they stay live; the
lazy `require` in the picker stays as the backstop.

### B-547 — D13 "Also add to {other pet}'s Vet Files" on the detail ⋯ menu
§0 D13 / §4.2 say the affordance sits "on the saved moment **and** the detail ⋯ menu";
only the saved-moment half had shipped, so the copy-to-another-pet action existed for
about four seconds, ever. The spec-vs-mock conflict the backlog flagged is resolved
**spec-authoritative** (per the task), making this the small VF-4b anticipated — D13
needed no amendment (it already named the detail menu; the mock simply hadn't rendered
it). New reader `readLocalVetDocumentGroup` reads the full local rows (the
library/detail read models drop columns a copy needs — `source`, `file_size_bytes`,
`notes`…) and feeds the existing `duplicateVetDocumentRowsForPet`. One line per other
pet, **multi-pet accounts only**, flips to a confirmed "✓ Added…" in place.

### B-549 — "Add another page" on the detail screen
The append machinery (`buildVetDocumentRows` takes `groupId`/`startPageIndex`/
`documentDate`) existed only behind the saved moment, so a discharge sheet whose page 4
was missed meant delete-and-recapture — the exact case the §4.4 `document_group_id`
grouping was built for. Added to the ⋯ menu for **image documents only** (a PDF group
is one page per PDF, §4.4). Camera path, matching the saved-moment append. Shipped in
scope — no re-file needed.

### Refactor
Extracted `pickVetImages` / `pickVetPdfs` from `app/vet-files.tsx` into new
`lib/vetDocumentPickers.ts`, so the detail screen reuses the exact camera path (one
permission prompt, one asset mapping, one definition) and the B-548 probe lives beside
the picker it guards. Verified byte-identical to the removed inline code. Also moved the
shared `AlsoAddTarget` type into `lib/vetDocumentCapture.ts` (beside `alsoAddLabel`/
`alsoAddedLabel`) rather than importing it sideways from a sibling component.

## Reviews (both run to satisfy the DoD)

- **`rls-privacy-reviewer` on the B-547 copy-under-another-pet boundary → PASS.** Every
  attack held server-side: a forged `otherPetId` = a foreign-account pet is denied by
  both the `nyx-vet-documents` owner-insert Storage policy and the row upsert's RLS
  (both re-derived from `auth.uid()`, so a compromised client can't file cross-account);
  `{own}/../{victim}` traversal throws in `buildVetDocumentPath`; a cross-pet copy in one
  account gets a fresh `document_group_id` and passes `enforce_vet_document_pet_scope`;
  `vet_visit_id` is dropped on the copy; the copy re-encodes via `compressForUpload` at
  sync with no raw-original path. **It also caught one non-privacy correctness gap, now
  fixed:** copying a *hydrated-but-never-viewed* page (`local_uri = ''`) minted a row
  under the other pet pointing at an object upload never writes (`needsObjectUpload('')`
  is false) — a silently blank clinical document. `handleAlsoAdd` now caches every page
  first (from the signed URLs the screen already resolved) and **declines with "Needs a
  connection"** rather than filing a broken copy offline — the same register as the
  share path.
- **`code-reviewer` → fix-before-merge (fixed).** The append reused `buildVetDocumentRows`,
  which always wrote `kind:'other'/title:null/notes:null` — safe for the saved-moment
  append (always pre-metadata) but wrong for the detail-screen append, where the owner
  may have already renamed/typed the document, so an appended page would disagree with
  its siblings (masked today by cover-pinned reads, a real defect the moment anything
  reads per-row). Fixed: `BuildVetDocumentRowsInput` gained optional `kind`/`title`/
  `notes` (defaulting to the D11 values), and `handleAddPage` passes the group's current
  facts (`detail.kind`, `detail.untitled ? null : detail.title`, `detail.notes`). Also
  fixed an accessibility clobber the reviewer flagged (my explicit `accessibilityState`
  overrode the busy-disabled state) and moved `AlsoAddTarget` to lib (the NIT). The
  extraction was verified behavior-identical.
