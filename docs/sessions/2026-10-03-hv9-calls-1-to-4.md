## Decisions

- The search caption reuses `SEARCH_COUNTS_NOTHING` rather than the brief's illustrative "Search finds; it never counts.": one sentence for one fact, in one place. This was stated in the plan the PM approved.
- `filterLabel` is required on `countLineOf`, not optional. A forgotten label would print "undefined" on screen, so the type checker forces every caller to supply one.
- The pet name gives up its `header` role for `button`, matching Home. `code-reviewer` flagged that VoiceOver's rotor loses History's only heading. Accepted as Home's precedent, and noted here for HV-12's accessibility pass.

## Teach

### One thing — A JavaScript change rides an update; a native change needs a new build (S1, L1)
The app on your phone is two layers. One is the native shell Apple reviews: the camera, the notifications, every built-in library. The other is the JavaScript that draws the screens and makes the decisions. A JavaScript change can be sent to installed phones as an over-the-air update in minutes. A change to the native shell needs a new TestFlight build and, for the store, a new review.

**Like:** a restaurant's menu versus its kitchen. Reprinting the menu (the JavaScript) is overnight. Adding a pizza oven (native) means a contractor and an inspection.

**In today's work:** `components/historyV2/PinnedRow.tsx`
`import { ChevronDown, Search } from 'lucide-react-native';` uses an icon library already inside the shell, and `PetSwitcherSheet` is a screen already shipped. Nothing new enters the kitchen, so the whole PR is menu changes.

**Why it matters to you as PM:** whether a fix can reach owners tonight or waits for an App Store review is decided by this line, not by how big the change looks.

**Check:** If the next History change added a brand-new library that talks to the phone's photo gallery, could it reach your installed TestFlight build by an OTA update? Why or why not?
