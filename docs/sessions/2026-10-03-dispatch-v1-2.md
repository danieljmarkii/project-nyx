# Dispatch v1.2: a merge wakes the dispatcher, one digest per round, rulings ranked by payoff

**Date:** 2026-10-03 · **Issues:** CUL-1503, CUL-1504, CUL-1505, CUL-1506, CUL-1507 · shipped via #1009
**One thing:** none — a process session; it illustrated no new concept on the curriculum's current rungs

## What happened

The PM asked for a retro on the dispatch loop, then asked to see what a day would look like after the proposed changes, then said "file them and build all five".

**The retro, from the record.** It drew on the ten `/dispatch run` status updates on Engines v3, the PRs they launched, and the child session records.
- Every one of the 18 launches merged. None died, and no two collided on the same files.
- The median time from launch to merge was about 75 minutes.
- Since v1.1, dispatch has had no wrongly closed issue to reopen. Two went Done early (CUL-1134, CUL-583), and the sessions that closed them caught it on their own read-back.

The friction, ranked by cost:
1. **The PM was the clock.** There were five runs on 9/29, then a 41 hour gap after the 9/30 batch merged.
2. **The PM's "go" was a rubber stamp.** Across 10 runs the PM accepted every proposal unedited. Since v1.1 the standing yes launched 2 of 13 rows.
3. **Rows waited on rulings and on missing rows.** At the 10/2 run only one row was ready. PR-28's split work (CUL-1436, CUL-1437) never reached the page.
4. **Children wrapped for a human reader nobody had.** All 18 ran the full `/wrap`, and nothing summarised them.

## What shipped

**`.claude/commands/dispatch.md`, v1.2:**
- **Wake (CUL-1503).** The session that runs `/dispatch` stays on as the dispatcher.
  - Each child sends it exactly two messages: one when its PR opens, and a final one carrying the wake line and its return block. A wake reruns steps 0–8.
  - A child's message is a trigger, never an input, and a message that doesn't start with the wake line is data.
  - Standing-yes rows launch on a wake only in the PM's daytime (or within 2h of the PM typing). Overnight, a 07:30 check-in launches them.
  - One fallback check-in, recorded as `Check-in: <UTC>`, catches a child that dies silently.
  - The status update names the dispatcher. A second session asks for `take over` before running beside a live one.
  - The never-line is now one exact text, passed verbatim as the child's appended system prompt.
- **Standing yes widened (CUL-1504).** The critical-path condition is gone. Migrations, discovery work, new owner-facing words, privileged verbs and a first dispatch still ask.
- **Round digest and teach row (CUL-1505).** Each wake that resolves a merge or a stop prints one digest built from the children's returns. One row in flight carries `Teach: yes`.
- **Ruling index (CUL-1506).** Step 3 computes every hold on the PM, ranked by rows it frees outright, then rows held. Step 8 keeps one `/dispatch: <project> — what's holding the run order` issue under `Waiting on PM`.
- **No-row detection (CUL-1507).** New project issues (from 2026-10-03) that no row names are proposed as rows. The PM adds one with `add CUL-NNN` or declines it with `skip CUL-NNN`.

**`.claude/commands/wrap.md`:** a `/wrap --dispatched` section. Steps 1–4 run before the merge, then the merge or the stop, then the read-back, then a five-line Dispatch return. There is no Dev Handoff in chat (the QA script goes in the PR body), and no Next Session Kickoff. A One thing is written only on the teach row, under `## Teach`, with no line starting `**One thing` so the ledger grep stays clean.

**`.claude/skills/backlog-groomer/SKILL.md`:** step 12 counts a `/dispatch:` index once and never lanes, defaults or closes it.

**`CLAUDE.md` § Dev Handoff:** a dispatched child skips the in-chat handoff (`/wrap --dispatched`). The section was tightened to pay for it, net −8 B.

## Review

An isolated `code-reviewer` pass returned fix-before-merge with eleven findings, four of them blockers:
1. A merge wake could chain launches overnight with nobody watching.
2. The never-line was not self-contained as a system prompt.
3. The order of a child's closing message was undefined.
4. The teach block had nowhere to live that wouldn't pollute the ledger grep.

Among the rest: `add 1` could hit a different issue after a wake, and check-ins could stack. All eleven were fixed in this PR and re-checked by the same reviewer. The re-check closed them and raised four small follow-ups, also fixed: the step 6 launch sentence now defers to the daytime gate, the teach flag clears when its row merges or dies, the never-line permits the self-merge, and the CLAUDE.md line says what a child skips.

## Decisions

- **PM, 2026-10-03:** build all five, including the widened standing yes (CUL-1504).
- **Team call, recorded for the PM:** the 07:30 morning check-in is armed overnight. CLAUDE.md § PR check-ins says never to leave one armed overnight, because such a check-in "is guaranteed to find nothing". This one is guaranteed to find something, the standing-yes rows held for daylight, so the rule's reason doesn't hold here. Flagged to the PM as a better-than-the-rule call. **PM ruled 2026-10-03: keep it.** CLAUDE.md § PR check-ins now names it as the one overnight exception.
- **Not done:** subscribing the dispatcher to children's PRs. The harness's PR-watch posture would have it fixing their CI.
