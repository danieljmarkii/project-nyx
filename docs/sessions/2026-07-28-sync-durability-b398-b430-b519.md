# Pre-release sync durability — B-398, B-430, B-519

**Date:** 2026-07-28

Three pre-release durability items in `lib/sync.ts` / `lib/db.ts`, landed together because they are the same bug wearing three hats: **the local queue could lose or strand an owner's health record, silently.** Shipped via #509.

---

## B-398 — the poison-pill wedge, and the badge that hid it

**What was wrong.** Every batch writer was shaped:

```ts
const { error } = await supabase.from(t).upsert(rows);
if (error) { console.error(...); return; }   // marks NOTHING synced
await markSynced(db, t, rows.map(r => r.id)); // assumes ALL landed
```

Wrong in both directions at once, and the two halves compound:

1. **One structurally-bad row wedged the entire table's queue.** The batch is a single upsert, so a row the server can never accept fails the call, and every other row is blocked behind it. The queue read is `LIMIT 100` ordered by rowid, so the poison row stays permanently in the window — the wedge is for the life of the install, not for a cycle.
2. **No give-up.** No attempt counter, no dead-letter, no reason recorded. The doomed request was re-sent every cycle forever.
3. **It was invisible.** `getSyncStatus()` counted unsynced `events` and nothing else, and `SyncBanner` keys off that. A wedged `meals` queue — the diet-trial owner's entire reason for using the app — reported zero pending and the banner stayed silent.

**What shipped.** A new pure module, `lib/syncQueue.ts`, holding the whole contract; `pushRows` in `lib/sync.ts` replacing seven hand-rolled upserts (it is `pushDietTrialRows` generalised — the diet-trial writers had already needed all of this for migration 040's UNIQUE index, and nothing about it was trial-specific).

- **`.select('id')` + a landed-set comparison** everywhere. An RLS-blocked write returns *success with zero rows*, not an error (the 009 trap); only ids PostgREST hands back are marked synced.
- **Per-row isolation on any row-level refusal.** The innocent rows land, the guilty row is left holding its own failure. Bounded: the rows that land leave the queue, so the fan-out shrinks rather than repeating.
- **`sync_attempts` / `sync_error` on all twelve queue tables**, with quarantine at `MAX_SYNC_ATTEMPTS = 25`.
- **`getSyncStatus` counts every queue**, plus a separate `quarantinedCount`; `SyncBanner` leads with the quarantined line.

### The decision that mattered most: what costs a row an attempt

A retry budget that counts network failures is a data-destroying bug wearing a durability feature's clothes. An owner offline for a fortnight — a diet-trial owner logging meals in a flat with bad signal, i.e. the wedge user — would come back online to find their whole queue quarantined by a server that never saw a single row.

So `classifySyncFailure` splits three ways, and the line is **did Postgres evaluate this row and refuse it?**

| Class | What it is | Cost |
|---|---|---|
| `transient` | No code at all (network/timeout/offline); a PostgREST code (`PGRST301` expired JWT); SQLSTATE classes `08`/`53`/`57` (connection, resources, operator intervention) | **Nothing.** No attempt, no isolation. |
| `rejected` | A row-level SQLSTATE — `23503` FK-not-landed, `42501` RLS, `22001` value too long | One attempt; quarantine at the cap. |
| `terminal` | `23505` / `23514` / `23502` / `22P02` | Quarantine immediately. |

The request-level carve-out was found by an existing test rather than by design: a `PGRST301` batch failure isolating into N single-row requests is pure waste, because the failure belongs to the session, not to any row. Charging each row an attempt for it would punish the innocent.

**A quarantined row is never deleted and never lies.** `synced` stays 0, the reason is recorded, the row stays on the device and stays counted — so giving up means the owner is *told*, never that a log quietly disappears. Any local edit clears `sync_error` and re-queues it, which is enforced by a source scan rather than by memory (a write path that forgot would make that row unrecoverable from inside the app forever).

### Two contract changes to existing tests, both deliberate

- **23503 now isolates.** The old test asserted it should not, reasoning that an FK parent resolves next cycle anyway. That missed the *mixed* batch, which is the common one: if row A's parent landed and row B's did not, the single upsert fails wholesale and A is blocked behind B, every cycle.
- **Success-with-zero-rows now spends an attempt.** Previously it stayed queued honestly but forever.

## B-430 — sign-out silently destroyed offline captures

`wipeLocalSession()` clears local SQLite unconditionally, **including rows still at `synced = 0`**. Latent until B-280's D6b ruling made it involuntarily reachable, but a *deliberate* sign-out has cost the same data all along — and on a household sharing one credential across two phones, sign-out is routine.

**Ruled: flush-before-wipe on a deliberate sign-out. Not quarantine-with-prompt.**

Quarantine-across-the-wipe was the more tempting option — it covers the involuntary case too. It was rejected because it collides head-on with FR-9, which is the reason the wipe exists: a shared or borrowed device must not leak the prior account's health record to whoever signs in next. A retained cache of that account's meal logs, symptom events and photos **is** that leak, whatever it is labelled — and it would need its own account-scoped storage plus a "whose rows are these?" answer at the next sign-in, since the retained rows carry the previous account's `pet_id`.

Flushing keeps the wipe absolute and puts the residue where it belongs: send what can be sent, then tell the owner the truth about the rest.

- `flushPendingForSignOut()` (sync.ts) — the push half of a cycle, extracted; pulling on the way out would hydrate rows the wipe deletes moments later.
- `flushForSignOut()` (session.ts) — flushes, then reports what is still unsent. **Fails toward warning**: a status read that throws returns a non-zero count, because "we cannot tell" must not read as "all clear" on precisely the broken device most likely to be holding unsent rows.
- Settings warns naming the count, offering *Stay signed in* / *Sign out anyway*. Silent in the common case (online owner, queue drains).

**Residual, unchanged and unfixable client-side:** an *involuntary* sign-out cannot push — the JWT is already gone and there is no owner present to ask.

## B-519 — the sign-out file wipe was a hardcoded UNION

`clearLocalData` deleted captured on-device files by unioning `local_uri` out of three hand-listed tables. The nastiest fail-open in the repo: a new mirror table missing from it would have its **rows** wiped by `LOCAL_WIPE_TABLES` while its **files** stayed on disk — and once the row naming a file is gone, nothing can ever find it again. An un-deletable photo of the previous account's pet, on a device now in someone else's hands, with no index left that even knows it is there.

Fixed the way B-424 fixed the row half: ask the database. `LOCAL_URI_TABLES_SQL` derives the set via `pragma_table_info`, so a table added tomorrow is covered the moment it is created. `KNOWN_LOCAL_URI_TABLES` survives only as a device-side fallback and is pinned equal to the derivation by the guard test, so it cannot become a stale second list.

## Fallout: the runtime schema was reproducible nowhere

Adding columns surfaced a gap nobody had named. The **real** local schema is the three DDL constants **plus** `initDb`'s `ALTER TABLE` upgrade path — and the ALTERs lived inside `initDb`, which needs expo-sqlite and so cannot run under jest. Every test wanting a realistic database hand-mirrored "the columns this code touches", and those copies drifted silently. `lib/captureInbox.test.ts` proved it by failing against a fixture that had been correct when it was written.

So the seventeen inline ALTER blocks became data — `COLUMN_UPGRADES` + `applyColumnUpgrades()` in `lib/localSchema.ts` — verified one-to-one against the removed statements. `initDb` and the tests now build the same schema from the same list, and the quarantine columns are generated from `SYNC_QUEUES` so the set that gets the columns and the set the badge counts are provably the same set.

`lib/sqlShape.test.ts`'s `STATEMENT_FLOOR` dropped 60 → 45 as a consequence (seventeen ALTER call sites became one loop; seven upserts became one `pushRows`). Verified by reading the delta rather than chasing the number down — `INSERT_FLOOR` did not move, because the statements that guard actually checks are untouched.

## Tests

**+55 cases**, 3418 passing, `tsc --noEmit` clean. New: `lib/syncQueue.test.ts` (31), `components/ui/SyncBanner.test.tsx` (7), plus `pushRows` behaviour in `sync.test.ts` and B-430 in `session.test.ts`.

Three of them are the ones worth keeping honest:

- **`SPENDS NOTHING on an offline device`** — the fortnight-in-a-basement case. If this ever goes green-by-accident, the feature has become the bug.
- **`quarantines at the cap and NOT before, against a real SQLite`** — executes the production statement 25 times against `node:sqlite`, because the boundary is a `CASE` reading SQLite's pre-update column values and an off-by-one is either a row parked a cycle early or one that never parks.
- **`THE WEDGE: one refused row no longer blocks the other 99`** — the assertion that was `[]` before this PR.

Both fail-closed guards are **mutation-verified**: a scratch table proves the derivation derives rather than returning a fixture. Without that, both would still pass if someone quietly replaced the query with a hardcoded list — which is exactly the failure B-424 removed from the wipe guard.

## Notes for the next session

- **Nothing here is deployed.** No migration, no Edge Function — the schema changes are local SQLite only, applied by `initDb` on next launch.
- **The quarantine surface is minimal by design.** An owner whose row is parked is told by the banner and told to re-save from History. A real "these entries need attention" screen (tap → the offending entry) is worth a backlog row if quarantine turns out to fire at all in practice.
- `MAX_SYNC_ATTEMPTS = 25` is a judgement call pinned by a test with a `>= 10` floor, so lowering it is a deliberate argument rather than a drive-by.
