# Engines v3 PR-11b — the pure Signal pipeline

**Date:** 2026-09-28

Shipped via #971 (CUL-1267, PR-11b only; PR-12 is the issue's other open PR). Engines v3 · Wave 1 · Lane A. Server only, no migration.

## What shipped

- **`supabase/functions/generate-signal/pipeline.ts`** — `runSignalPipeline({ rows, prior, nowMs, engineFlags, careRecord })`: synchronous, no I/O, no clock, no env. Every step between the reads and the phrasing moved in from `index.ts` unchanged and in the same order (row mappers, dose/vehicle pairing, `isTrialRunning`, detect, curate, decorate, strip onsets, summary packet, coverage, stand-down resolution). `assembleSignal` merges the markers after phrasing; `templatePayload` gives the EN-1 harness the whole cache row with no model.
- **The reserved slot, option (a) as the PM ruled at the plan:** `careRecord.ownerAnswers: { findingKey, answeredAt }[]` and `careRecord.appointments: { id, scheduledAt, cancelledAt, vetVisitId }[]` (066's columns). Required; the shell passes `[]` and makes no new read. Guard (d) pins it as read by nothing; PR-23 flips (d) on purpose.
- **`index.ts`** is now the I/O shell: auth, cap, flag read, the nine reads, the prior-row read (moved before the pipeline, same query, fenced), phrasing, the cache write and the shown log.
- **`standDownMintAllowed` moved** unchanged from `_shared/engineStamps.ts` to `_shared/engineFlags.ts` (re-exported). The new closure guard found that `engineStamps.ts` imports supabase-js, which would have put a network fetch into the harness's module graph.
- **Guards**, each proven by mutation: `_shared/engineCorpus/signalPipeline.{corpus,test}.ts` (13 hand-built cases in PostgREST shape, hand-stated cache rows, floor, flag-state invariance over every `ENGINE_KEYS` state, the reserved record read by nothing, repeatability and no input mutation, both fences keep findings and report the error); `generate-signal/pipeline.test.ts` (no clock/env/network/database/logging in the file, no remote specifier in its closure, every gated key registered in `SIGNAL_ENGINE_KEYS`).

## Proof

- Existing suites green; `index.test.ts`'s EN-F source pin moved with the gate (it pinned the gate's location, not its behaviour) and gained a pin on the shell's hand-over. 2,047 Deno tests; `deno check` clean on `supabase/functions/` and `scripts/`; CI green on the head.
- One-off differential (scratch, not committed because it needs the old code): old and new handlers against a stubbed Supabase client, 13 cases × 3 `app_config` states → 39 runs, 0 differences in response, cache row and shown log. A planted change showed up, so the comparison can see one. The `adversarial-reviewer` extended it to 186 runs (prior read throwing, null profile, extreme and empty timezones, blank and null names, a stubbed model, throwing resolution, carried markers across flag stamps): 0 differences.

## Reviews

- **`code-reviewer`:** after the single fence was split in three (read / resolve / merge), a merge throw had become silent. Fixed: `SignalPayload.standDownError` carries it and the shell logs it, with a test and a pin. It also flagged the missing hand-over pin (added) and nits (fixed).
- **`adversarial-reviewer`:** byte-identity held; the stand-down gate held with a simulated Signal key. It **broke** the flag-invariance guard: the states were hard-coded to `engines_v3_en0`, so a step gated on an unregistered key (it tried one that drops every card, safety included) passed all 99 tests and would also have slipped past the stand-down gate. Fixed by deriving the states from `ENGINE_KEYS` and adding the registered-key scan; its exact mutation now reds both.

## What this does to the vet report

Nothing. `generate-report` runs its own detection over its own window and never reads `ai_signals`. It redeploys on merge only because its closure includes `_shared/engineFlags.ts`; `analyze-vomit` and `analyze-stool` redeploy for the `engineStamps.ts` re-export. Byte-identical behaviour.
