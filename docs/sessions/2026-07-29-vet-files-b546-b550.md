# Vet Files — name the file, name the pet (B-546, B-550)

**Date:** 2026-07-29

Two VF-6 `pm-feature-review` findings landed, shipped via **#508** (draft). Both were small; the interesting part is what the re-review found on top.

## B-546 — the app had the filename and threw it away

`pickedFilesFromDocumentAssets` read `asset.name` to infer a MIME type and then dropped it, and `buildVetDocumentRows` wrote `title: null` unconditionally. A PDF gets no thumbnail **by design** (D5) and capture asks nothing **by design** (D11), so two lab PDFs pulled from one clinic portal on one day rendered as two rows identical down to the pixel: same glyph, same `Document — Jul 14`, same dashed Add-type chip, same date. The ER record class, unidentifiable — and the disambiguator had been in our hands the whole time.

PM ruled **option (b)**: render the filename as a secondary meta line, leave the row untitled.

Option (a) — filename-as-title — is the tempting shortcut and it is worth writing down why it loses. `title IS NULL` is the *only* test that distinguishes "nobody has named this" from "the owner typed that", and it is what the one-tap Name pill keys on (migration 044 says so in its own `COMMENT ON COLUMN`). A filename-as-title row would look named, lose its Name affordance forever, and hand the owner `Scan_20260714_0001.pdf` as the document's identity.

Four decisions inside the build:

- **The column is server-side** (migration 048, `source_filename`, nullable TEXT + a 1..255 CHECK). A local-only column was the cheaper option and it is wrong twice: provenance is a fact about the *document*, not about the device that filed it (D10 — it belongs beside `source` and `file_size_bytes`, which already round-trip), and it would vanish on the owner's second device, which is exactly the hydrated library where two undifferentiated PDF rows are hardest to tell apart, because that device has no thumbnail cache either until each document is opened once (AC 12).
- **Files path only.** `pickedFilesFromImageAssets` deliberately does not set it — a camera-roll asset is called `IMG_4821.HEIC`, machine noise that would put a meta line on every image row to say nothing. There is a test asserting image picks carry no filename, so widening it past the Files path cannot happen silently. It is a client *convention* and deliberately not a CHECK: a future ingestion path (email forwarding, share-sheet import, both parked in §11) will arrive with real filenames under some other `source`.
- **Sanitised at the write path** (`sourceFilename`): basename only (Android's SAF returns display names containing paths), control and bidi characters stripped, whitespace collapsed, capped at 120 — well under the server CHECK, so the client can never mint a row the server refuses and wedge it at `synced = 0`. This is the one value on the row persisted *without the owner typing it*, so nobody reviews it before it lands. The bidi rule is not paranoia: `U+202E` makes an extension render backwards, and on a screen whose job is telling a PDF from a photo that is a lie, not a curiosity.
- **Where it renders differs by surface, on purpose.** The library row shows it **only while untitled** — once a name exists the name *is* the identity, and a machine string under it is noise on a screen whose whole job is one calm list. The detail screen shows it **always**: that is where the owner confirms they are about to hand a vet the right file, and "which PDF is this, actually" is a question a typed name doesn't answer.

D13's duplicate-on-add carries it (the copy is the same file, filed twice — unlike `vet_visit_id`, which is dropped because a visit belongs to one pet). Both hydration branches carry it, so a device that captured pre-048 and a device that only ever hydrated converge rather than one keeping a stale NULL.

## B-550 — the detail screen named the pet nowhere

The header read "Vet Files"; the pet appeared only inside the filename of a file that had *already left the app*. So Sam could hand an ER vet a phone showing a two-cat household's document with nothing on screen saying whose it is — the one surface where getting that wrong means a vet reads the wrong patient's bloodwork.

- Header is now `{pet}’s Vet Files`. §4.1 already makes the pet's name the library header's job ("the only filing cue a multi-pet household gets"), and this bar sits *outside* the ScrollView, so it survives the phone being turned around over a scrolled document.
- `DocumentPdfViewer`'s bar carries `{pet} · {title}` — that Modal hides the header and is the actual handover surface for a PDF.
- Both resolve from `pets` by the **document's** `pet_id`, never `activePet`, and both degrade to the bare title when the pet cannot be resolved (archived pet, cold deep link) rather than rendering "your pet’s Vet Files". Same resolve-or-stay-silent rule VF-6 established for the share filename: an unnamed artifact is recoverable, a confidently wrong one is not.

## The migration

048 is one nullable column, its CHECK and its COMMENT. Applied to production **ahead of** this code, deliberately: the push payload now carries `source_filename`, so shipping the client first would have made PostgREST reject every vet-document upsert and wedge that queue. Pre-flight matched the header (0 rows, column absent); verified after (column present and nullable, CHECK present with the expected definition, `get_advisors` security + performance showing nothing new — the migration adds no function, policy or index).

**One rule was knowingly broken and is flagged in the PR:** this bundles a migration with UI, against schema-isolation. The session was pinned to a single branch, and the column is precisely what the UI renders — splitting it would have shipped a read of a column that does not exist.

## The re-review is the substance of this session's outcome

`pm-feature-review` re-ran against the built screens and returned **NEEDS-WORK on three of four flows**. Its framing is worth keeping: *both fixes stop one surface short of the moment they exist for.*

**Two findings were fixed in the same PR:**

1. **The filename line shipped at `colorTextDisabled`** — `#A3A3A3`, ≈2.5:1 on the row surface, below even the 3:1 large-text floor. The palette's "you cannot use this" colour, on the one string whose entire job is letting an owner tell two lab results apart one-handed in clinic light. Now `colorTextTertiary` (≈4.7:1), matching the meta line above it and the detail screen's rendering of the identical string. The lesson generalises: *quiet is a hierarchy instruction, 2.5:1 is a legibility failure, and they are not the same thing.*
2. **`petName`'s `'your pet'` prose fallback leaked into the share filename** — correct in the dialog title, and `your-pet-lab-result-2026-07-14.pdf` in the artifact the vet keeps. The header's fallback had been written to degrade properly and the filename had been left behind. Now passes `''` so `slug()` uses its own `pet` fallback, with a test pinning the anonymous path.

**One was raised to the PM and then fixed in the same session:**

**B-587** — the reviewer's blocking find, and the sharpest. An untitled document shared as `Pixel-other-2026-07-14.pdf`, because `vetDocumentShareFilename` fell back `title → kind` and capture defaults *both*. Untitled + `other` is not an edge case; it is what *every* document is until the owner does two optional things. So B-546's own thesis — the app had the name and dropped it — still held at the one action §4.3 calls "the single most important affordance after viewing": the owner reads `CBC-Pixel-2026-07-14.pdf` on the detail screen to check they have the right PDF, taps Send, and hands over `Pixel-other-…`. Second defect in the same string: `other` is an *absence* everywhere else in this feature and became an assertion inside a clinical filename.

It was put to the PM rather than fixed silently, because it changes what artifact a vet receives. **Ruled yes to both halves.** The chain is now `title → source filename stem → kind → "document"`, `other` never reaches a filename, and two "don't say it twice" rules ride along — the pet prefix is dropped when the name already starts with it (case-insensitively; a PIMS export is very often `Pixel-CBC-2026-07-14.pdf`, and prefixing again reads as a bug in the app that produced it) and the date suffix is dropped when the name already contains that date. A stem carrying no date still gets one. Both rules apply to a typed title too — one rule is easier to hold than two. Only the extension is stripped, and the new one comes from the row's stored mime, so `labs.PDF` cannot become `labs-PDF.pdf`.

That closes B-546 end to end for the first time: pick → row → detail → the file the vet keeps.

**Four were filed rather than fixed:**

- **B-588 (`Next`)** — the reviewer's highest-value catch. The **Name sheet** is the one surface that does not show the filename, so an owner naming one of two identical documents does it blind and has to Cancel, re-read the row and re-tap. B-546 surfaced the disambiguator on the row and withheld it from the surface where it gets *used*.
- **B-589 (`Next`)** — the **multi-PDF saved moment** now the only Vet Files surface where two PDFs are still identical: one card reading "2 documents" with a singular "Name it" that silently names the cover group.
- **B-590 (`Next`)** — the image lightbox is still unnamed. `PhotoViewer` is chrome-less by design, but email screenshots are this feature's *primary* capture class, so it is the higher-volume handover surface, not the lower one. The fix is an optional `caption` beside the existing Close, not a title bar.
- **B-591 (`Next`)** — pre-existing VF-4: `DocumentHero` branches `isPdf` before `unreachable`, so AC 12's honest "needs a connection" sentence is structurally unreachable for a PDF. Contradicts that screen's own header comment.

The reviewer also endorsed keeping the "hidden once named" rule (*"reads as tidying, not data loss"*), and named a real second-order cost of it: a half-named library asks the owner to compare a human name against a machine name. That is the argument for B-588 rather than for reversing the rule.

Two things still want the device: a screenshot of a populated library row at real width (middle truncation protects the extension and the stem, but the common PIMS shape `Pixel_Smith_CBC_2026….pdf` differs in the *middle*), and a long pet name in the header (`Header` is `numberOfLines={1}`).
