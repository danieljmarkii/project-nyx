# Signals v2 PR 7 (CUL-14) — the watching system (per-lane rows with real counts)

**Date:** 2026-08-15

Built PR 7 of the Signals v2 track (B-755): the D5-ratified **watching system** — the Signal empty state grows a per-lane row with **real partial counts** ("Timing — 4 of the 6 timed episodes a pattern needs"), replacing the abstract "we're watching for…" placeholder. Client-only, dark behind the two-gate `signals_v2` flag, **flag-off byte-identical**, **no redeploy** (G10). Blocked-by CUL-7 (PR 2, L1 + `timing_story`, #642) and CUL-8 (PR 3, L2 trial-response, #644) — both shipped; this PR reads the same local record they analyze, one layer below their server floors.

## Why this exists (R-5, the PM overrule)

Mock round 1's R-5: the PM overruled the team's defer-lean and ratified **"watching, with real counts" as a SYSTEM** — each lane contributes a row that states what it HAS and what its math REQUIRES. The register worries (does it read as a promise / a nag?) became **build constraints** (G8), not a deferral. The rows are the concrete form of the same idea the B-721 E1 ghost previews sketched — so when a lane has something real to report, the real-count row takes the ghost's place.

## The one architectural fact that shapes everything

The watching rows render in the **empty state** (building / no_pattern) — by definition the state **below every server floor**, where `generate-signal` has emitted no finding. So the counts **cannot** come from a cached finding; they are **computed client-side from local SQLite at render time**. This is the same shape as PR 6's standing trial line (`lib/trialResponseCounts.ts`) and PR 9's Patterns panels (`lib/patternsTiming.ts`): a **reader, not a second engine**. All meal-relative timing runs through `lib/mealTiming.ts` (G9); the local reads are **shared** with `lib/patternsTiming.ts` (`readVomitOnsets` / `readFeedingRows` / `readFreeFedSpans`) — one local-event source, never a second reader that could drift.

## The per-lane gates (each row is a "still needs" statement — G8)

| Row | Renders when | Copy |
|---|---|---|
| **Timing** | 1 ≤ timeable vomit episodes (60d window) < `minEligibleEpisodes` (6) | "Timing — N of the 6 timed episodes a pattern needs." |
| **Change** | fewer than 2 full weeks of span (`floor(dayNumber/7) < 2`) | "Change, week to week — needs 2 full weeks of logging to compare. This is week {ceil(dayNumber/7)}." |
| **Gap** (escalate-only, G5) | ≥3 collapsed gaps (180d era) AND the recent 3 strictly decreasing AND meaningfully shorter (latest ≤ 0.5× median) AND current (recency guard) | "Gaps between vomiting episodes — 6 days, then 3, then 2." |

- **Timing** is windowed to 60d (the engine's `analysisWindowDays`) so "N of 6" is honest for a mature-but-sparse vomiter (old episodes don't read "almost there"). A 0-timeable pet gets no row (no timing question to pose); a ≥6 pet gets none (the lane can run).
- **Gap** is the **watching floor** (`minGaps` = 3) — deliberately BELOW L4's **firing floor** (`runLength` = 4), which the deployed server finding owns; the config comment in `detection.ts` names this "PR 7's client row" explicitly. Every OTHER gate is **server-faithful** (G9): the same 180-day era window, the same strict-decrease, the same "meaningfully shorter than the median" ratio gate (adopted after the adversarial review — 5a), and the same recency guard. The ONLY difference from the finding is `minGaps` 3 vs `runLength` 4 — the sub-floor sensitivity the row exists for. All constants carry their anchors and are never tuned to any record (G6).

## Composition — the one design call (flagged for the PM frame-review)

§4.4: "the rows render inside whichever empty-state frame is live … additive content, not a frame." Interpreted as: the watching-rows feature introduces **no fourth frame** — it composes into the live one. Within the **building** frame it *replaces* the abstract "what we're watching for" middle (ghost previews / ghost list) with the concrete rows, because that placeholder was always a sketch of exactly these rows (the mock §05 shows only the real rows, never both — "duplicate information" was R-1's objection to A1). Within **no_pattern** (which has no such placeholder) it's purely additive. The headline and a single safety-floor line always survive. **Flags stay independent:** `signals_v2` on / `signal_design_v2` off renders the rows in the *shipped* frame; both on renders them in the B-721 frame.

### Reviews — verdicts

**`adversarial-reviewer` (the escalate-only gap detector) — PASS, with two findings folded in-session + one disclosed residual.** Every falsification of the escalate-only invariant HELD: strict-decrease is airtight (flat / lengthening / tie / single-dip / float-tie all → null), the recency guard suppresses stale/reversed runs on the correct latest gap, collapse defeats re-log gaming, and the timing "N of 6" is faithful to ⑤ (no over-statement). Three server divergences were named; two were real and are **fixed this session**:
- **5a (fixed): the `gapShorteningRatio` (0.5) gate was omitted.** Without it a trivial `[50h,49h,48h]` fires and rounds to a flat-looking "2 days, then 2, then 2" — a shortening *claim* that communicates non-change. Adopted the server's gate (latest ≤ 0.5 × median of all in-window gaps): server-faithful (G9), fixes the misleading render, and halves the by-chance rate. The mock's isolated `[144,72,48]` (as a pet's only 3 gaps, median 72) correctly no longer fires — a 4-episode record isn't strong enough evidence of acceleration; the row now fires only when the recent run is meaningfully shorter than the pet's *typical* gap. The verbatim copy is unchanged (the sequence is still rendered when the gate passes).
- **7 (fixed): the client gap read was unbounded.** The server 180-day-windows symptom events before collapsing; the client now applies the same `WATCHING_GAP_WINDOW_DAYS` (180) window-then-collapse, so client and server agree on "the current era" (no >180-day spanning run the server would never form).
- **5b (disclosed residual, now MEASURED): `minGaps` = 3.** The naive strict-decrease-3 fires ~16.7% by chance, but a seeded property sweep of the *shipped* detector (ratio gate + recency guard, added to `signalWatching.test.ts`) measures the actual null fire-rate at **~2.7% pooled / 3.3% worst-cell on constant-rate + uniform nulls**, and **~4.5% pooled / ~5.1% worst on autocorrelated (waxing/waning) nulls** — the class PR 8 disclosed, and the client mirror lands on PR 8's same ~5-6% residual. That is the documented sub-floor watching floor (the config comment reserves 3 gaps for "PR 7's client row"; the firing finding uses `runLength` 4). Acceptable for an escalate-only, counts-shown, no-verdict *disclosure* row (the ⑥/PR-8 "disclose the residual, assert a ceiling + a sanity floor so the test can't rot" discipline). The sweep pins pooled < 5% / worst < 6% (const+uniform) and < 8% (autocorrelated), with a >1.2% sanity floor.
