## C — Code conventions, full account

### C-1 · A category colour is a GLYPH tint; text on a light ground takes the INK (2026-08-30, CUL-578):

**A category colour is a GLYPH tint; text on a light ground takes the INK (2026-08-30, CUL-578):** `colorAccent` / `colorEventSymptom` / `colorEventMedication` are tuned for WCAG's 3:1 **non-text** target, so as small **text** they miss AA badly — teal is 2.26:1 on white and 2.08:1 on its own tint, rose 3.06:1 on its own tint. Each has an ink minted for exactly that pairing (`colorAccentInk` 5.17:1 / 4.75:1, `colorEventSymptomInk` 6.68:1, plus the medication + attention siblings). Same accent, same rose — the "one accent" rule holds; an ink is never a second colour. **But the ground decides, and a grep cannot read the ground.** `color: theme.colorAccent` appears at ~76 sites and a static scan cannot resolve an RN style cascade to say which sit on light: `Snackbar`'s teal is **8.75:1** on `colorNeutralDark` and is correct as shipped, while `colorAccentInk` there would be 1.9:1. So this class is walked per site, never swept — a mechanical repoint of all of them ships a **worse** defect than the one being fixed, under a green diff, on exactly the surfaces (night grounds, the recap's own links) where teal was right. The rule is pinned rather than remembered: `constants/theme.contrast.test.ts` holds the WCAG ratio helper and asserts **both** halves — every ink clears 4.5:1 on its ground **and the bright it replaced does not** — so repointing an ink back to the brand accent red-lights instead of being a green one-token edit. Consumption is asserted where it renders, off the **flattened style of the rendered tree** (`Badge.test.tsx`, `TrendZone.test.tsx`, `FilterChip.test.tsx`, `ScopeMenu.test.tsx`), so a node wired to the wrong style key fails even though the style block still reads correctly in the diff; the two ends are deliberately not restatements of each other. **The walk is done and the class is now GUARDED (2026-08-30, CUL-744) — `guards/accentOnLight.test.ts` fails the build** on a `color:` style key holding `theme.colorAccent` unless an inline `// accent-on-dark-ok: <ground>, <ratio>` within 10 lines above it says a human decided. The scanner still cannot resolve the ground, and does not pretend to: it requires that somebody *did*, which turns 81 undecided sites into 5 argued ones and makes a new light-ground accent label fail on the day it is written rather than in the fourth audit. Markers are per-site, never per-file — `FilterChip.tsx` declares `activeLabel` three times across three variants, two of them on dark, and a file-wide exemption there would have pre-approved the one that was broken. **Two things the sweep itself taught, both about the enumeration rather than the fix.** (1) **The grep that scoped the issue was leaky**: `color: theme.colorAccent,$` found 77, and dropping the anchor found **81** — the four extras were single-line declarations (`recLabelAttn: { color: theme.colorAccent }`), one of which was the `worth_a_call` escalation label on the stool/vomit AI read, at 2.08:1 on its own `colorAccentLight` card and the *least* legible of that card's three tones (`monitor` 7.17:1, muted 4.35:1) — the escalation read faintest, which inverts the severity ordering the plainness rule is built on. *An enumeration chosen by a grep is only as complete as the grep, and the sites it misses are not distributed randomly — they are the ones written in a different style, which is uncorrelated with how much they matter.* (2) The final tally was **76 repointed, 5 kept**, and the 5 are why a sweep would have been wrong: the ink is not "the safer teal", it is the teal for a light ground, and on `colorNeutralDark` / `colorBrandNight` it is the *failing* half (3.83:1 / 3.54:1). That inversion is pinned in `theme.contrast.test.ts` alongside the light-ground half, so a later "simplify to one accent token" pass has to argue with a ratio instead of shipping green.

### C-2 · Owner-facing text uses `ThemedText` (2026-08-22, CUL-364/CUL-605, `docs/nyx-app-polish-requirements.md` §7):

**Owner-facing text uses `ThemedText` (2026-08-22, CUL-364/CUL-605, `docs/nyx-app-polish-requirements.md` §7):** new owner-facing text renders through `components/ui/ThemedText`, never a raw `<Text>`. RN does not synthesize weights for custom fonts, so each Geist weight is its own loaded family — the wrapper derives the family from the style's `fontWeight` token (`weightRegular`→Geist, `weightMedium`→Geist-Medium, `weightSemibold`→Geist-SemiBold) so a style sheet states the weight once instead of two facts that must agree. An explicit `fontFamily` still wins (that is how `fontDisplay`/Newsreader survives), and the weight is dropped once the family carries it. There is **no default-`Text` override** (D9, the no-magic rule): a raw `<Text>` keeps rendering the system face, so the app-wide migration is a visible per-file swap (sweeps CUL-607…CUL-611) and any style sheet explains its own render. The `guards/ownerFacingCopy.test.ts` scan already covers `*Text` tags, so the swap does not move copy out of scan. **The one place a sweep must NOT swap is a nested span (2026-08-23, CUL-607):** every ThemedText injects an *explicit* family, and an explicit family on a child is exactly what breaks RN's native text-style cascade — so an inner `<Text>` that differs from its parent only in colour stays a raw `<Text>` and inherits the parent's resolved face. Swapping it mechanically ships a **face change mid-sentence**, which no test catches and no diff shows; a nested span that genuinely needs a different weight spells its own. Shipped precedent + the comment to copy: `components/history/FreeFeedingStrip.tsx`. Comment the exemption in place, naming the issue, so CUL-611's closing grep-audit meets the rationale rather than a bare violation. **Two carve-outs, both from the first sweep (2026-08-23, CUL-608).** A `<Text>` whose entire content is an **icon glyph** (`✓ ✕ ← + ＋ ›` — standing in for a vector glyph until B-745's `GlyphSvg` reaches it) is **not copy and stays raw**, keeping the system face. Checked against the shipped cmaps rather than assumed: Geist carries **no** U+2713 / U+2715 / U+FF0B in any loaded weight, so sweeping those forces a family lacking the codepoint and hands the render to OS fallback at a size tuned for a different face — a regression bought for nothing, since there is no prose on the node to gain the face. The rule is stated as *is this copy?*, not as a coverage table, so glyphs Geist **does** carry stay raw too and no one has to re-read a cmap; annotate each site, because §7's closing audit greps for exactly this shape. A **mixed** string goes the other way — `"Confirmed ✓"` sweeps, and its tick falls to fallback. Second: `Animated.Text` cannot take the wrapper, so its style sheet **names the family outright** (`fontBodyMedium`) and drops the weight — the explicit-`fontFamily` passthrough above, which satisfies the audit rather than excepting it. **A third nested shape, from the Home sweep (2026-08-23, CUL-610): a span carrying no style at all** — one that exists only to hold a `key` — becomes a **`Fragment`**, not a ThemedText. It has nothing to inherit *and* nothing to express, so a wrapper there injects the regular face over whatever weight the sentence around it carries. It renders identically while the parent is regular, which is what makes it a trap rather than a bug: it arrives later, in an unrelated diff, the first time the parent gains a weight (`components/home/TodayZone.tsx`). **And one thing the wrapper cannot reach:** it wraps `Text`, so a **`TextInput`** takes an explicit `fontFamily: theme.fontBody` on its style instead — a swept screen whose fields still render the system face is the half-done look the rollout exists to remove (shipped shape: `app/settings/feedback.tsx :: noteInput`). **The rollout closed 2026-08-24 (CUL-611) and is now GUARDED, not remembered — `guards/geistRollout.test.ts` fails the build** on: a raw `<Text>`/`Animated.Text` with no resolvable explicit family, a `<TextInput>` with none, a nested node that loses its weight (below), and a style block naming a family and a *disagreeing* weight (CUL-652 — the class a grep for `<Text>` is structurally blind to, since the node IS swept and still renders wrong). It parses the AST rather than grepping, which is what makes prose about the rule un-mistakable for the rule in **both** directions — a `fontFamily` in a comment can't satisfy it, a `<Text>` in a comment can't violate it. Exemption is an inline `// geist-ok: <reason>` within 10 lines above the site, and **one marker covers exactly one site** (otherwise one annotated glyph exempts every sibling near it and the file reads as reviewed). **The finding that generalises past this rollout: under a parent carrying an explicit family, a child's `fontWeight` is INERT** — RN won't synthesize, and the family the cascade hands down wins. So sweeping a parent silently flattens every weight contrast its children asked for; ten shipped that way (`12.4 **lbs**`, `37% *finished*`, the paywall's `/yr`) and none of it shows in a diff, because the child was never touched. Hence the split the sweeps now follow: a nested span differing only in **colour** stays raw (it *should* inherit); one carrying its own **weight** goes to `ThemedText` if it is copy, or spells `fontFamily` on its style if it is a glyph (`components/onboarding/ValuePreview.tsx :: vDown`). A `geist-ok` marker never excuses this — it says a node is deliberately raw, never that it deliberately renders the wrong weight.

### C-3 · A COMPLETENESS ratio beside a PARTIAL enumeration is a claim about the enumeration (2026-08-30, CUL-62):

**A COMPLETENESS ratio beside a PARTIAL enumeration is a claim about the enumeration (2026-08-30, CUL-62):** where a surface lists some class of thing over a span and then states how completely that span was tracked, the density is read as vouching for the *list*, not for the span — whatever it is a ratio of. The vet report's trial block discloses the trial days a window crops; a cold read ruled the bare count unreadable without a denominator (the page's own legend promises *"a count is never read without knowing how long and how completely it was tracked"*, so the omission was a **contradiction**, not a gap — and being told a rule then denied it stops a reader looking for the qualifier). The obvious fix, *"Meals were logged on 42 of those 42 days"*, then failed the adversarial pass on the patient the report exists for: a cat whose 42 cropped days held **42 refusals of the prescribed diet and 42 off-diet feedings**, none of which any count on the page can reach, where the clause enumerates only symptoms. Before the change that record said "42 trial days fall before it" and admitted a hole; after it, it told the reader the hole was **filled**. So the density renders **only the un-logged days** and nothing when the span is fully covered: silence can then mean "no caveat to add" but never "the record is complete", and the sentence can only move a reader toward doubt. Two rules travel with it. **(1) The scope goes where the reader meets the claim, not only in the legend** — a legend saying the section "names what was logged" is an unrestricted universal over a symptoms-only clause (CUL-69's rule (3) again); say what the disclosure *holds*, and name what it does not reach. **(2) A coverage fact is not an absence claim, so do not gate it on the thing being counted** — gating the density on the symptom count rendered "42 days nobody logged" and "42 days logged and genuinely quiet" identically, as nothing, and suppressing a coverage fact is the reassuring direction. **And the predicate must be the one the neighbouring sentence uses:** counting any `event_type='meal'` beside a coverage line that excludes treats put two scales in one row twelve words apart — `lib/dietTrial.ts` states in place that *"on live data 82% of feedings are treats, so a 'days with food logged' count is clearable entirely by treat data"*, so a stretch of nothing but dental chews rendered as fully tracked. Both reviewers found that one independently, which is the tell that a shared predicate was owed (§5.3). **The session-level lesson, and it is the same one four rounds of CUL-69 produced: the deletion held and the additions did not** — the core change survived every attack, and both blocking findings were in material added to satisfy the *previous* review. Also: three of sixteen mutations exposed guards that did not discriminate, including one that set the field under test directly on a snapshot fixture, so it exercised the renderer and was blind to assembly dropping the value — **a guard has to start where the fact does**. **The sibling shape, one layer simpler (2026-08-30, CUL-223): a COUNT spoken as a fact about the record must not be derived from a DISPLAY WINDOW.** Both weight cards rendered `readingCount` — read as "this pet has N weigh-ins" — from `getWeightHistory(petId, 12)`, so a pet with 20 read "12 readings". Harmless-looking while the count was terminal, and false the moment it labelled a tap-through to all 20: *a number that labels a destination must count what the destination holds.* The window itself was right and stayed (a long history shows its latest shape, never an ancient prefix), so the fix is a second read, never a wider one. **And when the two numbers meet in one function, keep them in separate variables** — the natural edit makes the total the loop bound as well as the spoken value, and the same identifier is also the array index (`seriesLbs[count - 1]`), so a total of 20 over a 12-row window reads `undefined` and then throws. State it where it can be read: the window is the only thing that may INDEX, the total the only thing that may be SPOKEN. **A third rule for the mutation discipline, from the other side: a mutation that does not change behaviour has not tested the guard.** A "renders no touchable when there is nothing to open" test stayed green under a `disabled`-node mutant — not because the test was weak, but because the branch it mutated was unreachable (the card's empty state never renders that component). Re-run as a reachable defect it went red. Check the mutant actually executes before concluding anything about the test.

### C-4 · Two counts over ONE population, described as independent, are a claim — and PRECEDENCE is the only honest resolution (2026-08-30, CUL-746):

**Two counts over ONE population, described as independent, are a claim — and PRECEDENCE is the only honest resolution (2026-08-30, CUL-746):** where a surface reports a set under two reasons, the reasons must partition it. The vet report's trial block printed a rung breakdown and then appended the dated-membership count as a trailing "also", on the strength of one docstring sentence claiming `fedBeforePermitted` was *"orthogonal to the two rungs and not counted by either"*. It never was — only rungs 2 and 3 ever set `offDiet`, so every dated-membership row is inside `byRung` too — and the same seven feedings were reported twice, with the misleading half leading in bold: *"7 were not recognised as trial food … 7 were also fed before that food was permitted"* over seven feedings of the PRESCRIBED hydrolysate, on a trial started Apr 21 whose `diet_trial_foods` row is dated Jun 1. A vet reads 88% non-compliance off a record that is the best evidence the owner complied, and C6 makes this the one figure on the report that judges a person. Appendix C had stated the precedence correctly since round 4; page 1 never got it, and round 5 had "fixed" the resulting cross-check ADDITIVELY. So the rule lives in one function (`exposureReasonOf`) that both surfaces switch on — *inverting it must red both pages' guards together, which is the only proof a rule is shared rather than duplicated* — and the counts are taken by MOVING rows out of their rung (`exposureBreakdown`, consumed by the sentence and the At-a-glance tile alike) rather than re-counting them, so the clauses partition the total by construction and no breakdown can fail to add up to the number in its own sentence. **Four rules generalise past this surface.** **(1) A fix that lands on the reassuring branch and not the accusing one is a shape to hunt for.** The tile's missing date span was a *known, already-fixed* defect — repaired on `mayStateRecordClean` (which reassures) and left open on `offDiet > 0` (which accuses), with the reason written in the repaired branch's own comment. B-529's three-route rung-3 copy is the identical shape and is still live on page 1 (CUL-759). *When you close a defect on one branch of a two-branch surface, check the sibling before closing the issue — and fix the accusing side first, because that is the one that costs a person.* **(2) First-member-wins on a grouped row is a defect with a DIRECTION.** `groupConfounders` took `permittedLaterFrom` from whichever member created the group, and that is not random: a row's candidate permission dates are the ones *after* it, so the earliest member's candidate set is a superset of every later member's, and the rows are date-sorted — the group is therefore always created by the member most likely to be **excused**, and its excuse applied to the rest. A treat permitted Jun 10–12, fed Jun 5 and Jun 20, rendered one row reading *"Fed before it was permitted (allowed from Jun 10) ×2"*, excusing a feeding made eight days after the permission ENDED. Two sibling fields already carried comments saying first-member-wins was a defect; this was the third instance and nobody had named it. *Any field that decides a row's stated reason joins the group key.* **(3) Precedence DELETES the losing reason, so the winning one must be true.** Once the date outranks the rung, the date is the page's only statement about that row. `permittedLater` scanned only `allowedFrom` dates AFTER the feeding, so it could not see an earlier membership that had been WITHDRAWN (§7 supports withdrawal as well as addition) — and a feeding inside that gap, the owner feeding something the vet had just removed, rendered as the innocent bookkeeping case with the true clause deleted from beside it. An earlier permission now disqualifies the reason outright, asked of the one predicate in both directions. *Before making a reason outrank another, establish the loser is the misleading half and not merely the later one.* **(4) WHERE THE RECORD CANNOT SETTLE A QUESTION, THE PAGE MUST NOT ANSWER IT — and four falsification passes were the cost of learning that here.** *"Fed before it was permitted"* is true of the record and reads as a compliance breach, and for the trial's own primary diet it cannot describe one. Two rounds therefore tried to say more: name the food (*"feedings of the trial diet itself"*), then characterise it (*"a gap in the record, not a departure from the diet"*, borrowed from the Antigen-check-paused row). Both were reverted, because `allowed_from` records when a row was **entered** and nothing in the record separates *the app's record started late* from *the vet switched the diet* from *the vet withdrew it*. Each version asserted one and was falsified by another: a **mid-trial primary-diet switch** made the noun false (on those days the trial diet was the OTHER food, and the same page tallied this one's protein as one the trial diet does not contain); an explicitly **withdrawn** earlier diet made the register false; a **mixed set** made page 1 and appendix C disagree about which reading applied — this issue's own defect, re-created by the fix meant to close it. The clause now says only what holds in every shape, in appendix C's exact words, and the counterexample is kept as a standing guard. Whether those rows belong in the off-diet NUMERATOR at all is a change to the shared `lib/dietTrial.ts` predicate the card and `ask` also read, so it is a Dr. Chen ruling (CUL-758), not a render fix. **Three things generalise from the arc.** *A closure can fail by moving the defect one word left* — round 2 fixed the clause the switch falsified and kept the noun, which was the exonerating half, and its own commit message quoted the contradiction it left standing. *A per-row rule and an all-or-nothing rule are not "one rule, two consumers"* — giving appendix C a per-row register while page 1 kept `early.every(...)` is the same duplication, relocated. And *the stopping rule is already written down*: findings at **3 → 6 → 6**, with ten of the last twelve caused by the fix before them, is the non-convergence the § Git Workflow review rules name, and the answer is to stop patching and put it to the PM — a borrowed register is especially prone to this, because borrowing the WORDS is not borrowing the MODALITY (the source sentence declines to make a finding; the copy made one). **And two testing rules the session paid for.** **A guard containing `.*` is not a guard:** `/Feedings not matched to the trial diet.*Jun 1 – Jul 2, 2026/` passed with the tile repointed at the coverage range, because `.*` bridged 400 characters into the PROSE sentence's copy of the same range — green over the exact defect it was written for, in the fix that cites CUL-613. **Slice the object under test and anchor the match; never match across the document.** Fifteen mutations were run; two of them caught defects in the *guards* rather than in the source, which is the ratio that justifies the discipline. **And a review subagent shares your working tree** — `code-reviewer` made three in-place mutations for its own mutation-testing while this session was mid-edit, clobbering two uncommitted changes and leaving one line altered; nothing was lost, but the failure is silent and reads as your own mistake. *Tell a review subagent in its prompt to `cp -r` the tree into `/tmp` before mutating anything, and snapshot before launching one.*

### C-5 · Adjacent controls must not share hit area (2026-08-23, CUL-612):

**Adjacent controls must not share hit area (2026-08-23, CUL-612):** two touchable siblings in a row need `gap >= hitSlop.facing(a) + hitSlop.facing(b)`, or their expanded rectangles overlap and a tap near the boundary resolves by **z-order**, not by intent. The 44pt floor and `hitSlop` solve *reachability*; neither solves *ambiguity*, and an overlap is invisible in a screenshot — so it is asserted in a test, never left to the device pass. Where the gap is tight, prefer **asymmetric `hitSlop`** (`{top, bottom, left, right}` — each control keeps its outward and vertical reach and yields only the edge facing its neighbour, half the gap each) over widening the row, which spends layout width the content usually needs. The shipped pair is `HITSLOP_ACTION_LEFT` / `HITSLOP_ACTION_RIGHT` in `lib/completionCard.ts`. **This matters most where one of the two is destructive and unconfirmed**: on the completion cards a mistouch aimed at "Change time" resolved to "Undo" and silently removed the log, because §5.6 makes that tap its own destructive confirm. **Pick the tool by the geometry, not by habit (2026-08-24, CUL-579).** `hitSlop` spends gap, so it is only correct where there is gap to spend: on controls that sit **flush** (the FAB menu's stacked rows, a segmented control's two halves) it manufactures the overlap above, and on a control **already at the floor** it buys no reach at all and only reaches into its neighbour's. There the fix is the opposite — **grow the box** (`minHeight`, as `menuAction` and `logForChip` do) or **delete the slop** (the three `radioRow`s, which were 44pt already). A wrapping row needs both gaps considered separately: `AdherenceChipRow` splits its single `gap` into `columnGap`/`rowGap` because vertical slop is shared between wrapped *lines*, which is the same defect rotated 90°. And **pin whatever geometry the floor depends on**: a claim like "32 + 6 + 6 = 44" that rests on a rendered font line box is unassertable — jest cannot compute it — so the box gets an explicit `minHeight` and the arithmetic becomes true by construction, which is what keeps a later type or weight change from silently dropping the control back under the floor. *A tap-target floor resting on a metric no test can compute is a floor nobody is holding.* **And the assertion reads the RENDERED geometry, never a token restated in the test (2026-08-29, CUL-621).** A gap test written as `expect(a + b).toBeLessThanOrEqual(theme.space3)` is not asserting the row — it is asserting that two constants the test itself names still add up, and it passes forever after someone narrows the actual `gap`. Walk up from the control to the row and read its flattened style (`TimeEditSheet.test.tsx :: actionRowGap`), so the thing under test is the layout rather than the arithmetic. Same failure shape as the `minHeight` rule above, one level out: there the floor rested on a metric no test *could* compute; here it rested on one the test *declined* to read. **And growing the box can SPEND the gap the rule needs (2026-08-29, CUL-618).** The two halves interact: moving a neighbouring `marginTop` into the grown box is the natural way to keep a card's rhythm while adding a `minHeight`, and it silently subtracts that margin from the gap the CUL-612 arithmetic depends on — on the Pet-tab name it dropped 12pt to 8 against a `hitSlop={8}` sibling, leaving the rule satisfied only by **exact equality**. Abutting is not overlapping, so nothing was broken and nothing would have failed; but equality is one spacing edit from a defect, and the in-place comment still claiming "12pt" had quietly become false — the thing a later reader would trust. So **re-check the neighbour's arithmetic AFTER growing a box, not just before**, and keep the margin that buys the headroom. **And an auto margin is NOT evidence of a gap (2026-08-29, CUL-688).** The rule's `gap` term has to be read off the resolved layout, not off the style sheet: flexbox gives flexible lengths to `flexGrow` items *before* it distributes what is left to auto margins, so a `marginLeft: 'auto'` next to a `flexGrow: 1` sibling resolves to **zero** and the two controls sit flush. On the confirm sheet that put 8pt of the `Saw it` chip inside the Change-time control, which carries no slop of its own to yield back — a control that opens the time picker resolving to one that reclassifies the event. Nothing in either style block says "flush"; the word that looked like space was `auto`. So when a neighbour grows, treat the gap as zero until you can name what holds it open. **Derive the slop from the gap it must fit inside, on BOTH axes, and guard each bound the value has.** `SimpleEventConfirm`'s chips compute their facing reach from the one `CHIP_PAIR_GAP` the style also reads, and their vertical reach from `CHIP_ROW_GAP` — `timeRow`'s `rowGap`, which is all that separates the pair from the row above once it wraps. Written as two independent `8`s that held by *coincidence*, and narrowing the row's gap would have reopened the defect **in the wrapped state alone**, where no test was looking. That reach is bounded on both sides at once (≥6 to keep a 32pt pill over the 44pt floor, ≤ the row gap to stay out of the neighbour), so **both** bounds get a guard: mutating the value red-lights exactly one of them, and a token change that makes them incompatible fails the build instead of silently picking a side. **And a LAYOUT change changes the ADJACENCY MAP, so a reach derived for the old map does not survive it (2026-08-30, CUL-756).** That same wrap had a third state nobody had written down: the pair is *itself* wider than the line it drops onto at accessibility text sizes (389pt against 256pt at AX5, measured off the shipped `Geist_500Medium` advances), and with `flexShrink: 0` all the way down the overflow left the sheet — `Found it` clipped, on the control that decides `occurred_at_confidence`. Fixing it means `chipPair` wraps too, so the chips **stack** — and that creates a vertical adjacency **that did not exist when `CHIP_REACH` was derived**. The natural implementation, reusing `timeRow`s 8pt `rowGap`, puts 8pt of each chip reach into the other: CUL-688 own defect rotated 90°, on the same classifier, arriving as a **side effect of repairing something else**, with nothing failing and the layout genuinely fixed. So the new separation is derived (`CHIP_STACK_GAP = CHIP_REACH * 2`) and the single `gap` is split into `columnGap`/`rowGap`, because one `gap` silently drags the stacked separation down to the 4pt facing value. *The test to apply: after any change that lets a container wrap, re-enumerate which controls now face each other — the pairs are no longer the ones the original arithmetic was written against.* Two rules travel with it. **(1) A dead property that LOOKS like it does the job is worse than none.** `chipPair`s `marginLeft: auto` had been inert since the row gained `flexGrow` — the very fact the CUL-688 clause above relies on — so it read as the thing right-aligning the pair while doing nothing; left beside the real `justifyContent: flex-end` fix, the next reader deletes the fix as the redundant one. Replace it, never keep both. **(2) A wrap only TERMINATES if a single child fits** (here 214pt against a 256pt line). Check that before choosing to wrap: if one child alone can overrun, wrapping relocates the overflow instead of resolving it, and the fix is the wrong shape however correct it looks. Both were settled by compiling React Native own Yoga out of `node_modules/react-native/ReactCommon/yoga` and running the real tree through it, because jest has no layout engine and a style assertion cannot tell a wrap that resolves from one that does not — which also falsified the expectation that `flexShrink: 0` would defeat the wrap (Yoga clamps the item to its line, so no `maxWidth` crutch is wanted here, unlike CUL-726 leaf-`Text` case).

### C-6 · `fireEvent.press` cannot prove a region is tappable (2026-08-24, CUL-579):

**`fireEvent.press` cannot prove a region is tappable (2026-08-24, CUL-579):** RTL-RN's `press` does **not** merely bubble — given a node with no handler above it, it can still reach one by **descending from an enclosing composite element**. So pressing an inert label that happens to share a wrapper component with a button fires that button, and the test passes over exactly the defect it was written for. This is not hypothetical: it is how the first `TimeConfidenceField.test.tsx` went green against the unfixed tree. To assert that a particular region is touchable, walk **up** from the text to its nearest responder host and compare **node identity** (`owningTouchable(label) === owningTouchable(value)` for "the whole row is one button"; `!== null` for "this is in a button at all"). Identity cannot be reached by descent, so it discriminates where a synthetic press does not. This is a specific instance of the CUL-613 rule — run a new guard against the tree it was written for — and the reason that rule keeps earning its place.

### C-7 · `disabled` is an accessibility CLAIM, not a way to hide chrome (2026-08-30, CUL-682):

**`disabled` is an accessibility CLAIM, not a way to hide chrome (2026-08-30, CUL-682):** RN copies a touchable's `disabled` into `accessibilityState.disabled` (`TouchableOpacity.js`), and iOS turns that into `UIAccessibilityTraitNotEnabled` — which VoiceOver speaks as **"dimmed"**. So `disabled` asserts *this control exists and is currently unavailable*. Where that is true, it is right, and it should be **paired with a label saying why**: `app/settings.tsx`'s Coming-soon rows keep `disabled` and swap in `'Privacy policy — coming soon'`; `DocumentHero` keeps `accessibilityRole="button"` and swaps in `'This document needs a connection'`. The defect is using it where the control **does not exist for that state** — the log sheet's title row was one `TouchableOpacity` with `disabled={!multiPet}`, so a one-pet household was told the pet switcher was unavailable on a row that has no switcher at all, and the row stayed a focusable responder while inert. **The tell is that the chrome is suppressed in the same breath:** if the branch also drops the chevron, the arrow, the affordance, then there is no control to call unavailable, and one prop is doing two jobs that are not the same act. The fix is to **split by host** — the interactive branch keeps the touchable, the inert branch is a plain `View` — because a state that renders no affordance should not render an interactive node either. **Every known instance is now closed (2026-08-30, CUL-728) — and the 85-site sweep that found two had missed a third**, `app/trial-exposures.tsx`, beside `components/ask/RundownTileRow.tsx` and `components/food/PhotoCarousel.tsx`'s empty hero. **The miss is the part worth keeping:** the two the sweep caught announce a *contradiction* on the element (`accessibilityRole={x ? 'button' : 'text'}` beside `disabled`), and that is what a grep finds. The third dropped the role **and** the label in its inert branch, so nothing disagreed with anything and `disabled` was left as the only claim on the node — invisible to a search for the contradiction, and sitting on the diet-trial rows that already carry the least explanation. So read the *branch*, not the disagreement: **the question is whether a control exists in that state, and a branch that answers no while still rendering a touchable is the defect whether or not anything else on the element says so.** And when the inert branch carries a label, it needs **`accessible`** on the `View` or the label never applies: the disc and the sentence stay two separate stops — a fix that looks present in the diff and does nothing on the device. (This entry originally also claimed that second stop reads the *ellipsed* string. It does not — see the next rule, which falsified it. The grouping is the whole reason the label is needed, and it is reason enough.) That half is a **regression the split itself introduces**, not merely an omission — a touchable is `accessible` by default, so a row of two or three `Text` nodes that announced as one sentence silently becomes three unrelated stops the moment it becomes a `View`, and nothing in the diff or a screenshot shows it. Finally, while splitting, fix the **mirror** defect in the same branch if it is there: a real button that never announced its role (both of `PhotoCarousel`'s add-photo affordances). Give it `accessibilityRole="button"` and **no invented `accessibilityLabel`** where its visible line already reads correctly — a label that differs from the words on screen is one Voice Control cannot be told to tap. Add one only to drop a leading glyph from the announcement (`'Add another photo'`, not `'＋ Add another photo'`).

### C-8 · A truncated `Text` still announces its FULL string — visual truncation is never an accessibility defect (2026-08-30, CUL-726):

**A truncated `Text` still announces its FULL string — visual truncation is never an accessibility defect (2026-08-30, CUL-726):** `numberOfLines` + an ellipsis is a *layout* result; it never edits the string the screen reader reads, on either platform. **iOS** — `Text` is accessible by default (`Libraries/Text/Text.js:145`, `accessible !== false`), and `RCTParagraphComponentAccessibilityProvider.mm:60–68` builds the first element's label from `_attributedString.getString()`, the whole string, with the reason written in place: *"add first element has the text for the whole textview in order to read out the whole text."* **Android** — `ReactTextView.java:382`/`:439` are `setMaxLines` + `setEllipsize`; the full `Spanned` is what `setText` receives and what `TextView.getText()` — the thing TalkBack reads — returns. So **adding an `accessibilityLabel` to "rescue" a truncated string is a placebo**: it changes nothing announced, and it closes the issue while leaving the real defect in place, which is worse than leaving it open. Check the same way before writing one: `react-native-svg` ships no accessibility props either, so a glyph disc beside the text is not a separate stop, and a label on the parent buys no grouping it did not already have. A label is still right when it says something the visible text does **not** (`Log for Nyx — switch pet`), or when a wrapper genuinely needs to become one node — that is CUL-682's shape, and only its *stated reason* was wrong. The converse is where a label becomes mandatory, and CUL-726's own fix is the case: **splitting one `Text` into two fragments the announcement**, so a label is what rejoins them — the same regression the entry above describes for a touchable becoming a `View`, arriving from the other direction. **What a truncated string does cost is the reader who can see it**, and that is a layout question: nothing outside the tab bar sets `allowFontScaling={false}`, so a 17pt header at xxLarge — a comfort setting, not an accessibility one — already cuts an 11-character pet name. When a compound string must give something up, the part that yields is decided by **how many times the surface says each half**: on the log sheet's confirm header the type is stated three times (the disc, the header, the summary pill that IS the save) and the pet exactly once, so the ellipsis was eating the only statement of write-time identity. One shape note for the fix, because the obvious pair does not compose: **`numberOfLines={2}` and "the type shrinks first" are mutually exclusive** — wrapping needs one paragraph, `flexShrink` needs two flex children, and nested `Text` spans are inline so they cannot carry it. The composition that delivers both is already shipped one row below (**AC-CHIP**): the row wraps, the yielding half is `flexShrink: 1`, and the protected half is `flexShrink: 0` **plus `maxWidth: '100%'`** — without the max-width it overflows instead of ellipsing when it alone overruns its line.

### C-9 · A record-scoped surface names the RECORD's pet, never the active one (2026-08-24, CUL-574):

**A record-scoped surface names the RECORD's pet, never the active one (2026-08-24, CUL-574):** any surface displaying one record — an event, a dose, a document, a queued completion payload — resolves its display name with **`resolveRecordPetName(pets, record.petId)`** (`store/petStore.ts`), never off `usePetStore().activePet`. The screens reached BY ID are the trap: the multi-pet day-summary spine pushes `/event/[id]` for *every* pet's rows, and deep links and notifications do the same, so the active pet is not an answer to "whose vomit is this?" — the pre-fix screen captioned Juniper's AI read *"If **Pixel** keeps vomiting or seems off, don't wait for the read"*, an instruction to watch the cat that isn't sick, on the highest-stakes copy in the app. The predicate is deliberately one (there were six hand-rolled `pets.find` variants carrying three different fallback ladders), and it carries two rules a caller must not re-derive: a **blank name counts as a miss** (callers interpolate into a sentence, and `''` renders a hole), and there is **no `activePet` rung** — `pets` holds only non-archived pets, so an archived record's `find` misses, and falling back to the current selection is the exact mis-attribution the lookup exists to prevent. **That rung is never a graceful degradation, and the proof generalises past pet names:** every store mutator keeps `activePet` a member of `pets`, so the fallback could only fire when the record's pet was *not* in the list — which entails it was not the active pet either. It was wrong 100% of the times it was taken. *A fallback to "the current selection" on a surface scoped to a record is not a fallback; it is a different, confidently-stated answer to a question that was already asked correctly.* Prefer **deriving** the name in the render body over mirroring it into `useState` — a screen that resets per-record state on navigation (`app/event/[id].tsx`'s `loadAll`) would need to remember an eighth reset, and a forgotten one flashes the previous record's pet. Residual sites are tracked, not assumed clean: CUL-626 (`MedicationCompletionCard`), CUL-659 (`NamedCompletionCard`). A companion rule from B-550/CUL-660 that this does *not* satisfy: correct-but-anonymous is better than confidently wrong, and still not right — a record screen in a multi-pet household should also **say** whose record it is.

### C-10 · A defaulted timestamp is the app's claim, and a displayed one is a promise (2026-08-24, CUL-576):

**A defaulted timestamp is the app's claim, and a displayed one is a promise (2026-08-24, CUL-576):** a capture surface that seeds `occurred_at` from the clock writes **`occurred_at_source: 'now'`**, never `'manual'`. Migration 007 defines `'now'` as *"was auto-stamped to `now()`"*; `'manual'` asserts a **human chose** this timestamp, and on the symptom/weight paths nobody had — the app did, at mount. That column is how the vet report and the correlation engine tell a witnessed-now log from an owner backfill, so mislabelling it is a record-fidelity defect even when nothing renders differently. B-525 fixed the mirror image (a picker edit keeping a stale `'now'`); `sourceAfterPointEdit` is still the one thing that turns the app's claim into the owner's, and **as of CUL-701 every point-time edit in the app routes through it** — the four capture/edit surfaces and all three completion cards. **The cards were the holdouts, and the reason generalises: their Save is live the moment the sheet opens, so a peek that scrubs nothing is a real gesture** — "tap Change time, look at the wheel, tap Save" was enough to stamp `'manual'` over a time the app had stamped itself. An affordance whose commit action is armed before the owner has done anything must treat *doing nothing* as a distinct answer from *doing something*, or every glance becomes an assertion. On the meal card that cost more than a false claim: `insertMeal` takes the source as a **parameter** and both photo paths fill it from a food photo's EXIF stamp, so the peek **destroyed** the attribution (`insertMedicationDose` hardcodes `'now'`, so the dose card really did only mis-claim — the issue's premise held for one card and not the other, which is why it is worth checking rather than assuming). **The staleness half is where the intuitive fix is wrong.** The clock default goes stale while a surface sits open, but the repair is to **re-derive it on re-entry** (`refreshedNowPoint` — returning from a photo picker, the app foregrounding), *never* to re-stamp at save. Two reasons, and both are properties of the surface rather than of the clock: **(1)** if the value is **on screen** — the `/log` time row, the B-745 confirm's summary pill, which its §0 makes *the save* — then re-stamping commits a number the owner was never shown; **(2)** an adverse event is logged **because it just happened**, so the screen opens *after* it and every passing second moves the clock *away* from the event. Mount is the better proxy for a 5:33 vomit; save is the worse one. The meal one-tap path may re-stamp for exactly the reason it states in place — *"the user never saw the time picker"* — so it is a **counterexample, not a precedent**, and copying it onto a surface that displays its time is the mistake CUL-576 was originally filed asking for. Only a `'now'` point ever moves: an owner-set time and an EXIF stamp both outrank the wall clock, and a *later* bound on the `found` path is a **weaker** claim, so window edges (`foundLatest`, `estimatedAt`) are deliberately left alone. One consequence worth knowing before it bites: once the clock can move, **a draft-dirty check keyed on the timestamp starts firing on its own** — CUL-612's discard guard now compares the *source*, so an assumption the app re-derived is not mistaken for the owner's work. **And the column is REQUIRED on `updateEvent`, deliberately unlike the optional-by-omission fields beside it (2026-08-29, CUL-708):** `severity`, `notes` and `confidence` preserve on omission because none of them describes the field the call always writes — but `occurred_at` *is* written on every call, and `occurred_at_source` describes who produced that value, so silence has no safe meaning in **either** direction. Defaulting to `'manual'` asserts an owner choice on a save that may have changed nothing (CUL-701); defaulting to *preserve* is not its safer mirror but a second defect — a caller omitting the key while **moving** the time leaves a clock-stamped row still claiming `'now'`, which is B-525, and B-525 shipped. So the caller answers and the compiler asks; there is **no runtime fallback behind the type**, because a default there is the same trapdoor one layer down. *The generalisable test: a field is only safely optional-by-omission if it is independent of what the call unconditionally writes — where it describes that value instead, silence is a claim, and the fix is to require it rather than to pick the less-bad default.*

### C-11 · Symptom-key lists are discovered, decided, and guarded (2026-08-28, CUL-676 W1-PR-3a):

**Symptom-key lists are discovered, decided, and guarded (2026-08-28, CUL-676 W1-PR-3a):** any array/Set/Record enumerating ≥3 symptom leaf keys, anywhere in the codebase, must be registered in `guards/symptomLists.test.ts` AND carry an explicit per-leaf decision row in the §13a membership walk (`constants/eventTypes.membership.test.ts`) — the guard **fails the build** on an unregistered list (comment-stripped scan, any quote style, Record-key form included; exemption via an inline `// symptom-list-ok: <reason>`, reason mandatory). The failure mode this closes is SILENT PARTIAL MEMBERSHIP — a leaf that tints on Home while being invisible to the widget, uncountable by Ask and unfilterable in History; nothing errors, the record is just quietly thinner per surface — and enumeration alone could not hold the line: the 2026-08-27 review found three unlisted lists in thirty minutes, and the guard's own first run found two more no review had named (`generate-report/render.ts`'s label switch, `analyze-stool`'s context set). Two limits to know: a **transitive consumer** (imports a list, declares no literals) is invisible to the scan — name it in the walk row of the list it rides on (the `dietTrialOutcomeFacts`→completion-sheet precedent); and registration without a walk row is half-registration — the walk is where the per-leaf decision lives, and a blank is an unfinished decision, never a default.

### C-12 · A read that hasn't answered is never an empty record (2026-08-24, CUL-575):

**A read that hasn't answered is never an empty record (2026-08-24, CUL-575):** a surface that reads local storage has **three** states below "has rows", not one — a **skeleton** while the read is in flight, an **error + retry** when it failed, and the designed **empty state** only once a read actually answered with nothing. Collapsing them means the app asserts *"nothing logged"* over a read it never completed, which on a health record is a false record fact and reads as an invitation to start logging to an owner who has months of it. `app/day-summary.tsx` refuses this in as many words; History fell into it for the same reason every list does — an empty array is the natural fallback for both "no rows" and "no answer". **A `loading` flag alone cannot carry it:** it starts `false` and flips inside the focus effect, so the very first frame is `rows=[] && !loading` — the empty state — which is why the shipped shape pairs it with a `loaded` ("a read has answered") flag, itself gated on there being something to wait for. Shipped precedent: `app/(tabs)/history.tsx` + `app/(tabs)/foods.tsx`; the row silhouette is `SkeletonRow`/`SkeletonRows` (`components/ui/Skeleton.tsx`), hidden from assistive tech so a screen reader reaches the real rows when they land. **The same rule downward, for writes: an optimistic rollback restores every store it touched, and re-checks the pet before it does.** History's failed delete restored the list but not `todayEvents`, so Home went on hiding an event that is still in the record (Home reloads Today on mount and on a hydration tick, *not* on focus — "the next read" can be hours). And a rollback that lands after a pet switch is the **wrong-pet class**: `todayEvents` is one global list scoped to whoever was active when it loaded, so the restore reads the active pet **fresh from the store, never from the closure** — the closure still holds the old pet and would pass the check wrongly. A failed write is also always *said*: the row reappearing under the owner's finger with no message is the app looking broken at the moment it is being careful.

### C-13 · A value returned before its write has landed is an INTENT, and its name must say so (2026-08-30, CUL-699):

**A value returned before its write has landed is an INTENT, and its name must say so (2026-08-30, CUL-699):** a deliberately fire-and-forget write — the snapshot reconciles, the cosmetic patches — cannot report whether it took, because its verdict is a row count that arrives *after* the function has returned. So the return is named for what it means to be: `reconcileWeightSnapshotAfterDelete` handed back `{ petId, snapshotKg }` even when both of its gates refused and nothing was written anywhere, and that shape reads as *"this is what the snapshot now is"* — now `intendedSnapshotKg`. Returning `null` on the one gate that IS synchronous is not the safer alternative but the opposite false claim: the gates are independent by construction, so a refused local patch says nothing about the server write beside it, and a caller would read "nothing happened" over a correction that landed. **Why it survived a well-covered function: no test asserted the return in the REFUSED case** — a shape exercised only on the happy path can assert whatever it likes, and mutating the source per CUL-613 red-lighted exactly one test, the one written that day. Same family as CUL-708's *silence is a claim*, one layer out: there the caller had to answer because the field described a value the call always writes; here the function must not answer more than its own write can confirm.

### C-14 · A component already inside a `Modal` never presents another one (2026-08-26, CUL-662):

**A component already inside a `Modal` never presents another one (2026-08-26, CUL-662):** presenting a second RN `Modal` while one is up from the same presenter is unreliable on iOS — the inner one fails to present or presents detached, its `visible` state sticks `true` with nothing on screen, and if the host dropped its scrim for the newcomer's benefit, nothing is left to tap. The beta log sheet shipped that way and **wedged the app until it was force-quit** for every multi-pet account. A surface reusable in both positions splits: a **panel** (the content, no presentation of its own) plus a thin `Modal` **wrapper** for hosts that present from the root. `PetSwitcherPanel` / `PetSwitcherSheet` is the shipped shape; `HomeHeader` and the FAB keep the wrapper because the FAB's menu is an in-tree overlay, not a Modal — **which is why copying a guard off the FAB was the original mistake.** Two things a layer does not inherit and must state for itself. **(1) Assistive-tech containment.** iOS makes a presented Modal's siblings inert for VoiceOver; a layer gets none of that, so the panel declares `accessibilityViewIsModal` and the host sets `importantForAccessibility="no-hide-descendants"` on its own content (that half can only come from outside the panel). Without both, a screen reader walks the surface *behind* the scrim — on a capture surface that is the wrong-pet class (CUL-574) arriving through the accessibility tree. **(2) Anything the layer navigates to.** A pushed screen renders *behind* an RN Modal, so a row that calls `router.push` must tell its host to dismiss too (`onNavigateAway`), or the tap visibly does nothing. Note this second one is *created* by the fix: while the layer never presented, its rows were unreachable. **A layer that animates itself needs the reset on the way OUT, not just the way in** — it stays mounted between opens, so its `Animated.Value` survives holding the end state, and a passive effect runs *after* paint, so the second open paints one frame fully-open before snapping back to replay. It looks perfect the first time, which is what hides it. **What a component test can prove here is the structure, never the presentation:** jest renders two Modals happily, which is how this shipped past a well-covered component. So the guard is *exactly one Modal, layer open and closed* — and, per CUL-613, it was run against the pre-fix tree and confirmed red (2 visible Modals) before being trusted.

### C-15 · A shared surface reused by a capture host drops whatever LEAVES that host (2026-08-29, CUL-678):

**A shared surface reused by a capture host drops whatever LEAVES that host (2026-08-29, CUL-678):** the pet switcher is one component on four hosts, and the two management rows it carries — `Add a pet`, `Archived pets` — are right on the Home header and the Pet tab (the household's roster, edited from a screen about the household) and wrong on the log sheet and the FAB menu, where they are account admin standing where the owner came to record something. **Both rows leave**: the host closes, and `Add a pet` additionally makes the new pet active device-wide (`addPet(data, { select: true })`), so one mis-tap two taps from a vomit log costs the log *and* silently re-points every surface in the app at a different pet. The gate is `captureSurface` on `PetSwitcherPanel`, defaulting off. Four things generalise past this feature. **(1) Name the prop for what the HOST is, not for what it hides** (`captureSurface`, never `showManagementRows`) — a new host then declares itself and inherits the rule, instead of re-deciding a policy the shared component owns. **(2) The rule hides ADMIN, never a pet** — the switcher still answers the one question its title asks, and a "simplification" that dropped a pet on a capture surface would be the wrong-pet class (CUL-574) wearing this fix, so the test asserts the pets are all still there rather than only that the rows are gone. **(3) Drop the query with the row.** The archived link is the only consumer of the panel's `pets` count, so on a capture host that fetch is skipped entirely — a round-trip whose answer nothing can read, made at the moment the owner is trying to log something — and the test asserts the **call**, not the row, because that is what tells *never asked* apart from *asked, and hid the answer*. **(4) A wiring that the gate makes unreachable is kept, not deleted, when it is a defect guard.** `onNavigateAway` (CUL-662's dismiss-before-push) can no longer fire on `EventTypeSheet`, its only consumer; removing it would mean a future host that re-shows the rows rediscovers the wedge invisibly, so it stays with the reason in place and the order it pinned stays asserted on the panel, where the contract lives. **The deletion was only available because somewhere else had already gained the door** — CUL-618 put a switcher on the Pet tab and CUL-704 kept the single-pet header's, and before those, `/add-pet` and `/archived-pets` were reachable from this one file. So *check the door map before removing an entry point*: pulling a control out of the wrong surface is a **move**, and it is only a move if the destination already exists. **And the same prop carries the DISCLOSURE half (2026-08-29, CUL-680).** A capture host is, by construction, the one that frames the shared surface in scoped language — the log sheet's title is "Log for {pet}", the FAB chip "Logging for {pet}" — over a switch that is not scoped (`selectPet` persists to disk and re-points every surface). So `captureSurface` both hides what leaves *and* names the real scope, and a new capture host inherits both by declaring what it is. Two things generalise. **(1) Where the copy must be honest, prefer the CONTRAST to an enumeration**: "the whole app … not just this log" beats "Home, Trend and History", because Trend is a zone on Home rather than a tab, so the specific-sounding version ships a surface name the app does not have — and any such list dates the moment the tabs move. nyx-voice Pattern 2's push toward specificity is about naming magnitudes and anchors in *insight* copy; on a disclosure the specific thing is the scope contrast. **(2) A scoped-sounding label is only a defect where a CONTROL sits under it** — `app/log.tsx`'s identical "Log for {pet}" header is deliberately untouched, because that screen carries no switcher and so mis-states nothing.

### C-16 · Haptics (2026-08-22, CUL-604, `docs/nyx-app-polish-requirements.md` §5.6):

**Haptics (2026-08-22, CUL-604, `docs/nyx-app-polish-requirements.md` §5.6):** never import `expo-haptics` at a call site — go through the verbs in **`lib/haptics.ts`**, which are named for **moments, not patterns** (`commitSymptom()`, never `impactAsync(Soft)`). Raw constants all look interchangeable in a diff, which is exactly how the two tone rules get broken; naming the moment makes a violation visible at review. **A symptom commit is not a success** — routine commits take the success notification, a symptom commit takes a single soft impact (we acknowledge a 2am vomit log, never congratulate it; the same reasoning that withholds the gold glow from the `calm` beat). The tone comes from the payload's existing tone, which derives from `SYMPTOM_TYPES` — **never mint a second symptom predicate** (the diet-trial §5.3 lesson). **Silence on safety, by rule:** a safety card arriving or a red-flag read landing gets **no haptic** — plainness is the severity signal, and a buzz on bad news is the phone rewarding it. That absence is enforced structurally, not by memory: the module exports no verb a safety surface could call, and **`guards/haptics.test.ts` fails the build** if a safety component imports it (scan set derived from safety markers, so a *new* safety renderer is covered the day it is written; exemption only via an inline `// haptics-guard-ok: <reason>`). **There is exactly one exemption in the codebase — `components/home/SignalZone.tsx` (CUL-601), and the shape of it is the precedent to copy:** §4's arrival moment needs a tap on a file that renders safety cards, so the rule is kept **by gate rather than by intention** — the arrival is unreachable whenever the finding set contains a safety finding, and a test (`a safety-led first arrival plays no haptic`) pins that rather than the comment asserting it. Moving the call into an unscanned helper file would have avoided the exemption and defeated the guard, so don't: **take the exemption and pay for it with a gate and a test.** That arrival is also why the vocabulary is no longer literally seven verbs — `insightArrival()` was added because none of the seven fit (nothing was *committed*; the engine finished thinking), and §5.6's own rule forbids a call site reaching past the module for a raw constant. A new moment gets a new verb even when the payload matches an existing one; `lib/haptics.test.ts` pins the export list so adding one stays a visible, argued change. Every verb is fire-and-forget, swallows rejections *and* synchronous throws, and returns `void` — a cosmetic effect must never end up awaited on the critical path of a health write. A commit haptic fires at the **moment store's reveal**, not at the call site, so a new log path inherits its haptic with its card and a superseded card plays nothing.

### C-17 · Completion surfaces speak the record, not "Logged" (2026-08-23, CUL-606 + CUL-614, `docs/nyx-app-polish-requirements.md` §5):

**Completion surfaces speak the record, not "Logged" (2026-08-23, CUL-606 + CUL-614, `docs/nyx-app-polish-requirements.md` §5):** a commit confirmation names what was written — `"Vomit · found by 5:33 PM"`, `"Weight · 12.4 lbs"` — and the sentence is **derived**, never passed. `momentStore`'s named payload carries the record's structured fields (`LoggedRecord`), so a call site has nowhere to put a display string and the bare "Logged" is unreachable by construction; `lib/completionCard.ts` composes through `lib/logCopy` → `describeOccurredAt`, the same path History and the vet report use, so a beat can never claim more certainty than the row holds. **A "Change time" on a completion card is not the meal card's re-assert.** The meal card restates `witnessed` because a meal is witnessed by construction; copying that onto a symptom card would stamp `seen` over a row the owner only *found* — B-448's leak in a new place, and the vet report prints the difference. So the write splits by what the record holds: witnessed/estimated/unclassified **omit** the confidence key entirely; an open-ended window moves its discovery bound **with** the point; a two-sided window renders **no picker at all**, because one datetime control cannot express two bounds and every single-value reading discards or invents an edge. Withholding an affordance is cheap; a lying one is not. The literal is sourced from the record (`value: record.confidence`) rather than written inline — `lib/occurredAtConfidence.guard.test.ts` holds that a found-it classification reaches the DB through a variable, never a literal, and reading it back is what makes "this restates, it does not decide" provable. Relatedly, `updateEvent`'s `severity`/`notes` are now **optional-by-omission** like `confidence`: they were required and always written, so a caller that knew only the new time silently deleted the owner's note. **The rule is app-wide as of CUL-614, and its enforcement has two shapes** — the R1 card cannot be *handed* a display string (no parameter to put one in), and the R2 in-sheet beat (`components/log/SheetLogBeat.tsx`) cannot be *left without* one (`title` is required; the `'Logged'` default is deleted). Neither has a fallback that says nothing, and a nameless record names its kind (`'Food logged'`, `'Dose logged'`) rather than dropping to the bare word. ### C-18 · Every commit path routes through its completion card (2026-08-23, CUL-613, `docs/nyx-app-polish-requirements.md` §5):

**Every commit path routes through its completion card (2026-08-23, CUL-613, `docs/nyx-app-polish-requirements.md` §5):** a screen that writes a meal or a dose fires `showMeal` / `showMedication` — it does not roll its own confirmation. Reading the test and agreeing with it is not the check; three guards written that session looked right and **one did not discriminate at all** (it pressed an inert label and asserted a handler was not called — trivially true, and just as green with the defect present). The rule is worth the thirty seconds because the failure is silent in the direction that matters: a guard written by someone who knew exactly what the defect was, specifically to catch it, still missed it. **And split a new test by its required direction before writing it.** A *guard* must fail before the fix and pass after. A *refactor-safety* test is the opposite — it must pass **before and after**, because its job is to pin the behaviour you are preserving; one that goes red pre-change is describing something else, and you have no baseline. Write both against the pre-change tree and confirm each lands on its own side, or the suite cannot tell a preserved behaviour from a changed one. **And a guard's detector fixture lives OUTSIDE the tree the guards scan (2026-08-29, CUL-712)** — `guards/fixtureRoot.ts`'s `createFixtureRoot()`, never a file written into `app/` or `components/` and deleted in `afterEach`. Jest runs suites in parallel workers, so an in-tree fixture is live inside *another* guard's scan window, and the two failure modes are an **ENOENT crash** (unlinked between the directory walk and the read — hit for real on CUL-654, green on the identical re-run) and, worse, a **spurious violation** naming a file that no longer exists by the time anyone looks, pointing at a rule nobody broke. An exemption marker is no protection: markers are per-guard, so a fixture deliberately exempted for its owner is fully exposed next door. That noise floor is load-bearing rather than cosmetic — § Git Workflow forbids fixing a red run by weakening the check, and an intermittent red with a vanished file is exactly the pressure that gets a guard weakened or a suite dropped. **The fix is a helper, not an exclusion**, and the distinction is the point: a per-scanner `__*_guard_fixture__*` denylist is one line each but the *next* guard has to remember it, which is the shape that produced this — all three authors knew about `afterEach` and none knew about the neighbour. So the scanner takes a **required** `root` parameter (a default silently re-points a forgetful self-test at the real working tree — the CUL-708 shape where silence is a claim), the fixture keeps its `components/`/`app/` *shape* inside that root so the walk under test is still the live one, and `createFixtureRoot` **throws** if the path lands in-repo. Precedent that never had the problem: `guards/edgeFunctionDeploy.test.ts` — a scanner that can be pointed at a root never has to trust its own working tree. **And the teardown is guarded by PROVENANCE, not only by containment** — `removeFixtureRoot` refuses any path it did not itself hand out, on top of refusing anything in-repo. A recursive delete standing behind a single predicate is one wrong predicate away from deleting source, and that is not hypothetical: a reviewer probing exactly that question during this build wiped `components/` from the working tree in seconds (recovered from HEAD; nothing lost, because it was committed first). The two checks are deliberately independent — containment can be wrong, provenance cannot — which is the CUL-641 shape applied to a destructive test helper: *the gate is the whole rule*. One corollary for the threading itself: the risk is a scan quietly ending up pointed somewhere emptier, which leaves the guard green over real defects, so prove the LIVE scan still fires by dropping a real violation into the real tree — the floor assertions (`textCount > 500`, `callSites(...).length > 0`) are what stop an empty set passing, but they are not a substitute for the probe.

### C-19 · A record-anchored DATE is free; a DURATION is guarded (2026-08-30, CUL-69):

**A record-anchored DATE is free; a DURATION is guarded (2026-08-30, CUL-69):** where a surface re-anchors a claim to the record — the earliest logged entry, the first row of a type — that DATE is a fact about the record and costs nothing to state. A **duration** derived from the same anchor is not: it is an inference the detection engine protects with three floors (`loggingEligible` over both halves of the onset span, `countDistributionWeeks`' B-188 anti-barbell packing, the `minSpanDays`/`minEpisodes` conjunction), and **any layer that widens it inherits those floors or must not widen it**. ### C-20 · Every soft delete goes through the one shared reversal (2026-08-28, CUL-641):

**Every soft delete goes through the one shared reversal (2026-08-28, CUL-641):** a surface that removes a logged event calls **`reverseLoggedEvent`** (`lib/undoLog.ts`), never `lib/db.ts`'s raw `softDeleteEvent` — **`guards/reversePath.test.ts` fails the build** on a file that does (exemption: an inline `// reverse-path-ok: <reason>`; `lib/widgetBridge.ts` holds the one, a loop-driven rollback of replayed captures where the shared path would fire one sync flush per row). So the reversal is literally shared, and a new side-effect is inherited rather than added N times. Two rules travel with it. **(1) A delete site never has to know what it removed:** `reconcileWeightSnapshotAfterDelete` self-guards on the event actually being a weigh-in, because four hand-rolled "is this a weight check?" checks is the shape that produced the bug. It reads the **parent's** `event_type` alongside the child, so a weigh-in whose child has not hydrated yet is an *unevaluable weigh-in* that says so, never a silent "this wasn't one" — a bare child lookup turns `events`-before-`weight_checks` hydration into a logging gap scored as an absence. And a record-scoped store patch goes through **`patchPetById`**, never `updatePet`: the latter derives its target from `activePet`, and a record screen is reached BY ID for any pet (CUL-574), so an is-it-active guard there silently skips the pet the record belongs to — `selectPet` never refetches, so that staleness survives the session. **(2) When a denormalized snapshot has TWO writers, a delete may only ever undo the write THIS record made.** `pets.weight_kg` holds both the owner's onboarding/Edit-profile weight and the latest weigh-in, so the rule gates on identity first: *is the snapshot this reading's own value?* No → leave it entirely alone. Yes → latest remaining reading, else the value this reading displaced (only Undo knows it), else null. **The gate is the whole rule, and the first draft shipped without it on a rationale the adversarial pass falsified in both directions.** Ungated re-pointing *destroyed* an owner-typed Edit-profile weight when an unrelated older reading was deleted; and "leave it alone when nothing remains" preserved **the deleted reading itself**, not a profile weight — because the WRITE path had already overwritten the onboarding value at log time, so what survived was the corpse, which `WeightTrendCard` then captions *"From {pet}'s profile."* and `EditPetModal` writes back on Save. Comparing the deleted row's own value to the snapshot separates *"this number is the corpse"* from *"this number is the owner's"* at zero schema cost. **The generalisable trap: a "leave it alone, we might destroy something" argument is only as good as the claim that the something still exists** — check whether an earlier writer already destroyed it, or the caution preserves the very thing it was meant to remove. Nulling a corpse is not data loss, and it matters most at a **pre-filled** field: Principle 2 trains owners to confirm rather than type, so a stale number sitting in `seedWeightPrefill` is one tap from becoming a real reading, biased toward the older/heavier value — the direction that masks loss. Undo's extra power is an *information* difference, not an inconsistency, and it is why `previousSnapshotKg` rides on `NamedPayload` and **not** on `LoggedRecord` (CUL-606's shape rule: that type carries only what the ROW says; a displaced snapshot is a side-effect ledger). Absent and `null` are read apart with an explicit `undefined` check — never `?? null` — or an ordinary History Remove wipes a profile weight it never touched.

### C-21 · Every destructive action carries exactly one safety net — a confirm before, or a way back after (2026-08-29, CUL-645):

**Every destructive action carries exactly one safety net — a confirm before, or a way back after (2026-08-29, CUL-645):** the app's five destructive actions are consistent once read together, and the rule is *confirm XOR reversal*, never "everything confirms." History Remove, the detail screen's Remove and Remove photo take the **confirm**; food archive takes the **way back** and its own comment argues the trade in as many words (*"the undo snackbar is the safety net… a modal asking 'are you sure?' for a reversible tidy-up would be friction, not safety"*); vet documents deliberately take **both**. ### C-23 · A push marks the VERSION it sent, never the row (2026-08-30, CUL-691):

**A push marks the VERSION it sent, never the row (2026-08-30, CUL-691):** a sync writer reads its rows, goes to the network, and marks them synced when the response lands — and on every LWW table an owner can rewrite the row inside that gap. So `markSynced` (`lib/sync.ts`) takes rows and matches `WHERE id = ? AND updated_at IS ?`, and `applyFailurePolicy` does the same, because a refusal must be recorded against the version that was refused. Marking on an id alone strands the newer change forever: nothing re-queues it (the row reads synced) and hydration will not correct it (the local `updated_at` is newer, so LWW keeps the local state) — and on the failure side it is worse, since `sync_error` on a fresh tombstone drops the row out of every queue read (`synced = 0 AND sync_error IS NULL`) for the life of the install. **`IS`, not `=`** — null-safe, or a legacy NULL `updated_at` can never be marked and the row re-pushes forever, which is the B-398 wedge. Three things generalise. **(1) The guard rests on an invariant that is now scanned, not remembered:** a re-queueing mutation must always MOVE `updated_at` — true across all sixteen `synced = 0` write sites, but it was true by convention, and deleting the stamp from `softDeleteEvent` re-opens the defect with the whole suite green. `syncQueue.test.ts` already refused exactly that for the other half of the same write contract (clearing `sync_error`); the `updated_at` half now sits beside it. Watch for the shape already in the tree: `adoptVetDocumentLocalUri` writes `vet_documents.local_uri` and skips `updated_at`, safe **only** because `vetDocumentRowToRemote` omits that column from the push payload — two facts in two files with nothing tying them. **(2) A TYPE ASSERTS NOTHING A TEST CAN READ.** The unguarded set was a hand-written type union, and moving `vet_documents` into it re-created a closed bug (B-478 VF-6) on the exact queue that bug was found on, with `tsc` clean and 6194 tests green. A runtime check keyed on a hand-maintained type is one-directional by construction: it catches the registry disagreeing and is blind to the union claiming. So the set is a runtime array the type derives from, and the two halves pin each other — schema↔registry in `syncQueue.test.ts`, registry↔union in `sync.test.ts` (the split is forced: `lib/syncQueue.ts` is deliberately outside the supabase import graph and cannot see `lib/sync`). **(3) A test that reads an id out of a captured statement is not testing the statement.** `markedIds()` took `params[0]` and discarded the guard, so `pushRows` binding a fresh clock — or `created_at`, the copy-paste shape — passed 6199/6199 while **wedging every LWW queue forever**. Asserting the SQL's shape (`toContain('updated_at IS ?')`) does not close it either; only replaying the real capture against a real row does, with a fixture whose `created_at` deliberately differs from its `updated_at`.

### C-24 · A queue drains ONE AT A TIME, and the wait is bounded (2026-08-30, CUL-622):

**A queue drains ONE AT A TIME, and the wait is bounded (2026-08-30, CUL-622):** a new push entry point goes through **`serializeQueuePush`** (`lib/sync.ts`) — one active drain per queue table, never two. CUL-691's version guard decides what a response may DO on return; it cannot decide what ORDER two requests reach the server in, and nothing serialized these pushes: every write path fires one and forgets it, and `syncCycleInFlight` guards only the full cycle (`syncNow`, `flushPendingForSignOut`). So the ordinary completion-card flow put two versions of one row on the wire at once — the insert's push, then "Change time" two seconds later, inside a card that lives 5000ms — and **whichever request Postgres applies last wins**. If the pre-correction one lands last every guard downstream still reads clean, because the correction's own mark is legitimate, so the row goes `synced = 1` and nothing re-queues it. **The half that makes it a correction the owner LOSES rather than a server that lags is `set_updated_at()`**: it re-stamps the server row with the server's clock on the conflict-update, so the stale copy is *newer* by hydration's `remoteT > localT` over rows at `synced = 1` — and the next pull writes the pre-correction value back over the correction on the device too. `hydration.ts`'s accepted server-time-LWW failure mode does **not** cover this: that ruling is two devices editing one row offline, where the app cannot know which edit came first; here it is one device, one owner, one correction, and the send order was ours. Four rules travel with it. **(1) A caller arriving mid-run gets a TRAILING run, never the active one** — the active run may already have read the queue before that caller's write, so handing it back is a promise that resolves without sending the row it was called for. One trailing run is enough (it reads the queue when it starts, so it subsumes every caller that arrived meanwhile), and its slot is released when it **starts**, not when it finishes, or a write landing after its queue read joins a run that structurally cannot see it. **(2) The wait is BOUNDED, and that is what makes serialising safe at all.** CUL-691 considered this fix and refused it for a reason recorded on CUL-733 — *a hung request with no timeout blocks every push behind it* — which is right, since supabase-js sets no request timeout. Past `QUEUE_PUSH_WAIT_CEILING_MS` a trailing run goes anyway, so a stalled queue degrades to **exactly the concurrent behaviour it had before the fix** rather than to a new failure mode. Judge a lock on a write path by where it degrades TO, and never drop the waiting run instead: on this path the waiting write is a tombstone or a corrected symptom time. **(3) Keyed per TABLE, not globally** — one global lock closes the defect too and makes every write wait behind an unrelated queue's round trip; the per-table scope is pinned by a test, not by intention. **(4) The trailing slot is checked BEFORE the in-flight slot**, and the order is load-bearing: the active run's `.finally` clears the in-flight slot several microtask jobs before the trailing run starts, so looking at in-flight first lets a caller landing in that window start its own drain beside the pending trailing run — two concurrent drains, the defect back. Joining a pending trailing run is always safe, because one that has not started has not read the queue. **(5) Every mechanism here is a one-token tidy-up away from doing nothing, and three of them survived a suite written specifically to prove them.** The trailing run calls `startDrain`, never `serializeQueuePush` (recursing **defeats the ceiling** — past it the slot is still held, so the recursive call schedules another wait, a chain ending only when the hung request does) and never a bare `drain()` (which starts a run that never claims the slot, so the next caller pushes beside it); and the slot release is identity-checked, never a bare `delete` (which lets a stale post-ceiling run clear the live run's slot). Each is *correct on the ordinary path*, which is what hides it. Of the three, one was caught by its own test on the first run and **two shipped green through all six original tests and the whole 96-case file**, found only when both reviewers mutated the source. The counting lesson is sharper than "write tests": the release test asserted **queue reads**, which are identical either way, and only asserting the **upsert count at the moment the next caller arrives** discriminates — *a test that counts the work done cannot see a caller that failed to wait.* **(6) The ceiling is calibrated against the DRAIN's duration, never the owner's window.** Justifying 15s by the completion card's 5000ms life measures the wrong thing: `drainEventAttachmentsQueue`/`drainVetDocumentsQueue` walk up to 20 compress-then-upload round trips and `pushRows`' isolation pass fires up to 100 sequential requests, so on those the ceiling is the *ordinary* path and the queue spends the rest of that run unserialized. Costless on `event_attachments` (insert-only), materially thinner on **`vet_documents`** (LWW, where a rename mid-upload is this exact defect). So the honest claim is *strong on the row queues, partial on the object queues* — bounding the REQUEST is what makes it uniform (CUL-743).

### C-25 · Owner-facing copy is guarded, not just reviewed (2026-08-18, B-477/CUL-445):

**Owner-facing copy is guarded, not just reviewed (2026-08-18, B-477/CUL-445):** keep raw provider strings out of owner-facing copy. `guards/ownerFacingCopy.test.ts` is a jest AST source-scan (the `widgets/CulpritWidget.test.ts` shape) over `app/`+`components/`+`lib/`+`hooks/`+`store/`+`constants/` that **fails the build** when (a) an owner-facing display sink — an `Alert.alert(...)` body, a `set*Error*()` setter, a Snackbar `.show({ message })`, a `<Text>` child, or a display-copy prop — reads a display string off an error (`error.message`, `String(err)`, `err.toString()`, `(error as Error).message`, `error!.message`, a template interpolating one, or a Postgres `.details`/`.hint`/`.code`), including one hop of local indirection (`const m = e.message; …(m)`) — the B-399 leak class, 15 sites wide; (b) any rendered owner-facing string carries a `!` (nyx-voice Pattern 4, app-wide); or (c) an error-copy string uses an untranslated clinical term (nyx-voice Pattern 5, error-sinks only — the vet report is a separate audience and keeps clinical language). 'lit' : 'lit'`) and storing a raw error for mapping-at-render (`setFailureError(error)` → `isOffline(...)`) are both spared, since only the extraction of a display *string* is flagged. For a genuine false positive, an inline `// copy-guard-ok: <reason>` (reason mandatory) suppresses one finding — an exemption is a named decision, never a silent hole. **The base-is-error-like rule has a blind spot the guard had reasoned itself into, closed 2026-08-30 (CUL-651): a DATABASE COLUMN is not error-like syntactically**, so `{row.ai_extraction_error}` — the Edge Function's verbatim `err.message`, stored — rendered a Claude HTTP status to an owner in a `<Text>` child while this file was green. An argument that holds for one kind of value and is silently assumed to cover all of them is how a guard goes blind while staying green.* **And one thing that generalises past copy, from the same fix:** the banner's gate (`isFailed && row.ai_extraction_error`) looked like belt-and-braces and was the only client-side thing separating *"we tried and could not read it"* from *"we did not try"* — the cap, the flag-off and a transport fault all stamp `'failed'` and write no error. So: *withholding an affordance is cheap and a destructive one is not* (CUL-606's rule, sharpened) — and, the transferable test, **when a fix makes a hidden state visible, follow the CONTROL that widening exposes, not just the state it reveals.** The gate is pinned in both directions with the reason beside it; the state those rows actually need is CUL-768's.

### C-26 · A shared module's boundary is what IMPORTS it, not what its name suggests (2026-08-29, CUL-717):

**A shared module's boundary is what IMPORTS it, not what its name suggests (2026-08-29, CUL-717):** owner-facing copy never goes in `lib/utils.ts`. ### C-27 · A service-role query names its subject by id PAIRED WITH ITS OWNER (2026-08-30, CUL-696):

**A service-role query names its subject by id PAIRED WITH ITS OWNER (2026-08-30, CUL-696):** any ad-hoc script or runbook SQL run on the service-role path — the Supabase SQL Editor, MCP `execute_sql` — scopes its subject as `WHERE p.id = '<uuid>' AND p.user_id = (SELECT id FROM auth.users WHERE email = '<owner>')`. RLS does not apply there, so **the query is the only thing scoping it to one account**. Two things that look like ownership checks and are not: a **name match** (`pets.name` is neither unique nor owner-scoped — there are genuinely two cats named "Nyx", the owner's and the QA mirror's, 958 and 771 live events, and `LIMIT 1` with no `ORDER BY` picked between them by query plan), and a **bare `id = '<uuid>'`**, which is correct only while that literal happens to name the right pet — a fact about the file's contents rather than a property the query enforces. Pairing makes a wrong or stale id return **zero rows** instead of another account's record. **Write the pair exactly once.** A second copy — a preflight, a guard block, a sibling subquery — can drift from the one the query actually uses, and then it validates a pair nobody ran: worse than no check, because a maintainer following the file's own diagnostic gets a confident answer to a question they did not ask. Where a file needs a preflight, point it at the live CTE (`SELECT * FROM target_pet;`), never at re-typed literals. Two corollaries the same session paid for. **(1) Zero rows is ambiguous and never means "this record is empty"** — it means the pair did not resolve, *or* the filter excluded everything, *or* the rows are soft-deleted; say which causes exist, or the CUL-575 class arrives in SQL. **(2) Scoping the subject does not scope the JOINS.** `meals.food_item_id` and `medication_administrations.medication_id` are bare FKs with no same-account guard (unlike `paired_event_id` / `diet_trial_id` / `vet_visit_id`, which got BEFORE triggers in 023/041/044 for exactly this reason), so a correctly-scoped export can still carry another account's food brand or drug name under the right `pet_id` — reproduced end-to-end, zero live instances, tracked as **CUL-736**. ### C-28 · An adversarial rewrite of owner-facing copy re-enters the voice pass (2026-09-01, CUL-778):

**An adversarial rewrite of owner-facing copy re-enters the voice pass (2026-09-01, CUL-778):** when the `adversarial-reviewer` (or any clinical/statistical pass) changes a string an owner will read, the Designer / `nyx-voice` read runs again on the *result*, and the DoD persona line says so. ### C-29 · Timezone-honest fixtures (2026-08-01, B-514):

**Timezone-honest fixtures (2026-08-01, B-514):** the day boundary is LOCAL midnight (B-421), so **a fixture for a local-day question must not be a UTC literal** — `Date.parse('2026-07-24T12:00:00Z')` is already 25 Jul at UTC+13/+14 and 23 Jul at UTC−11, and the assertion silently becomes a statement about the runner's clock. Two idioms, chosen by what the code under test reads: pass an **explicit `timeZone` argument** where the helper takes one (`getDietTrialProgress(trial, now, 'UTC')`), or build the instant from **local components** (`new Date(2026, 6, 24, 20, 0)`) where it does not — and it deliberately does not on the widget/publisher path, whose device zone *is* the owner's midnight. Never widen a production signature just to make a test pinnable. Where one value is read two ways (a lexical `YYYY-MM-DD` off stored text *and* a local day index — `buildDeletedVetDocumentRow`, B-640) no single instant pins both: use UTC literals **at the same time of day**, since two instants sharing a time-of-day shift together and their local-day *difference* is invariant. Enforced by the **`App (jest, non-UTC timezones)`** CI job (UTC+14 / UTC+12:45 / UTC−10) — seven suites had drifted before it existed. Offset extremes are **not** a superset: UTC+14 missed a failure the +12..+13 straddle band caught, so add a zone rather than assume the ends cover the middle. Do not "fix" that job by pinning it back to UTC.

### P-1 · CI on every PR (B-390): what the first run taught

- **CI runs on every PR (B-390, `.github/workflows/ci.yml`, shipped 2026-07-25 via #440).** Two jobs: `App (typecheck + jest)` (`npm ci` → `tsc --noEmit` → `jest --ci`) and `Edge Functions (deno test)` (`deno test` over `supabase/functions/` — the suites `jest.config.js` ignores, and the **only** type check covering that path since `tsconfig.json` excludes it). This does not replace the pre-push hook or the DoD — it makes them non-optional. Three standing facts about the workflow: the Deno job runs `npm ci` **on purpose** (its type-check resolves a transitive `@types/node` out of `node_modules`); the Deno test step carries **`--allow-read=supabase/functions`**, which is **load-bearing, not cruft** — `deno test` grants no filesystem permission by default, and `detectionSoftDelete.test.ts` (B-071) reads `generate-signal/index.ts` to assert every query feeding the detection engine still carries its `.is('deleted_at', null)` filter, so stripping the flag turns that guard into a `NotCapable` failure (the grant is read-only and cannot re-open the network `--cached-only` closes); and both jobs must stay green — do not "fix" a red run by weakening the check (`--no-check`, `continue-on-error`, dropping a suite) without saying so in the PR. Actions are **SHA-pinned**; bump the SHA and its trailing version comment together. _The gate is live (2026-07-25):_ the `main` ruleset is **Active** with both checks required, an **empty bypass list** (nobody bypasses, including the owner), required PR + 0 approvals, require-branches-up-to-date, block-force-pushes and restrict-deletions. A red check now blocks the merge, so a green CI run is a precondition of shipping, not a report.

### P-3 · The claim ritual: why status alone is not a claim (CUL-624)

**`In Progress` on its own is not a claim, and a check keyed on status alone is worse than none.** The launch path sets `In Progress` at session start, so status says only *someone started*, never *who* — and the someone is usually you. Measured 2026-08-30: CUL-726 went `In Progress` 28 minutes before its PR, CUL-691 63 minutes, CUL-624 about fifty seconds before this session's first tool call. A status-only rule would have stopped the session that wrote this rule. **The branch name in the comment is the discriminator**; the status is what makes the issue visible to a `list_issues` sweep. So: another branch's claim, recent, no merged PR → **stop and surface** — do not plan, do not code, name the branch and the claim time and ask. Another branch's claim >24h old with no open PR → stale; say so in one line, post a fresh claim, continue. An open PR already referencing the issue → that is work in review, not a claim → surface before touching it. Nothing at all → claim it and carry on.

### P-12 · Design mocks are Artifacts — same-URL republish, full text

**Design mocks are Artifacts, and a mock round re-publishes to the SAME URL (instituted 2026-07-31).** Every mock round ships twice: the committed `docs/culprit-<track>-mockups.html` file is the source of truth and what review reads, and a published **Artifact** is how the PM actually looks at it (phone, no clone, no Codespace). The rule that matters: **round N+1 re-publishes over round N's artifact URL** — pass `url` to the Artifact tool, or the same `file_path` inside one session — so a link the PM has already opened, bookmarked, or pasted into a thread keeps resolving to the current round instead of silently going stale beside a newer one they never got. Corollaries: keep the `<title>` and favicon stable across rounds (the PM finds the tab by its icon, and a changed title reads as a different document); name the round *inside* the page, not in the title, so the URL's identity is the track and the page's identity is the round; and when a round supersedes an earlier one, say so in the page so a reader who scrolled back knows which frames are dead. `Artifact({action: 'list'})` finds the URL when a later session no longer has it in context — this is the only way to target an existing artifact, since a session that did not publish it always mints a new URL.

### P-13 · Split current from archive, full text
