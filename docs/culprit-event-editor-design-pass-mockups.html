What an edit writes

Times are shown in the phone's zone and stored in UTC (toISOString); nothing on this page changes that. Remove is a soft delete through the one shared reversal (reverseLoggedEvent, a deleted_at tombstone), never a DELETE. A replaced photo is the one hard removal: the old object leaves Storage, which is why CUL-2176 matters. Only the fields the owner touched are written (B-448), and that rule is the reason S1 keeps a form.

The question: edit in place, or a screen of its own

Brief S1. These three are options for that one decision, not today / faithful / pass. All three draw the same vomit: Biscuit, Tue 21 Oct, 2:14 AM, seen, a photo and a note.

Why not (C). The record screen is a reading surface whose safety render changes only by ruled brief (PR-10). Opening its rows in place puts form controls between the verdict and its facts, turns every tap into a write (the editor's Cancel discards today, and its touched-only rule depends on staging), and the look's "at least one word" and the weight's "a real number" checks have no Save to stop at. PR-10's P1 already made Edit a header action that opens a form. (B) gets what in place promised (the same order and the same rows as the record, so the edit reads as the record) without those costs.

§19

Motion

Today: the editor rises as a page sheet; the date picker opens inline and pushes the form down; Save dims while it writes. Nothing loops.

Faithful and design pass: nothing new moves. The time opens TimeEditSheet (the one "Change time"), so the form never jumps under a finger. Save becomes the Tick in place of its label while the write is in flight (the app's one loop; Reduce Motion: still, full opacity). The loading state (§12) is Skeleton rows, under a second. Remove's confirm is the platform alert; the rigid haptic fires on its confirm, never on the row (CUL-604).
